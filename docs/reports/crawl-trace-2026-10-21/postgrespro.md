### 3.1 `304` → `source_unavailable` — 520 (главная потеря прогона)

Текст отказа у всех 520 одинаковый:

```
CrawlError: Scrapy-краул '<url>' не удался: Ignoring non-200 response
```

Это **не** сбой источника: сервер корректно ответил `304 Not Modified`, потому что
валидаторы были отправлены (`If-None-Match`/`If-Modified-Since`) и совпали. Кэш
подтверждает — мета записи содержит и `etag`, и `last_modified`:

```json
{"content_type": "application/pdf", "etag": "\"59e75db1-96ac5\"",
 "final_url": "https://edu.postgrespro.ru/dba1-9.4/dba1_03_install.pdf",
 "last_modified": "Wed, 18 Oct 2017 13:57:05 GMT", "status_code": 200}
```

Механизм потери класса: в `core/adapters/crawl_scrapy.py` не выставлены ни
`HTTPERROR_ALLOWED_CODES`, ни `handle_httpstatus_list` (`DEFAULT_SCRAPY_SETTINGS`,
`:117-131`), поэтому `HttpErrorMiddleware` поднимает `HttpError` на любой не-2xx.
Ответ уходит в errback (`_failed` → `_record_failure`, `:322-345`), который знает только
404/410 и oversize, — и `304` падает в `source_unavailable`. Ветка «304 → байты из
кэша» в `_raw_page_from_scrapy_response` (`:375-385`) существует, покрыта кодом и
**недостижима** на реальном пути.

**Цена, измеренная по данным прогона:**

| | шт. |
|---|---|
| всего `304` | 520 |
| из них `url_state.doc_version_id` указывает на известный документ | 243 |
| из них `document_version.status = 'active'` | **240** |
| из них попало в `corpus_docs` этого прогона | **0** |

То есть **240 документов, которые система уже знает и считает активными, в корпус этого
прогона не попали**. Остальные 277 `304` — URL без `doc_version_id` в `url_state`
(впервые увиденные в этом цикле либо сброшенные прошлой сессией): они бы дали новые
документы, но тоже не дали.

Это и есть главный дефект среза: он делает недельный инкрементальный цикл
**разрушительным** — документ, который не изменился, выпадает из корпуса, а не
переиспользуется.

### 3.2 `robots_disallow` → `source_unavailable` — 134

Текст: `Scrapy-краул '<url>' не удался: Forbidden by robots.txt`. Это robots-запрет,
записанный как «источник недоступен».

| хост | шт. | что там |
|---|---|---|
| `repo.postgrespro.ru` | **104** | весь хост: `/` + 102 `/doc/...` (PDF/EPUB документации Enterprise/Standard/ora2pgpro) + `/ora2pgpro/keys/pgpro-repo-add.sh` |
| `postgrespro.ru` | 26 | `/order*`, `/user*`, `/useragreement` — формы заказа и ЛК |
| `pubgit.postgrespro.ru` | 2 | `/` |
| `support.postgrespro.ru` | 1 | `/` |
| `nextcloud.postgrespro.ru` | 1 | `/` |

Почему это не косметика: `robots_disallow` входит в `BLOCKING_FAILURE_KINDS`
(`core/domain/enums.py:110`), `source_unavailable` — нет. Записанный класс **понижает
блокировку**: `corpus_coverage.complete` для `postgrespro` может стать `True` при 134
robots-запрещённых URL, включая целый хост `repo.postgrespro.ru`, где лежит
дистрибутивная документация продукта. Ровно ту дыру, которую закрывает гейт 2.3.0.

Отдельно видно, что robots-запрет на `/order*` и `/user*` — это штатное поведение
сайта (личный кабинет и заказ), а не потеря контента. Но `repo.postgrespro.ru` —
потеря содержательная: там 102 URL документации.

### 3.3 oversize → `source_unavailable` — 19

Текст: `Expected to receive N bytes which is larger than download max size (20971520)`.
Все 19 — `edu.postgrespro.ru`, все — учебные материалы и демо-базы:

```
DBA1-handouts-16.zip, DBA1-handouts-13.zip, DBA2-handouts-16.zip, DBA2-handouts-13.zip,
DEV1-handouts-16.zip, DEV1-handouts-12.zip, DEV2-handouts-16.zip, DEV2-handouts-12.zip,
QPT-handouts-16.zip, PGPRO-handouts-16.zip,
demo-small.zip, demo-medium.zip, demo-big.zip,
demo-small-20161013.zip, demo-medium-20161013.zip, demo-big-20161013.zip,
demo_small.zip, demo_medium.zip, demo_big.zip
```

Причина потери класса — `_is_oversize_failure` (`crawl_scrapy.py:503`): предикат ищет
`maxsize` / `maximum size` / `downloaded more than` / `too large` / `filesize` /
`stopdownload`, а Scrapy пишет `larger than download max size`. Проверено прямым вызовом
на точной строке: `False`.

Это ровно тот сценарий, который снимает `crawl.max_artifact_bytes = 256 MiB` + спуск в
архивы: 19 архивов учебных материалов сейчас отсечены как «недоступные», хотя они
доступны и содержат PDF.

### 3.4 `parser_failed` — 5 (класс верный, содержание разное)

```
edu.postgrespro.ru/dbtech/dbtech-2018-msu-4-sql-intro.pdf
postgrespro.ru/media/docs/enterprise/9.6/ru/postgres-A4-fop.pdf
        → docling: статус конвертации PARTIAL_SUCCESS
postgrespro.ru/media/docs/enterprise/9.6/ru/postgres.epub
postgrespro.ru/media/2025/03/04/how-to_sec_1+2_SoD+SecureSchema.sql
postgrespro.ru/media/2025/03/04/how-to_sec_3_Masking.sql
        → trafilatura: извлечение не дало текста
```

Два разных дефекта в одном классе:

- **`PARTIAL_SUCCESS` выбрасывается целиком.** `extract_document.py` считает любой статус
  кроме `SUCCESS` ошибкой, а docling при частичном успехе отдаёт готовые страницы.
  Здесь это стоило двух PDF.
- **`.sql` и `.epub` уходят в HTML-путь.** Расширения не документные по
  `document_suffix`, поэтому `extract: auto` отдаёт их trafilatura, которая на SQL/EPUB
  даёт пустой текст. Отказ виден и класс верный, но маршрутизация явно не та.

Учёт fetched → doc по **системному** признаку (`url_state.doc_version_id` →

| A. документ по этому URL | 625 | 625 из 634 документов |

| D. документа нет вовсе | **16** | см. ниже |

Про 9 «doc-only» URL: элемент сеанса существует под другой формой того же адреса

против `https://postgrespro.ru/…`). Это артефакт сравнения, а не потеря; но он
показывает, что URL документа в `corpus_docs` — не тот URL, который обошёл краул, и
сопоставлять таблицы «по сырой строке» нельзя.

149 дублей — это не потеря, а работа дедупа корпуса: `?utm_source=hero`,
`/materials/item/5971096` vs `/materials/5971096`, `/dmedia/…` vs `/media/…` (один и тот
же файл), `?lang=ru`-варианты. Победитель дедупа — первый по порядку ingest, поэтому
документ может храниться под URL, который оператор не заказывал
(`/products/postgrespro/enterprise?utm_source=hero` выиграл у чистого URL).

## 5. Чем именно остановился обход

**Исчерпание фронта**, а не потолки — с одной оговоркой про бюджет:

| потолок | значение | факт |
|---|---|---|
| `max_documents` | 800 | `fetched` = **790** — не достигнут |
| `max_depth` | 8 | максимум **4** — не достигнут |

Очередь опустела при 790 < 800 и `pending = 0`, значит последний элемент был добыт
до исчерпания ёмкости. Восемь неиспользованных единиц бюджета — следствие того, что
`max_documents` считается по retained-страницам, а часть элементов ушла в отказы.

**Оговорка о доказательности:** `truncated`/`truncated_reason` в БД не персистятся
(они живут в `IndexBuild`, который не был записан), поэтому «усечения не было» — вывод
из счётчиков, а не прочитанная запись. Это отдельная дыра наблюдаемости, общая для всех
трёх протоколов.

Почему фронт кончился на глубине 4 при разрешённых 8: расширяют обход только
`fetched`-страницы. На глубине 3 из 873 элементов **574 — отказы** (520 из них — те
самые `304`), на глубине 4 из 505 — 119. То есть глубина 3 была почти полностью
«съедена» отказами: страницы, которые не удалось обработать, не дали ссылок. Правильно
обработанный `304` дал бы переиспользованный документ, но не расширил бы BFS; а вот
robots-запрет на `repo.postgrespro.ru` (104 URL) закрыл целое поддерево документации.

## 6. Аномалия: 2 из 3 seeds не дали ни одного элемента

Для `https://postgrespro.ru/docs/` и
`https://postgrespro.ru/products/postgrespro/enterprise/` в `crawl_session_items`
**нет строк** — ни `fetched`, ни `failed`, ни `pending`. В `url_state` тоже нет строк с
этими URL (там есть только `https://postgrespro.ru/docs` без слэша и
`…/enterprise` без слэша — обе добыты BFS'ом первого корня, на глубинах 3 и 1).

Что установлено точно:

- блэклист их не зачёркивает (`exclude_paths` не матчит эти пути, проверено);
- профиль резолвится (`max_depth: 8`, `max_documents: 800`);
- они не были дублями: строк с trailing-slash формами нет вообще;
- их содержимое всё равно попало в корпус — но через BFS первого корня, на глубинах
  1 и 3, **из бюджета первого корня**.

Что не установлено: механизм. Кандидаты по коду — ранние возвраты `_drain_root`
(`seed_blacklisted`/`seed_truncated`, `corpus.py:4618-4622`) и `note_consumed`
(`:4560-4592`), но статически ни одно условие не воспроизводится: блэклист ложен, а
`seed_truncated` требует `frontier.fetched >= 800` на момент `add_seed`. Лог прогона
утрачен при перезагрузке хоста, `errors` фазы не персистится.

Проверено на живом конфиге пакета: все 14 seed-URL прогона прогнаны через реальную
цепочку `resolve_crawl_limits` + `Frontier.add_seed` — **каждый вернул `queued`**
(ни блэклист, ни `max_documents` не отказывают на входе), а `state.db.seed_set`
содержит все 14 записей `enabled` с `source_ref = --urls`. То есть потеря происходит
**после** приёма в очередь, и ни одна из гипотез «до постановки» не подтверждается.
Отличить «упал на фетче» от «не дошёл до фетча» по ретенции нельзя — решение о
постановке корня не оставляет durable-следа.

**Это третий случай того же класса** (см. `pangolin.md` §6: `https://sbertech.ru/`).
Три из десяти seeds трёх первых продуктов (`jatoba` 3/3, `pangolin` 3/4, `postgrespro`
1/3) не оставили следа. Это уже не
курьёз: свойство «seed без строки неотличим от отсутствующего seed'а» ломает и бюджеты
(§1), и доверие к провенансу входов.

## 7. Что произошло после краула

Краул закончился в 20:03:19. Экстракция шла до перезагрузки хоста (20:22Z), после
которой процесс исчез. На момент смерти:

| | значение |
|---|---|
| `corpus_chunks` | **0** |
| `index_manifest` | **0** |
| `corpus_coverage` | **0** |
| `corpus_docs` | 634 (не двигался с 19:54:59) |
| `extract_cache` | 255 записей на диске |

То есть фаза корпуса не закрылась: **ни одного чанка, ни одного манифеста, ни одной
записи покрытия**. Публиковать статусы по этому прогону нельзя не только по правилам
(гейт покрытия), но и физически — нечего публиковать.

Задолженность экстракции на момент смерти была небольшой (D = 16, из них 14 — архивы,
которые всё равно не извлекаются), поэтому гигантский документ, застрявший в
предыдущем прогоне (`c741439c3758`, 683-страничный PDF), здесь **не воспроизвёлся**.

Память: пик приближения к краю зафиксирован на ~62-й минуте (`available` 681 MiB при
`used` 6253 из 6934, воркеры 2564.9 / 1623.6 MB, родитель 453.3 MB). OOM-killer за
прогон не срабатывал — смерть пришла от перезагрузки хоста, а не от нехватки памяти.

## 8. Наблюдения, требующие решения (не факты о продукте)

1. **`304` ломает инкрементальность** (§3.1): 240 известных активных документов выпали
   из корпуса. Это блокер для run2 и для недельного цикла вообще.
2. **`robots_disallow` записан как `source_unavailable`** (§3.2): блокирующий класс
   понижен, покрытие может стать `complete=True` при закрытом `repo.postgrespro.ru`.
3. **Предикат oversize не знает формулировку Scrapy** (§3.3): 19 архивов записаны как
   «источник недоступен».
4. **`url_state` отравлен** этими же отказами: 673 строки с
   `last_error_kind='source_unavailable'`, `consecutive_failures` до 3 (10 строк на 3,
   277 на 2, 392 на 1). При включении freshness-гейта (`next_check_at`) эти URL будут
   выглядеть деградировавшими, хотя сервер отвечал корректно.
5. **Архивы исчезают после фетча** (§4): 14 zip скачаны, лежат в `corpus_raw`, не дали
   документа и не оставили следа. Это ровно тот случай, ради которого нужен
   `archive_observations` с прогнозом до экстракции.
6. **`PARTIAL_SUCCESS` уничтожает готовую работу** (§3.4).
7. **Два seed'а не выполнились** (§6) — и вместе с ними два бюджета по 800.
8. **`truncated` не персистится** (§5) — «усечения не было» приходится выводить, а не
   читать.

## 9. Открытые вопросы

- Причина отсутствия двух seed'ов (§6) — общая с `pangolin.md` §6. Пока не найдена,
  провенанс входов для любого продукта с несколькими seeds недостоверен.
- Сколько документов реально есть на `repo.postgrespro.ru`: 102 URL документации
  заблокированы robots, и по трассе нельзя отличить «robots закрывает то, что уже
  есть в `edu`» от «robots закрывает уникальный контент». Нужен один ручной заход
  оператора.
- 240 «потерянных» документов: их байты есть в `corpus_raw` (из прошлых циклов), значит
  починка `304` вернёт их без сети — но проверить это можно только прогоном.
