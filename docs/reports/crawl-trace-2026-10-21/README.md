## Что это и чего здесь нет

Протокол **декодирует** то, что уже произошло: почему каждое URL получило свой
исход, докуда дошёл обход по глубине, сколько страниц стало документами корпуса и
чем именно остановился обход. Это не отчёт о качестве корпуса и не оценка
продуктов — только трасса краула.

Протоколы описывают **только фазу краула**. Экстракция/индекс в этом прогоне не
завершились (`corpus_chunks` = 0, `index_manifest` = 0, `corpus_coverage` = 0), поэтому
`❌`/`✅` здесь не выводятся и не обсуждаются.

## Источник данных

Всё восстановлено из двух баз, без обращения к сети. Обе — **замороженные копии**:
канонические пути прогона (`runs/ru-pg-dbms-e957c5e8fe49/`, `state/ru-pg-dbms/`) будут
переиспользованы следующим прогоном, поэтому протоколы ссылаются на снимок.

- `runs/_snapshots/ru-pg-dbms-e957c5e8fe49/cohound.db` — `crawl_sessions`,
  `crawl_session_items`, `corpus_docs`;
- `runs/_snapshots/ru-pg-dbms-e957c5e8fe49/state-at-freeze.db` — `url_state`
  (валидаторы, `reuse_kind`, `doc_version_id`), `document_version`, `seed_set`.

### Где лежат данные

Снимок снят `cp -a` в момент, когда прогон уже был мёртв (хост перезагружен
2026-10-21T20:22Z), и проверен `pragma integrity_check` = `ok`:

| файл | строк |
|---|---|
| `cohound.db` | `crawl_session_items` 1646, `corpus_docs` 697 |
| `state-at-freeze.db` | `url_state` 1645, `document_version` 939 |

`runs/` целиком в `.gitignore` — снимок **не** коммитится, он воспроизводим только
пока существует на диске. Числа в протоколах самодостаточны: каждая таблица/сводка
несёт свои значения, поэтому читатель без доступа к базам может проверить
арифметику по тексту (все итоги сходятся точно — см. «Общий срез»).

Ретенция сырых байтов (`corpus_raw/`) использована для пересчёта «текст страницы =
текст существующего документа»: текст извлекался тем же `trafilatura` на дефолтных
настройках, поэтому это **реконструкция**, а не авторитетный счётчик прогона
(см. «Открытые вопросы» в каждом файле).

**Ключевое ограничение среза:** прогон умер посреди фазы корпуса, а не после неё.
Сама фаза краула при этом **завершилась** у всех трёх продуктов (`pending`/`running` = 0,
последний фетч 20:03:19Z), поэтому «обход закончился» — наблюдение, а не догадка.
Но **чем** он закончился, в БД не записано: `truncated`/`truncated_reason` живут в
`IndexBuild`, который не был записан, а очередь `Frontier` не персистится. Во всех трёх
протоколах причина остановки выводится из счётчиков и названа как вывод.

## Единая легенда классов отказа

| Класс в БД | Блокирующий (I2c) | Что означает |
|---|---|---|
| `robots_disallow` | да | `robots.txt` запрещает URL |
| `parser_failed` | да | извлечение не дало пригодного текста |
| `extraction_timeout` | да | потолок времени извлечения |
| `payload_too_large` | нет | ответ больше потолка (`max_response_bytes` / `max_artifact_bytes`) |
| `source_unavailable` | **нет** | «источник недоступен» — фактически мешок для всего неклассифицированного |
| `not_found` | — | 404/410, терминально |

Расхождение между **настоящей** причиной отказа и **записанным** классом — главная
тема всех трёх протоколов: на scrapy-пути (`core/adapters/crawl_scrapy.py`,
`_record_failure`, `:322-345`) распознаются только 404/410 и oversize, всё остальное
падает в `source_unavailable`. Поскольку `source_unavailable` не входит в
`BLOCKING_FAILURE_KINDS` (`core/domain/enums.py:110`), потеря класса = потеря
блокировки покрытия.
