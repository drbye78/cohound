# Дубликаты URL в крауле: `_seen` дедуплицирует по точной строке

**Дата замера:** 2026-10-29, 15:05 MSK (снимок живого прогона `ru-pg-dbms-3d3dc7c3c969`,
прогон **продолжался**; числа — нижняя граница, а не итог).
**Инструмент:** `scripts/measure_crawl_efficiency.py` (БД открывается `mode=ro`,
прогон не останавливается). Сырьё: `raw-1505.jsonl` рядом с этим отчётом.
**Предмет:** сколько бюджета `max_documents` уходит на те же страницы под другой формой URL.

## Что измерено

`Frontier._seen` — множество **точных строк** URL (`core/pipeline/crawl_frontier.py:1082`:
`if url in self._seen`). Нормализации пути нет, поэтому `…/page` и `…/page/` — два разных
элемента очереди. Оба фетчатся, оба извлекаются, оба заряжаются в `max_documents`.

| продукт | `fetched` элементов | уникальных URL (после `rstrip("/")` в пути) | дубликаты | доля |
|---|---|---|---|---|
| `digital_q_database` | 2402 | 1238 | **1164** | **48.5 %** |
| `pangolin` | 629 | 575 | 54 | 8.6 % |
| `jatoba` | 23 | 23 | 0 | 0 % |
| **итого** | 3054 | — | **1218** | — |

Проверка на конкретной паре: `…/versiya-180/intro-whatis/` (глубина 1) и
`…/versiya-180/intro-whatis` (глубина 2) — оба `200`, `content_hash` **разный** (тело
отличается canonical-ссылкой), извлечённый текст совпадает. Поэтому `corpus_docs` = 1143,
а не 2402: документ дедуплицируется по `content_hash` на уровне корпуса. **Доказательство
не испорчено — испорчен бюджет.**

## Почему это важно

1. **Потолок `max_documents` тратится вдвое.** У `digital_q_database` объявлено 800
   (`packages/ru-pg-dbms/domain_profiles.yaml`), а обход дошёл до 1238 уникальных страниц
   при 2402 фетчах. Половина бюджета ушла на уже прочитанное.
2. **Форма дерева не та, что считали.** Замер 28.10 («TOC — 700 страниц») считал только
   ссылки оглавления. Снимок 15:05: глубина 0 — 14, 1 — 739, 2 — 893, 3 — 546, 4 — 232,
   5 — 37, 6 — 2 элемента (уникальных URL: 716 / 881 / 420 / 208 / 12). `max_depth: 8`
   ещё не исчерпан — дерево продолжало расти, поэтому «потолок по замеру» нельзя объявлять
   до конца прогона.
3. **Это не дефект доказательной базы, а дефект счётчика.** `truncated`/`complete`
   наследуют бюджет: продукт объявляется усечённым там, где он лишь дороже, чем нужно.

## Второй дефект того же счётчика (замер §6.3, `09`)

Реконструкция «уже израсходованного» на resume заряжает бюджет **первому корню-претенденту**
(`core/pipeline/corpus.py:3286`), а host-корень `https://database.diasoft.ru/` с
префиксом `/` перехватывает все URL продукта. Следствие: `truncated` и `complete` зависят
от того, перезапускался ли хост. Измерено: 1610 `fetched` при потолке 800 — ровно `2 × 800`,
то есть два перезапуска.

## Что с этим делать (не сделано, ждёт решения по границе)

Обе правки — `execution_change` (меняют корпус, а не провенанс), то есть новый `run_id`:

1. нормализовать ключ дедупа (путь без хвостового `/`; query — часть идентичности и
   остаётся), а не сравнивать точные строки;
2. заряжать бюджет **владельцу** URL (самый специфичный `root_path_prefix` — предикат уже
   есть в `_group_revalidation_items`, `core/pipeline/corpus.py:3332`), а не первому претенденту.

Потолки поднимать **после** замера дерева по факту: цифра «1188 страниц», названная в
промежуточном снимке 15:11, тоже устарела — глубина 4–6 появилась позже.
