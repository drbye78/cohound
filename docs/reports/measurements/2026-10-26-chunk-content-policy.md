# Что считать содержанием чанка: замер пяти политик отсева

**Дата:** 2026-10-26
**Прогон:** `ru-pg-dbms-3edf2b06097c`, продукт `jatoba`
**Сборка:** `cb_ecf3850d1bf7b0b2fdb08235` → `pb_72868f6b2a683d21bee7beb6` (9398 чанков)
**Метод:** лексический индекс строится в `/tmp/opencode`, рабочий `index_store` не трогается;
БД прогона — только на чтение. Оценщик не вызывается: меряется то, что он **увидит**.

## Вопрос

28 % чанков описаны как «формовая макулатура», и BM25 будто бы ставит её первым хитом.
Владелец попросил замерить три варианта политики отсева, прежде чем принимать
методологическое решение. Замерено пять — и **первая постановка задачи оказалась
неверной**: и доля, и вред были завышены. Ниже то, что показали числа.

## Главная поправка: предикат «мусора» был негодным

Первый предикат (назовём его **D0**) — «короче 40 символов ИЛИ плотность
букв/цифр ниже 0.35» — дал 2669 чанков, 28.4 %. Проверка на живых доказательствах:

```
записей cell_evidence в прогоне: 149 (130 direct + 19 derived-без-чанка)
со ссылкой на chunk_id:          106 (после отсева отсутствующих в корпусе)
D0 считает «мусором»:             33  ← из них 28 теряются при отсеве
```

Что это за 33 «мусорных» чанка:

```
| ja_anonymizer             | маскирование данных. Компонент «ja_anonymizer»
KNN                                | KNN                           | Х Х
| Функциональная возможность - J18 J5
| Использование синтаксиса JSONB +
. Компонент «ja_Log»                                            | ja_Log
копирование, восстановление и целостность данных
```

Это **строки матриц возможностей** — самый ценный материал для сравнительной карты:
`Х` в столбце = продукт поддерживает. Предикат длины/плотности не отличает
`| + | + |` от `| ja_anonymizer | маскирование данных |`: у обоих мало букв и много
разделителей. **D0 негоден как мера содержания.**

**Различающий признак — повторяемость структуры, а не плотность.** Бланк потому и бланк,
что он один и тот же в каждом документе. Скелет (схлопывание длины разделителей и чисел)
делает `| + |` любой ширины одним классом, а строку матрицы — нет:

| признак | чанков | доля |
|---|---|---|
| скелет повторяется ≥2 раз | 572 | 6.1 % |
| скелет повторяется ≥3 раз | 358 | 3.8 % |
| только пунктуация, ни одного слова | 39 | 0.4 % |
| уникальных скелетов | 8972 | — |

Топ повторяющихся скелетов:

```
49×  [<!- image ->]
37×  [| | № изменения: | Подпись отв. лица: | Дата внесения изм: | |-|-|-|]
29×  [0.0.0-0 0 0-0 Листов 0]
26×  [| |]
25×  [| | № изменения: | Подпись отв. лица: | Дата внесения изм: | |-|-|-|  …]
```

То есть настоящей макулатуры **6.1 %**, а не 28.4 %: остальные 22 % «низкой плотности» —
настоящие короткие строки таблиц.

## На реальной сборке проблема ещё меньше

Важно: оценщик видит не объединение top-10 всех запросов (до 30 чанков), а склейку по
`chunk_id` с сортировкой по скору и срезом до `cutoff_K=10` (`core/pipeline/evaluate.py:1179`). Первый
замер считал объединение — это была ошибка метода. Все числа ниже — один и тот же
предикат (скелет ≥2) на одной и той же сборке:

| политика | чанков | форм в top-10 | первый хит — форма | теряет доказательств |
|---|---|---|---|---|
| **base** | 9398 | **2.6 %** | **1 / 119** | 0 / 106 |
| **P1 отсев по плотности (D0)** | 6729 | **3.4 %** ⚠️ | 1 / 119 | **28 / 106** |
| P2 точные дубли ≥3 | 9186 | 2.6 % | 1 / 119 | 0 / 106 |
| P3 точные дубли ≥2 | 9105 | 1.7 % | 1 / 119 | 1 / 106 |
| P4a скелет ≥2, оставить 1 копию | 8972 | 1.4 % | 1 / 119 | 2 / 106 |
| **P4b скелет ≥2, снять все** | **8826** | **0.0 %** | **0 / 119** | **4 / 106** |
| P5 = P4b + чанки без слов | 8822 | 0.0 % | 0 / 119 | 4 / 106 |

Три вывода, которые видны только из этой таблицы:

1. **P1 хуже базовой по обоим осям сразу.** Она не только уничтожает 26 % доказательств,
   но и **повышает** долю форм в top-10 (2.6 % → 3.4 %): выкинув 28 % коротких содержательных
   чанков, она меняет статистику BM25 так, что оставшиеся формы всплывают выше. Политика,
   которая портит то, что должна чинить.
2. **Точный дедуп почти ничего не делает** (P2 — ноль изменений, P3 — −293 чанка): формы
   различаются длиной разделителей и не совпадают буквально. Поэтому и `content_hash`-дедуп
   их не видит.
3. **Скелетный отсев работает, но нужен вариант «снять все», а не «оставить копию».**
   Если оставить одну копию формы (P4a), она всё равно попадает в top-10 — доля падает лишь
   до 1.4 %, и первый хит-форма остаётся. Только полное снятие (P4b) даёт 0 %.

Единственный параметр, у которого форма была первым хитом, — `autovacuum под 64-bit XID`,
чанк `| + | + |` со скором 22.09. Снимает его только P4b.

## Побочный эффект P4, о котором надо знать

Убирая 572 чанка, политика меняет статистику BM25 (частоты документов, IDF) — поэтому
меняются скоры и порядок не только у «своих» параметров:

```
P4b скелет>=2: финальные 10 изменились у 61/119 параметров (у 29 из 53 остаточных ❓)
```

То есть снятие 572 чанков (6 %) переставляет выдачу у половины параметров — не только у
тех, где форма мешала. Это смена статистики BM25, а не точечная правка. Поэтому это
`execution_change` (`content_change` по сборке), а не «поправили фильтр»: старые прогоны
по чанкам становятся несравнимыми, нужен новый `run_id` и повторная оценка.

# Что это даёт для политики

| политика | вердикт |
|---|---|
| **Отсев по плотности (P1)** | **Отвергнуто окончательно.** Уничтожает 26 % настоящих доказательств и при этом *повышает* долю форм в top-10. Провал по обеим осям. |
| Точный дедуп по тексту (P2/P3) | Не работает: формы различаются длиной разделителей. Ноль изменений. |
| Скелет «оставить копию» (P4a) | Полумера: форма всё равно попадает в top-10. |
| **Скелет «снять все» (P4b)** | **Работает: 0 % форм, 0/119 первых хитов, цена — 4 из 106 ссылок и −572 чанка.** |
| Без слов дополнительно (P5) | +4 чанка к P4b. Не стоит отдельного правила. |

## Что это меняет в приоритетах

1. **D2 не объясняет `❓` и не является узким местом.** 2.6 % слотов и 1 из 119 первых
   хитов. Даже полное устранение даёт не карту, а чистоту прибора.
2. **Отсев по плотности нельзя применять ни в каком виде.** Он уничтожает 26 % настоящих
   доказательств, и делает это незаметно — матрицы возможностей выглядят как «мало букв».
   Если кто-то вернётся к идее «фильтровать короткие чанки», это уже замерено и отвергнуто.
3. **Скелетный отсев P4b — дёшево и корректно, но низкий приоритет.** 572 чанка, 0 %
   форм в top-10, 4 из 106 ссылок. Делать — когда появится причина трогать чанкинг
   (например, F3), а не отдельным раундом.
4. **Настоящий блокер — путь «честное НЕТ».** `❌` в прогоне **ноль**: не потому что
   функционал есть, а потому что доказательство отсутствия нельзя ни выразить в схеме
   оценщика, ни сохранить. Это отдельный отчёт и отдельная починка.

## Границы замера

- Один продукт, одна сборка, один профиль (R0, BM25). Dense-плечо влияет иначе — не мерено.
- «Содержательность» я определял структурно (повторяемость скелета), а не семантически.
  Чанк может быть формой и при этом уникальным по скелету — такие остаются в top-10 при
  любой политике; P4b снимает ровно то, что повторяется.
- Потеря «4 из 106» проверена по `source_id` существующих доказательств; на новых
  прогонах число будет другим (другой порядок чанков — другие id).
- Скрипты: `/home/roger/cohound-measure/d2_probe/` (`d2.py` — первая, неверная постановка;
  `d2b.py` — реальная сборка; `d2c.py` — скелетные политики и проверка доказательств).
