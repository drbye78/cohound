# Extract-кэш: hit-rate и цена вытеснения (O32, план 26)

**Дата:** 15.11.2026
**Дерево:** `266e9df` + рабочая правка `core/pipeline/extract_cache.py` (амортизация проверки
бюджета) — то есть замер снят **до** коммита правки, на том же хосте, что и остальные числа.
**Прибор:** `scripts/measure_extract_cache.py` (нейтрален к предметной категории: читает файлы
кэша и строки `document_version`).
**Хост:** WSL2, 7 GiB RAM, 12 threads, SSD (`/dev/sdd`).

Команда (воспроизводит всё ниже):

```bash
.venv/bin/python scripts/measure_extract_cache.py \
  --bench-files 1000 5000 10000 --repeats 2000 \
  --cost 44796:100:2000 --cost 44796:1000:2000 --cost 44796:10000:2000
```

## 1. Что лежит в кэше

| | значение |
|---|---|
| файлов `*.json` | **44 796** |
| суммарный размер | **924.6 MB** |
| размер записи p50 / p95 / p99 / max | 5 169 / 53 358 / 124 376 / **21 401 472** байт |

Документ плана 26 говорил о 24 277 файлах / 726 MB. Настоящее число — **44 796 / 924.6 MB**,
то есть кэш вырос в 1.84 раза по файлам с момента аудита. Это не расхождение методики: аудит
считал по одной раскладке, замер — по `~/.cohound/data/extract_cache` целиком, включая записи
членов контейнеров (у них ключ — хеш байтов члена, а не retained-файла).

## 2. Цена полного обхода (то, что делает `_evict_if_needed`)

`rglob("*.json")` + `stat` + сортировка по `(mtime_ns, путь)`, **без удаления**:

| повторов | медиана | min | max |
|---|---|---|---|
| 5 | **0.289 с** | 0.282 | 0.292 |
| 2000 | **0.299 с** | 0.291 | 0.387 |

Число устойчиво: 0.29 с при 44 796 файлах, разброс — единицы процентов. Цена линейна по числу
файлов (индекса нет), поэтому на 100 000 файлах её следует ждать ~0.65 с — это экстраполяция,
а не замер, и в отчёте она помечена.

## 3. Цена записи: бюджет включён против `budget=None`

Запись — `put()` одного `ExtractedDoc`; песочница из записей **медианного** размера реального
кэша (5 169 байт), потому что порог проверки считается в байтах.

| режим | медиана `put` | всего на 2 000 записей | обходов |
|---|---|---|---|
| `budget=None` (сегодняшний дефолт D8) | 0.0021 с | 4.10–4.38 с | **0** |
| бюджет 10 000 MB | 0.0021 с | 4.098 с | 0 |
| бюджет 1 000 MB | 0.0021 с | 4.197 с | 0 |
| бюджет 100 MB | 0.0021 с | 5.07 с | **1** |

Медиана `put` **не различает** режимы — обход случается редко, и в медиану не попадает.
Различие видно в сумме: 10.3 MB записанного при бюджете 100 MB (порог = 1/16 бюджета = 6.25 MB)
дают ровно **один** обход и +0.9 с к прогону.

## 4. Цена «обход на каждой записи» — та, что была до правки

Число обходов при проверке на каждой записи равно числу записей. Отсюда прямая цена прогона
(8 115 документов корпуса `ru-pg-dbms`, 08.11.2026):

```
8 115 × 0.289 с = 2 346 с = 39.1 мин
```

Это цена **только обходов** — без извлечения, без записи, без `fsync`. Отсюда правка:
проверка бюджета амортизирована по записанным байтам, порог — `EVICT_CHECK_BYTES_DIVISOR = 16`
(1/16 бюджета).

Амортизированная цена того же прогона: при бюджете 1 GB прогон пишет ≈42 MB (8 115 × 5 169),
то есть 0.7 порога ⇒ **ноль-один обход, ≤0.3 с**. Перебор бюджета между проверками — не более
порога (6.25 % при 1 GB) плюс одна запись; при `N` процессах над одним корнем — до `N × порог`,
потому что счётчик живёт в процессе.

## 5. Первое включение бюджета на существующем кэше — разово, но заметно

Бюджет 100 MB на кэше 924.6 MB: первый же обход вытеснил **25 425** записей из 44 796.
Это не дефект, а смысл бюджета, но цена названа: включение маленького бюджета на прогретом
кэше — это одноразовая пере-экстракция половины корпуса. Отсюда правило для оператора:
бюджет меньше текущего размера включается **осознанно**, а не «на всякий случай».

## 6. Hit-rate: кэш обслуживает 100 % документов **текущего** штампа

Считается по `state.db:document_version` (`content_hash` — хеш **текста**) против конвертов
кэша по полю `doc_content_hash`. Первый вариант прибора сопоставлял ключ кэша (`content_hash`
**байтов**) с хешем текста и дал 0/17 874 — это была ошибка прибора, а не факт о кэше.

| штамп экстрактора | попаданий / документов |
|---|---|
| **всего** | **14 931 / 17 874 = 0.8353** |
| `trafilatura-html-6` | **14 704 / 14 704 = 1.0000** |
| `trafilatura-html-5` | 48 / 2 985 = 0.0161 |
| `docling-doc-3:layout_tables/cuda/…` | 134 / 140 = 0.9571 |
| `text-plain-2` | 27 / 27 = 1.0000 |
| `docling-doc-4:full/cuda/…/ocr-cyrillic-v5` | 10 / 10 = 1.0000 |
| `docling-doc-4:layout_tables/cuda/…` | 5 / 5 = 1.0000 |

Читается так: **внутри одного штампа кэш полон** (1.0 на html-6, 27/27, 10/10, 5/5). Общие
16.5 % промахов — почти целиком `trafilatura-html-5` (2 937 промахов): это документы, которые
извлекались **до** `D2/D3` и с тех пор не пере-извлекались, потому что штамп сменился
(`html-5` → `html-6` → `html-7`) и старые записи кэша для них не годятся. То есть hit-rate
измеряет **не** качество кэша, а долю корпуса, ещё не прошедшего объявленный `execution_change`.
После пере-извлечения под `html-7` он вернётся к 1.0 и будет падать ровно на величину
следующего `execution_change` — это его нормальное поведение, а не деградация.

## 7. Что из этого следует для D8

1. **Бюджет по умолчанию `None` — верное решение, и теперь оно с числом.** Включённый бюджет
   без амортизации стоил бы 39.1 мин на прогон из 8 115 документов; с амортизацией — ≤0.3 с.
2. **Ось `deploy.extract.cache_max_bytes` включается без оговорок по цене** — цена проверки
   перестала быть доводом против.
3. **`scans` публикуется в `stats()`** — число обходов на прогон стало наблюдаемым. Без него
   «бюджет включён» было бы утверждением, которое нельзя проверить.
4. **Вытеснение живёт в каждом процессе отдельно** (счётчик байтов и `scans` — на экземпляр).
   Это остаётся известной проблемой: при `N` воркерах перебор бюджета — до `N × порог`.
   Индекс вместо скана отвергнут намеренно: он потребовал бы согласованности между процессами,
   а скан — единственный источник истины о занятом месте.

## Что не измерено

- Цена `fsync` на запись отдельно от записи (в замер входит суммарно: 0.0021 с на запись
  медианного размера). Отдельный замер `fsync` есть для `embed_cache`
  (`2026-10-25-embed-cache-footprint.md`: 40 372 fsync ≈ 207 с, ~5 мс/запись) — здесь он не
  повторялся, потому что предмет O32 — вытеснение и hit-rate.
- Поведение при `N > 1` процессах над одним корнем: сканирования конкурируют, счётчики не
  разделяются. Это свойство конструкции, названное в §7.4, а не измеренная величина.
- Экстраполяция 0.65 с на 100 000 файлов — расчёт по линейности, не замер.
