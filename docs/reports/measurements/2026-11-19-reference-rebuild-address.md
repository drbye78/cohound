# Reference-корпус PG 11–17: пересборка ради адреса чанка (19.11.2026)

**Дата:** 19.11.2026. **Дерево:** `a30bec3` (отпечаток сборки видит схему адреса).
**Прибор:** сама команда `hound baseline build`; сверка содержимого — прямой запрос
`corpus_chunks` (скрипт-однострочник, приведён ниже).
**Срез:** `~/.cohound/stands/ru-pg-dbms/reference/ru-pg-dbms/postgresql/{11..18}/`.

## 1. Зачем пересобирать

Замер `2026-11-18-reference-map.md` нашёл дефект: адрес чанка в reference-БД хранился во
внутренней форме чанкера `{doc}#{n}`, которую `parse_source_id` (`core/util/ids.py:60`)
не разбирает (нужно 3 или 4 сегмента через `:`). У прогона когорты адрес переписывает
`corpus_index._chunk_id`; сборка reference-корпуса этого не делала, поэтому дата носителя
I2d была, а адреса, которым её искать, — нет. Следствие: карта по такой сборке понижала
бы `❌` до `❓` с токеном `absence_undated`.

Адрес починен для PG 18 (пересобран 18.11), остальные семь версий сохранили прежний адрес.

**Почему первая попытка пересборки не сработала.** `build_id` — отпечаток **содержимого**,
а `reference_content_digest` считался по одним хешам текстов. Текст после правки адреса
остался байт-в-байт, отпечаток совпал, `build_id` совпал — и сборка ответила
«уже была: содержимое то же, ничего не перезаписано» (`12:41:13`, лог `v11.log`),
оставив в каталоге БД с неразбираемым адресом. Адрес — часть содержимого сборки (он
попадает в `corpus_chunks.chunk_id` и оттуда в `source_id` evidence), поэтому схема адреса
вошла в отпечаток: `reference_content_digest(chunks, address_scheme=CHUNK_ID_SCHEME)`,
`CHUNK_ID_SCHEME = "product:doc:chunk_no"` (`core/pipeline/reference_corpus.py:587`).

**Содержание не изменилось — это проверено, а не предположено.** Множества
`corpus_chunks.content_hash` (16-hex префикс `sha256` текста, его пишет чанкер) у старой и
новой сборки каждой версии **совпадают поэлементно**: у v11 7 232 уникальных значения из
8 370 строк в обеих сборках, и `set(old) == set(new)`. То есть пересборка не тронула ни
одного текста — изменился только адрес, и `build_id` сменился ровно поэтому.

## 3. Что теперь работает на всех восьми версиях

- **Адрес разбирается.** `chunk_id` вида
  `postgresql:ef4004…b0a5:0` → `parse_source_id` даёт
  `SourceRef(product_id='postgresql', doc_id='ef4004…', chunk_no=0)`. Старая форма
  `postgresql:abc#0` даёт `ValueError` («ожидается 3 или 4 сегмента»).
- **Дата носителя есть у каждого документа.** `read_artifact_dates` (тот же читатель, что
  использует `baseline map`) на всех восьми сборках возвращает `by_doc` ровно по числу
  документов: 1 100 / 1 108 / 1 116 / 1 141 / 1 151 / 1 151 / 1 131 / 1 136,
  `by_doc_version` пуст (у reference-сборки нет `corpus_artifact` — она пишется прогоном
  когорты). Значит `absence_undated` на карте по этим сборкам больше не возникает из-за
  адреса.
- **`current.json` указывает на новую сборку** каждой версии; выбор не по `mtime`.

## 4. Цена

- v11 — отдельный прогон (12:53); v12–17 — **44 мин** суммарно (13:34:14 → 14:18:12),
  то есть 5–9 мин на версию. Это цена **сети** на этом хосте (те же 4.4–5.5 мин, что и в
  первом замере 18.11), а не свойство линии.
- Пере-эмбеддинг **не нужен**: reference-сторона живёт на BM25 (векторов нет, §8.4
  плана 27), а `content_hash` не изменился.
- Повторная сборка теперь идемпотентна **по содержанию**: при том же адресе
  `reference_content_digest` даст тот же `build_id` и ответ «уже была».

```python
import sqlite3
def hs(db):
    c = sqlite3.connect(db)
    h = [r[0] for r in c.execute("select content_hash from corpus_chunks")]
    c.close(); return h
assert set(hs(old_db)) == set(hs(new_db))
```

## 6. Границы

- Карта (`hound baseline map`) по 11–17 **не перезапускалась**: пересобраны сборки, а не
  карты. `map_id` — функция условий, и он сменится сам, когда карта будет построена;
  повторять живой прогон LLM ради проверки адреса не требуется — адрес проверен на уровне
  БД (`parse_source_id` + `read_artifact_dates`).
- Замер **не** утверждает, что карта по 11–17 даст те же вердикты, что по 18: это другой
  корпус (другая версия документации), и вердикты — предмет отдельного прогона.
