# Гейт качества: гибридный проход PDF (pdfium + docling) — **не проходит**

**Дата:** 2026-10-28. **Вопрос:** если простые страницы PDF извлекать нативным текстовым слоем
pdfium, а docling запускать только там, где он нужен (таблицы, графика, структура), —
**сохраняется ли качество** относительно текущего `layout_tables`?

**Вердикт: нет — в текущем виде.** Качество не сопоставимо, и безопасный вариант не окупается.
Оба вывода — измерения, а не оценки:

1. **Потери текста материальны.** На реальной книге корпуса (665 стр.) pdfium отдаёт на
   **11.5 %** меньше символов и теряет **6.7 % идентификаторов** docling-а. Идентификатор —
   это имя параметра/функции, то есть именно тот токен, который в карте становится
   доказательством. Потерянный идентификатор — потерянный факт о продукте.
   *Уточнение 02.11* (`2026-11-01-pdf-identifier-loss.md`): та же метрика разложена на живом
   PDF — 26 из 84 «потерь» были экранированием `_` в docling-markdown (наш артефакт), а
   остальные 58 — текст, нарисованный внутри схем и рисунков, который pdfium читает по
   текстовому слою. Вывод «pdfium теряет относительно docling» держится, но состав потери
   другой: это не разбор и не таблицы, а текст в изображениях.
2. **Дешёвого классификатора страниц не существует** на этом материале: чтобы гарантировать
   полноту (recall 1.0) по таблицам, помечать надо **90 %** страниц — тогда экономия ≤10 %.
   Любое правило, дающее реальную экономию, теряет таблицы (recall 0.958 при 38.5 %
   экономии).

Поэтому гибридный пайплайн **не реализован**: он либо теряет доказательства, либо не экономит.
Ниже — числа, скрипты и что именно проверялось, чтобы вердикт можно было оспорить.

---

## 1. Условия и материал

| параметр | значение |
|---|---|
| арбитр качества | docling `layout_tables` — то, что сегодня публикуется в карту |
| документы | 181 стр. (книга, 3 таблицы, 107 страниц с заголовками) и 665 стр. (книга, 48 таблиц, 328 страниц с заголовками) |
| источник docling-разбора | постраничный markdown/`tables`/`texts` из прогона `layout_tables` |
| сторона pdfium | `pypdfium2`: текстовый слой, символьные боксы, кегли, типы объектов |
| модели | **не запускались** для pdfium-стороны: весь смысл гибрида — не запускать их |

Скрипты и сырые данные (воспроизводимо, не в `/tmp`):

```
docs/reports/measurements/2026-10-28-hybrid-quality-gate/
  analyze.py          потери текста: символы, идентификаторы, числа, заголовки
  probe_detector.py   признаки по объектам pdfium (пути/изображения/боксы)
  char_detector.py    признаки по символьной геометрии (сетка таблицы, кегль заголовка)
  scan_corpus.py      доля корпуса, пригодная к pdfium без потери структуры
  pages-medium.jsonl, pages-large.jsonl           постраничные потери
  detector-medium.jsonl, detector-large.jsonl     объектные признаки
  char-medium.jsonl, char-large.jsonl             символьные признаки
  corpus-eligibility.jsonl                        скан корпуса по документам
```

## 2. Потеря текста при уходе страницы в pdfium

| документ | символов docling | символов pdfium | доля | идентификаторов потеряно | чисел потеряно |
|---|---:|---:|---:|---:|---:|
| 181 стр. | 188 657 | 185 877 | **98.5 %** | 0 из 28 (0 %) | 4 из 627 (0.64 %) |
| 665 стр. | 1 068 713 | 945 778 | **88.5 %** | **147 из 2 204 (6.67 %)** | 57 из 5 875 (0.97 %) |

Потери не размазаны: на 665-страничной книге **30 страниц** дают менее 50 % символов docling-а.
Это ровно страницы таблиц и рисунков — то есть там, где docling-модель делает работу, которую
текстовый слой не делает вовсе.

Замечание в пользу точности: pdfium местами находит **больше** идентификаторов, чем markdown
docling-а (2204 → 2662 в сумме), потому что markdown теряет часть служебного текста вёрстки.
Это не компенсирует потерю: сравнивать надо по множествам, и потерянные 147 идентификаторов
docling-а pdfium-ом не воспроизводятся.

## 3. Детектор «страница с таблицей»: три подхода, все провалились

Таблица — это то, что нельзя потерять. Значит детектор обязан иметь **recall 1.0**; precision
вторичен (лишняя страница в docling стоит только времени).

**3.1. Векторные пути (`FPDF_PAGEOBJ_PATH > 0`).** Идея «таблица нарисована линиями» на этом
материале ложна: таблицы свёрстаны **без линий**.

| документ | recall | помечено страниц | precision |
|---|---:|---:|---:|
| 181 стр. (3 таблицы) | **0.000** | 4 / 181 | 0.000 |
| 665 стр. (48 таблиц) | 1.000 | **663 / 665** | 0.072 |

То есть на малой книге признак не находит ни одной таблицы, а на большой помечает почти всё —
это не детектор, а константа.

**3.2. Объектная геометрия (число текстовых блоков, изображений, боксов).** `cols > 1`,
`grid_dense`, `cols >= 3`, `images > 0`: recall 0.000–1.000 при precision 0.017–0.075, то есть
признак либо не отличает ничего, либо помечает 638–663 страницы из 665. Причина механическая:
текстовый объект pdfium — это **абзац**, а не ячейка.

**3.3. Символьная геометрия (сетка по боксам символов).** Лучший из проверенных подходов:
строка с ≥3 прогонами, разделёнными разрывом ≥8 pt; таблица = ≥3 таких строки.

| правило | recall (48 таблиц) | помечено | precision | экономия страниц |
|---|---:|---:|---:|---:|
| `grid_rows >= 3` | 0.875 | 252 / 665 | 0.167 | 62 % |
| `grid_rows >= 6` | 0.729 | 135 / 665 | 0.259 | 80 % |
| `grid_rows >= 10` | 0.521 | 58 / 665 | 0.431 | 91 % |
| `cols >= 8` | 0.979 | 501 / 665 | 0.094 | 25 % |
| `cols >= 5` | **1.000** | **598 / 665** | 0.080 | **10 %** |
| `rows >= 1` | 0.958 | 409 / 665 | 0.112 | 38 % |

Строка `cols >= 5` — единственная с recall 1.000, и она помечает 90 % страниц: экономия
схлопывается. Правило, дающее экономию 38 %, теряет 2 таблицы из 48 — то есть текст.

## 4. Заголовки: потеря структурная, а не текстовая

pdfium иерархии не даёт вовсе — `heading_path` для таких страниц пуст, а именно он питает
метаданные чанка (markdown-чанкер) и, значит, контекст доказательства.

| документ | страниц с заголовками у docling | потеряли бы структуру |
|---|---:|---:|
| 181 стр. | 107 | **106** |
| 665 стр. | 328 | **328** (при уходе всех) |

Важное уточнение, которое делает вариант не безнадёжным: **кегль восстанавливает заголовки**
дешёво (символы крупнее `1.15 × body`, ≥80 % строки): recall **0.951** (312/328) и **0.944**
(101/107) при precision 0.510 и 0.732. То есть заголовочную разметку можно синтезировать на
стороне pdfium — но recall 0.95 значит, что 5 % заголовков исчезнут молча.

## 5. Почему вердикт «не проходит», а не «доработать детектор»

Свести вместе три измеренных факта:

- потеря 6.7 % идентификаторов — это **утрата доказательств**, а не косметика: I22 требует
  непустую цитату, а цитата без имени параметра бесполезна;
- чтобы не терять, детектор обязан иметь recall 1.0 по таблицам, а единственное такое правило
  помечает 90 % страниц → экономия ≤10 % времени извлечения;
- при этом сама экстракция уже ускорена **8–12×** объявленным устройством GPU
  (`2026-10-28-gpu-vs-cpu-extraction.md`): на финальной когорте (~32 000 страниц)
  `layout_tables` на GPU — **63.5 мин**. Гибрид с экономией 10 % сберегает ~6 минут ценой
  риска потерять каждое пятнадцатое имя параметра.

Менять измеримость карты на 10 % времени — не та сделка. **Гибрид в текущем виде не
реализуется** — но не выбрасывается: материалы, скрипты и детекторы сохранены в этом каталоге
как основа для дальнейших экспериментов (решение владельца, 2026-10-28). Условие пересмотра
названо в §6: размеченные страницы для честного recall детектора либо модель-классификатор,
дающая recall 1.0 при реальной экономии.

## 6. Что осталось бы честным вариантом (если гибрид всё же нужен)

Не «сделать детектор получше», а изменить единицу решения и источник доказательства:

1. **Документный гибрид по кэшу.** `extract_cache` уже знает для каждого документа, были ли в
   нём таблицы и заголовки. Документ, у которого в прошлом разборе их **не было**, доказуемо
   эквивалентен pdfium-у (обоими путями получается плоский текст). Это безопасно по
   построению и не требует классификатора — но работает только на повторных прогонах, а
   первый прогон по новому пакету всё равно идёт docling-ом.
2. **Модель-классификатор страниц** (рендер + крошечная CNN). Только она может дать recall
   1.0 при реальной экономии — но это новая инфраструктура и свой гейт: её recall надо
   измерять отдельно и на размеченных страницах, которых сейчас нет.
3. **Уровень `text_layer` остаётся тем, чем он и был** — объявленным механизмом для корпусов,
   где структура не нужна (спецификации, CHANGELOG, plain text), с честной потерей 11.5 %
   символов, названной в отчёте прогона.

## 7. Ограничения этого замера

- Два документа — книги. Технические PDF (мануалы с колонтитулами и таблицами параметров) могут
  вести себя иначе; выборка по корпусу ниже даёт представление о доле, но не о качестве.
- Арбитр — docling. Если docling сам теряет текст (что он делает, см. §2 про 2204 → 2662), то
  «потеря» относительно него — верхняя оценка. Абсолютной истины здесь нет ни у одной стороны,
  поэтому вывод сформулирован как «pdfium-путь теряет идентификаторы, которые docling нашёл», а
  не «pdfium хуже вообще».
- Кеглевый детектор заголовков проверялся как признак, а не как готовый генератор разметки:
  качество синтезированной иерархии (`##` vs `###`) не измерялось.
- Детектор таблиц проверен на 48 настоящих таблицах — это мало для утверждений о других
  корпусах, но достаточно, чтобы не строить на нём пайплайн.

## 8. Доля корпуса, пригодная к pdfium без потери структуры

Скан корпуса `postgrespro` (единица — **документ**: `family` и `heading_path` живут на
документе, а не на странице), 240 документов / **15 929 страниц**. Документ пригоден, если
**ни одна** его страница не помечена консервативным правилом (`cols >= 5` или есть
строка-заголовок):

| величина | значение |
|---|---:|
| документов / страниц в скане | 240 / 15 929 |
| страниц с признаком заголовка | **14 295 (89.7 %)** |
| страниц рискованных (таблица **или** заголовок) | 15 304 (96.1 %) |
| страниц рискованных **не** из-за заголовка (верхняя оценка таблиц) | 1 009 (**6.3 %**) |
| документов, пригодных целиком (ни одной рискованной страницы) | **0 (0 %)** |
| документов, где все рискованные страницы — заголовочные (верхняя оценка пригодности) | 81 (33.8 %) |
| их страниц | 1 725 (**10.8 %**) |

Читается так: **заголовков в этом корпусе почти столько же, сколько страниц** (89.7 %). Это
технические книги и документация — там, где у продукта есть структура, и ровно её pdfium
отдаёт плоским текстом. Поэтому документного «безопасного подмножества» в корпусе фактически
нет: ноль документов проходят критерий «ни таблиц, ни заголовков», а верхняя оценка с
реконструкцией заголовков по кеглю — 10.8 % страниц.

Экономия 10.8 % страниц при 50-кратной разнице на страницу — это ~10 % времени извлечения
документов, то есть меньше, чем уже дал GPU объявленным устройством.
