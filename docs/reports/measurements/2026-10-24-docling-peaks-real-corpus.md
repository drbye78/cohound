# Замер: пик docling `layout_tables` на документах реального корпуса (F1)

**Дата:** 2026-10-24
**Срез дерева:** `a596798`
**Хост:** 6.9 GiB RAM, Python 3.14.0, `docling-slim` 2.135.0, `PDF_QUEUE_MAX_SIZE = 1`
**Скрипт:** `/tmp/opencode/peak-real/measure.py` (один документ — один процесс; `ru_maxrss`)

## Зачем

`workers_from_budget` делит бюджет на `DOCLING_PEAK_MB[level]`. В коде стоит
`layout_tables = 1953` — из замера `2026-10-23` на **одном** документе ≈1 MB / ~30 страниц.
`run.yaml` пакета обосновывает **два** воркера другим числом (2126 MB на 665-страничном PDF).
Два числа на один вопрос означают, что формула и ручная ось опираются на разные популяции, и
проверить, какой верить, было нельзя.

Вопрос: каков пик на **реальных** документах корпуса и предсказуем ли он по размеру файла
или числу страниц (то есть годится ли одна константа на уровень).

## Как

`DoclingDocumentExtractor(DocumentLevel("layout_tables")).extract_bytes(bytes, "probe.pdf")` в
отдельном процессе; пик — `resource.getrusage(RUSAGE_SELF).ru_maxrss`. Сторож опрашивает
`MemAvailable` каждые 0.5 s. Документы — рететенрованные артефакты `corpus_raw/postgrespro/`
(не синтетика). Четвёртый замер шёл под `systemd-run --user --scope -p MemoryMax=4G
-p MemorySwapMax=0`, чтобы OOM не задел хост.

## Результат

| документ | страниц | файл, MB | пик RSS, MB | символов | время, с | исход |
|---|---:|---:|---:|---:|---:|---|
| `745d7c1d…` документация Postgres Pro Enterprise 9.6.24.1 | **2763** | 14.5 | **3679** | 0 | 2784 | `parser_failed`: таймаут 2700 s |
| то же, `document_timeout = 5400 s` | 2763 | 14.5 | ≥2700 (cgroup) | — | остановлен на 3420 | не завершился |
| `746c23f4…` | 665 | 7.3 | **2131** | 1 067 915 | 1166 | ok |
| `d7e74768…` | 191 | 12.9 | 1582 | 200 803 | 288 | ok |
| `ec3721ec…` | 36 | 17.9 | 1888 | 39 376 | 65 | ok |

Константа в коде — 1953 MB. На реальном корпусе — **1582 / 1888 / 2131 / 3679**.

## Что из этого следует

1. **Константа занижает пик, и занижает сильно.** Максимум наблюдённого — 3679 MB, на 88 %
   выше 1953. Занижение пика даёт лишнего воркера, то есть OOM-kill, а не «медленнее»:
   ошибка в опасную сторону.

2. **«`full` дороже `layout_tables`» — неверно как утверждение о пике.** Замер `2026-10-23`
   дал `full` 3107 против `layout_tables` 1953 на **одном и том же** 30-страничном документе.
   На 2763 страницах `layout_tables` берёт 3679 — больше, чем константа `full`. Значит пик
   определяется **документом**, а уровень задаёт лишь множитель; константа «на уровень» —
   максимум по популяции, а не свойство уровня.

3. **Число страниц и размер файла — не предикторы.** 36 страниц дали 1888 MB, 191 — 1582,
   то есть **меньше**, чем у документа в шесть раз короче; 17.9 MB дали 1888, 7.3 MB — 2131.
   Монотонной связи нет. Поэтому «оценка по размеру входа до экстракции» (напрашивающееся
   решение) не работает: остаётся максимум по корпусу.

4. **Крупнейший документ корпуса не извлекается никогда.** `document_timeout` для
   `layout_tables` — 2700 s (`core/adapters/extract_document.py:444`), документ израсходовал
   2784 s. Это не тихая потеря: docling вернул `PARTIAL_SUCCESS`, адаптер отдал
   `ExtractedDoc.error`, фаза пометила `parser_failed` — то есть дефекта в проводке нет,
   **проверено** (воспроизведение с `document_timeout=5 s` даёт тот же `PARTIAL_SUCCESS`).
   Второй прогон с `document_timeout = 5400 s` остановлен на 3420 s без завершения
   (cgroup показал 2.7 GB, оценка по 665-страничному — ~1.75 s/стр., то есть ~4800 s на
   весь документ). Значит подъём таймаута — не гарантия, а ставка: чтобы документ прошёл,
   его надо поднимать примерно вдвое, и тогда один документ занимает **~80 минут**
   единственного воркера.
   Последствие методологическое: origin с блокирующим `parser_failed` делает
   `coverage.complete = False`, поэтому `❌` по продукту требует аттестации (I2c).

5. **`MemAvailable` падал до 1092 MB при одном воркере** на 665-страничном документе
   (соседи: редактор, MCP-прокси, демон поиска). `MEM_RESERVE_MB = 512` вычитается из бюджета
   **на старте** и не является запасом на весь прогон: реальный остаток был вдвое меньше
   резерва. Это аргумент за изоляцию прогона cgroup-ом (F1/R8), а не за больший резерв.

## Что это меняет в коде

- `DOCLING_PEAK_MB[layout_tables]` → **3679** (максимум по измеренной популяции, а не
  «типичное»). Направление ошибки выбрано сознательно: занижение даёт OOM, завышение — на
  одного воркера меньше, то есть медленнее, но живой прогон.
- Следствие для `ru-pg-dbms`: при бюджете `MemAvailable − 512` один воркер требует
  `500 + 3679 = 4179 MB`, то есть `MemAvailable ≥ 4691 MB`. При меньшем — preflight откажет
  `EXIT_USAGE` с числами, а не упадёт OOM-killer'ом. Это и есть цель F1.
- `crawl.extract_workers` из `run.yaml` пакета убирается: пусть решает формула. Ось не входит
  в `CrawlLimits.as_dict` (проверено AST: имя встречается только в докстринге `as_dict`, в
  `payload` его нет), поэтому `run_id` не сдвигается.

## Открытый дефект, найденный замером

`document_timeout` (`core/adapters/extract_document.py:444`) — константа по уровню, которая
**меняет состав корпуса**: с таймаутом 2700 s документ на 2763 страницы попадает в
`parser_failed`, с 5400 s — возможно, в корпус. Проверено AST: `document_timeout` не
встречается ни в `digests.py`, ни в `crawl_frontier.py`, то есть в
`execution_contract_digest` его нет. Значит два прогона с разными таймаутами получат один
`run_id`, хотя корпус у них разный — ровно та ошибка, которую §13 запрещает для осей
краула. Таймаут обязан стать осью контракта (`CrawlLimits`/`crawl_config_digest`), а не
константой в адаптере.

## Воспроизводимость

Документы — рететенрованные артефакты `corpus_raw/postgrespro/` (в `.gitignore`,
воспроизводятся краулом). Скрипт замера в репозиторий не кладётся: он одноразовый и не
является частью продукта; пересъёмка воспроизводится по разделу «Как».

Ограничение применимости: пик снят на **одном** документе за процесс при
`PDF_QUEUE_MAX_SIZE = 1`. Воркер, обрабатывающий 25 документов до рециклинга
(`extract_max_tasks_per_child`), держит арены glibc — `ru_maxrss` там только растёт, а
`malloc_trim` возвращает часть ОС. То есть 3679 MB — пик **документа**, не пик воркера
за 25 документов; для последнего нужен отдельный замер по стоку `{runs}/{run_id}/workers/{pid}.rss`.
