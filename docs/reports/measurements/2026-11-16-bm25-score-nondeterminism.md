# Балл BM25 не воспроизводился между прогонами: причина, цена, исправление (план 26, O41)

**Дата:** 16.11.2026. **Дерево:** `e3e7485` + правка адаптера этого замера.
**Корпус:** прогон `ru-pg-dbms-145ad66ca3f9`, **253 306** чанков, 0.33 GiB текста,
сборка `cb_5c090025af68b95615c87869`. **Прибор:**
`scripts/check_bm25_determinism.py` (два независимых процесса + сравнение отпечатков).

## 1. Дефект

Найден при замере O14: два прогона одного и того же прибора на одном и том же корпусе дали
**разную выдачу**. Не «шум в последнем знаке»: `prompt_hash` ячейки считается по
`chunk_ids`, поэтому два прогона с одним `run_id` отдавали оценщику **разные чанки** при
неизменных объявленных входах.

```
python scripts/check_bm25_determinism.py --db …/cohound.db \
  --golden packages/ru-pg-dbms/sources/retrieval_golden_docs.json --cells 40 --out a.json
# … то же во втором процессе …
python scripts/check_bm25_determinism.py --compare a.json b.json
```

```
сравнение: ячеек 40; иной состав 3, иной порядок 5, иные баллы 12; max |Δ балла| = 3.815e-06
сегментов: 16 против 24; сборка 13.6 с против 13.34 с
```

## 2. Причина

`tantivy.Index.writer()` по умолчанию вызывается с `num_threads=0` — «взять с хоста». При
параллельной записи корпус режется на сегменты по бюджету памяти writer'а, и **раскладка
зависит от расписания**: на одном и том же входе замерено **14, 15, 16, 20, 22, 23, 24**
сегмента в разных процессах. Балл BM25 агрегируется по сегментам, поэтому он расходится в
последних битах: типично **1.9e-06**, максимум **7.6e-06** (fp32).

Зависит именно **раскладка**, а не только число сегментов: в контрольном режиме
(`--mode threads`, бюджет объявлен, потоки — с хоста) два процесса дали по **8** сегментов,
но выдача всё равно разошлась — 1 ячейка из 40 сменила состав, 2 порядок, 4 баллы,
max `|Δ| = 1.9e-06`. Значит границы сегментов (какие документы куда попали) тоже решает
расписание, и «сравнять число сегментов» дефект не лечит.

`_deterministic_hits` от этого не защищает и не должен: он держит **равные** баллы на
границе `top_k` внутри окна, а здесь баллы не равны — они отличаются на 1–4 ULP, и порядок
документов внутри выдачи меняется.

## 3. Что исправлено

`core/adapters/lexical_tantivy.py`: `WRITER_THREADS = 1` — writer объявляет число потоков
явно (`index.writer(num_threads=WRITER_THREADS)`), бюджет памяти не менялся (дефолт 128 MB).

```
# после правки, режим default (никаких подмен)
режим default: документов 253306, сегментов 2, сборка 29.6 с
режим default: документов 253306, сегментов 2, сборка 29.62 с
сравнение: ячеек 40; иной состав 0, иной порядок 0, иные баллы 0; max |Δ балла| = 0.000e+00
```

**Цена:** сборка индекса **13.6 → 29.6 с** на 253 306 чанках (×2.18). Пик RSS не вырос
(замер по `ru_maxrss`: 251 MB при параллельной записи против 239 MB при одном потоке).
Бюджет памяти writer'а менять не понадобилось: с одним потоком дефолтных 128 MB хватает —
проверено и на 256, и на 1024 MB, отпечаток тот же побайтово.

**Что не изменилось:** состав top-K на 40 ячейках — **0** различий против прежней сборки,
порядок — **0** различий; расходятся только значения баллов (≤3.8e-06), а в `prompt_hash`
они не входят. На полном эталоне (132 ячейки) метрики те же: R0 0.258 hit@10, R1 0.152,
R2 0.212.

**Что стало стабильным:** `MRR` профиля R0 — **0.121** во всех трёх прогонах после правки
(до правки: 0.1198…0.1237 на пяти прогонах при неизменном `hit@10`).

## 4. Почему не «допуск на балл»

Второй кандидат — упорядочивать с допуском `ε` на балл. Он **не проверен до конца и не
нужен**: `ε` пришлось бы брать ≥ 7.7e-06 (измеренный максимум расхождения), а такой допуск
склеивает баллы, которые различают документы, — то есть меняет ранжирование там, где оно
было верным. Моделирование на опубликованных top-10 двух прогонов показало, что допуск
любой величины (2e-06…1e-04) не устраняет расхождение **состава** на тех же двух ячейках:
конкурент за 10-е место в одном прогоне вообще не входит в выдачу другого, и никакое
правило, читающее только баллы выдачи, его не восстановит. Один поток устраняет причину, а
не следствие.

## 4.1 Приёмка в тестах

Механизм закреплён двумя тестами `tests/adapters/test_lexical_tantivy.py`:

- `test_writer_threads_are_declared` — `index()` передаёт writer'у ровно
  `WRITER_THREADS` (перехват `_open_index`; ловит регресс «кто-то вернул `num_threads=0`»);
- `test_two_builds_give_the_same_scores` — две независимые сборки одного корпуса дают
  побайтово одинаковые баллы (на 200 чанках: проверяет механизм, не цену).

Цена на большом корпусе и контр-опыт с потоками хоста — только прибором: тест на 253 306
чанках стоил бы ~30 с и 240 MB в общем прогоне ради того, что уже измерено здесь.

## 5. Чего замер не показывает

- **Другие корпусы.** Число сегментов зависит от объёма текста: на 0.33 GiB при одном
  потоке вышло **2** сегмента. Раскладка детерминирована (функция входа и бюджета), но её
  число на корпусах иного размера здесь не измерено — при объявлении нового профиля это
  надо перемерить тем же прибором.
- **`split`.** Замер сделан на `local`; шов строит свои порты, и его лексическое плечо этим
  прибором не проверялось.
- **Влияние на вердикты.** Расхождение баллов ≤3.8e-06 на этом корпусе не сдвинуло ни одной
  метрики эталона; утверждение «вердикты не менялись» здесь **не измерено** (для этого
  нужен повторный прогон оценки, а не прибор ретривала).

## 6. Воспроизведение

```bash
DB=~/.cohound/stands/ru-pg-dbms/runs/ru-pg-dbms-145ad66ca3f9/cohound.db
G=packages/ru-pg-dbms/sources/retrieval_golden_docs.json
python scripts/check_bm25_determinism.py --db $DB --golden $G --cells 40 --out a.json
python scripts/check_bm25_determinism.py --db $DB --golden $G --cells 40 --out b.json
python scripts/check_bm25_determinism.py --compare a.json b.json   # exit 0 — детерминизм

# контр-опыт: воспроизвести дефект (writer с потоками хоста)
python scripts/check_bm25_determinism.py --db $DB --golden $G --cells 40 --mode threads \
  --out c.json
python scripts/check_bm25_determinism.py --db $DB --golden $G --cells 40 --mode threads \
  --out d.json
python scripts/check_bm25_determinism.py --compare c.json d.json   # exit 1 — дефект виден
```

Контр-опыт 16.11.2026 после правки: `c.json` и `d.json` — по **8** сегментов, но
`иной состав 1, иной порядок 2, иные баллы 4; max |Δ балла| = 1.907e-06` ⇒ дефект
воспроизводим, а исправление измерено тем же прибором, что и он.

`--mode threads` — это **контр-опыт**, а не рабочий режим: он возвращает writer'у
`num_threads=0` и существует ровно для того, чтобы дефект оставался воспроизводимым после
исправления (иначе «до» проверить нечем).
