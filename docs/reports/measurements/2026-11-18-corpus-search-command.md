# `hound search`: разведка по корпусу прогона — цена и что она даёт

**Дата:** 2026-11-18 · **Команда:** `hound search` (`core/cli/commands/search.py`) ·
**Чтение корпуса:** `core/store/corpus_reader.py` · **Слияние и ответ:**
`core/pipeline/corpus_search.py` · **Корпус:** `ru-pg-dbms-145ad66ca3f9`
(5 продуктов, 253 306 чанков, сборка `cb_5c090025af68b95615c87869`).

## 1. Зачем это понадобилось

Разбор ложных `present` в `hound baseline recon` (план 27 §16.2.1) требовал ответа на
вопрос «что вообще есть в корпусе по этому понятию». До команды такой ответ добывался
одноразовыми скриптами поверх `corpus_chunks` — то есть **мимо** продукта: другой
токенизатор, другое слияние запросов, никакого провенанса. Это тот же класс дефекта, что
и каталог, собранный генератором: результат есть, а описать, чем он получен, нельзя.

Команда — **композиция** уже существующих частей, а не новая подсистема: `retrieve()`
(профили R0/R1/R2, I16/I17), `render_queries` (те же запросы, что у Ш6),
`build_retrieval_ports` (новый, см. §4), порт `discovery_llm` для ответа.

## 2. Граница с оценщиком — по типу, а не по соглашению

| | оценщик (Ш6) | `hound search` |
|---|---|---|
| вход | параметр каталога | свободный текст либо `--param` |
| что делает | запросы → чанки → LLM | запросы → чанки (→ LLM при `--answer`) |
| выход | **вердикт** ✅/⚠️/❌ + цитата | **материал**: чанки с адресами |
| роль | evidence (I1/I22) | разведка: не пишется никуда |
| модель | объявленный вход (I21) | операционная настройка (§7.4) |

Ответ LLM идёт через `DiscoveryLLMPort`, а не `EvaluatorPort`: у `SearchAnswer` нет ни
`status`, ни `citation_quote`, поэтому его нельзя передать туда, где ждут
`LLMCellOutput` — тест `test_search_answer_is_not_a_verdict` держит именно это.

## 3. Цена — измерена, по стадиям

`scripts`-проба на этом хосте (БП, `bge-m3@5617a9f6`, fp16), 253 306 чанков:

| стадия | R0 (лексика) | R2 (гибрид) |
|---|---|---|
| открытие читателя + строка прогона | 0.00 с | 0.00 с |
| `partitions` + `COUNT(*)` по 5 партициям | 0.01 с | 0.01 с |
| плечи: засев tantivy из чанков сборки | **29.60 с** | 31.33 с (то же + dense-индекс) |
| загрузка весов `bge-m3` | — | внутри 31.33 с |
| вектор запроса | — | **8.46 с** (dim 1024, первый вызов) |
| сам поиск | 0.00 с | 0.19 с |
| **итого на вызов** | **29.6 с** | **40.0 с** |
| `--answer` (LLM по 4 фрагментам) | +6.1 с | — |

Три вывода, которые важны для решения:

1. **Платится не поиск, а засев индекса.** Сам `retrieve` — единицы миллисекунд;
   29.6 с — это `TantivyLexicalIndex.index()` по 253 тыс. чанков, и он **не
   персистится** (решение C8: источник чанков уже персистентен, персист потребовал бы
   версии схемы и миграции при смене профиля/движка). Интерактивной эта команда станет
   либо на корпусе версии (1–2 тыс. страниц — секунды), либо после материализации
   индекса, триггер для которой назван в плане 27 §12.
2. **Лексический профиль не грузит веса.** `dense=False` в `build_retrieval_ports` —
   не оптимизация «по вкусу»: `bge-m3` стоит секунды и гигабайты RSS, и включать её в
   цену R0 значило бы назвать цену R0 неправдой.
3. **Модель запроса обязана совпасть с моделью корпуса.** Сверяется **имя** модели:
   `embedder.model_id` несёт пин ревизии (`model_id@sha`), а `runs.embed_model_id` —
   наблюдаемая строка без ревизии. Ревизию по манифесту не сверить, и первая редакция
   проверки отвергала исправный прогон на ровном месте (`BAAI/bge-m3` против
   `BAAI/bge-m3@5617a9f6…`) — измерено на первом же запуске R2.

## 4. Что пришлось изменить в коде, и почему это не «поблажка»

**`core/store/corpus_reader.py` — чтение корпуса прогона с чужой `schema_version`.**
Все 9 run-DB стенда объявляют `3.20.0`, код ждёт `3.26.0`; гейт `SchemaVersionMismatch`
отвергает их целиком, и правильно делает — иначе «догнанный» файл неотличим от
настоящего. Решение владельца 18.11.2026: разрешить **узкий** читатель. Что он делает и
чего не делает:

- читает `runs` (одна строка), `corpus_chunks`, `index_manifest`;
- **не** читает `cells`/`cell_evidence`/`corpus_coverage` — вердиктов и охвата здесь нет
  по построению, поэтому «подтвердить» что-либо командой невозможно;
- **не** пишет: `mode=ro`, ни DDL, ни миграций, ни `-wal`; тест сравнивает sha256 файла
  до и после;
- отсутствующие в чужой схеме колонки читаются как «неизвестно», а не как ноль:
  `table_ref`/`char_start`/`char_end` → `None` (ноль — валидное начало первого куска);
- гейт по умолчанию **включён**: без `--allow-legacy-schema` файл чужой версии
  отвергается с кодом `schema` (exit 2), и сообщение называет флаг.

**`build_retrieval_ports` в `core/cli/wiring.py`** — сборка только плеч ретривала.
`build_adapters` строит ещё композит экстрактора (docling), чанкер, краулеры и
реестровые фетчеры; чтению корпуса это не нужно и стоит секунд и памяти. Оси берутся из
того же места, что у прогона (`resolve_embed_spec`/`resolve_embed_precision`/
`lexical.profile`), поэтому «какой моделью посчитан вектор запроса» — объявленный вход,
а не догадка о составе extras (O6). Заодно `seed_lexical_index` принимает
`_ChunkSource` (три метода) вместо `StorePort`: читатель корпуса — тот же вход по
смыслу, и приведение типа тут не нужно.

## 5. Что команда уже дала на двух спорных параметрах

Разметка каталога оставила два параметра с `confidence=low`; корпус ответил по-разному,
и это ровно та разница, которую нельзя было увидеть из сравнительной таблицы.

**№119 «Pluggable TOAST» — postgrespro: ✅, дословно.** `docs/enterprise/18/storage-toast`
§68.2.3 «Подключаемый механизм TOAST»: «…предоставляет открытый API, позволяющий
разрабатывать и использовать собственные реализации TOAST для столбцов таблиц и типов
данных…», плюс полный набор `add_toaster`/`set_toaster`/`reset_toaster`/`drop_toaster`,
`CREATE EXTENSION toastapi; CREATE EXTENSION bytea_toaster`. У tantor — **0 чанков**.
Значит по природе утверждения это `distribution_absence`, и без `scope_acceptance` `❌`
не публикуется — именно тот случай, ради которого класс и переставлялся.

**№46 «Append Only Storage» — tantor: ✅, а таблица ставит ⚠️.** `hydra.html` §F.25.7:
«Таблицы Hydra Columnar поддерживают обновления и удаления, но остаются хранилищем данных
append-only (только для добавления данных)… Изменённые данные переписываются в конец
таблицы». Плюс `tantorlabs.ru/products/dbms`: «колоночный метод хранения данных,
оптимизированный для работы с **append-only** данными».

**postgrespro по №46 — ⚠️:** в поставке есть `citus` с колоночным хранилищем, но фразы
«append-only» в корпусе **ноль** попаданий, а `citus_columnar` поддерживает UPDATE/DELETE.
Это и есть «append-only реализован внешним расширением/движком» — ⚠️, а не ✅.

Заодно видно, **почему recon ошибался**: запрос «append only storage» первым делом
приносит `storage-toast` postgrespro с кодом `CREATE TABLE test_bytea_append` — совпадение
по слову, не по предмету. `--explain` показывает это в одну строку (`← 1, 3`: фрагмент
вернули заголовок и термин `append`).

## 7. Границы, которые надо назвать

- **Это не evidence и не может им стать.** В корпусе может быть фрагмент, «подтверждающий»
  параметр, но вердикт ставит оценщик по правилу каталога и с цитатой (I1/I22); поиск
  показывает материал, из которого человек делает вывод.
- **Один прогон — один корпус.** Продукт-скоуп (I17) держится: `--product` сужает, но не
  расширяет; продукты вне сборки — отказ с перечнем существующих.
- **Пустая выдача — валидный результат.** «В корпусе такого нет» — факт о корпусе, а не
  ошибка команды; именно так выглядит честное «не нашли».
- **Профиль — ось выдачи, а не объявление прогона.** Дефолт `R0` выбран потому, что он не
  грузит весов; `R2` требует объявленной модели и даёт +8.5 с на вектор запроса.
- **Цена 29.6 с — цена этого корпуса на этом хосте**, а не свойство команды: она почти
  целиком приходится на засев индекса, который на корпусе версии (1–2 тыс. страниц) —
  секунды.
