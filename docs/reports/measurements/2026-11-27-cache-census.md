
6.2 с, dry-run (`--apply` не передавался), результат: `corpus_raw_unreferenced`
**69 424 файла / 13 153 643 824 байт (12.25 GiB)**, `live_paths` 33 721,
`uncovered_state_dbs: []`, `http_cache_*` — 0 по всем классам (кэш внешних вызовов
полностью объяснён).

**Почему объединение по двум БД, а не по одной.** Один каталог `corpus_raw` делят канонная
БД (`~/.cohound/data/state/ru-pg-dbms/state.db`, 8 738 версий) и БД стенда (43 825 версий);
пересечение живых путей — 3 283. Прогон по одной стендовой БД давал 74 879 кандидатов, из
которых 5 455 файлов / 1.09 GB нужны канонной. Отсюда `--state-db` повторяемый, а живое
множество — **объединение**: одна БД на общий корень означала бы удаление чужого корпуса.

## Что из этого следует для бюджета `extract_cache`

Объявленный потолок (`config/deploy.yaml:extract.cache_max_bytes`) выведен из замера, а не
выбран: 2 GiB = 4× рабочего набора самого крупного продукта. Рабочий набор оценён сверху:
`postgrespro` объявляет 800+3 000+150+200+500 = **4 650** документов, p99 записи кэша
0.1 MB ⇒ ≈0.47 GB. Цена промаха измерена отдельно
(`2026-11-23-work-class-cost.md`): `model_free` 49.5 мс/док, docling text 0.030 с/стр, то
есть полное пере-извлечение профиля ≈ 23 мин — бюджет покупает именно эти минуты.

Сегодня 1.04 GiB < 2 GiB ⇒ вытеснение не срабатывает ни разу. Это **граница роста**, а не
уборка: `mtime` не обновляется попаданием в кэш, поэтому LRU по `mtime` — «последняя
запись», а не «последнее использование». Возврат мёртвых записей — по живучести (нет ссылки
из версий), и это `scripts/prune_orphans.py`, а не бюджет.

## Границы

- **`--apply` не запускался**: удаление 12.25 GiB необратимо и не является частью этой
  переписи. Число — приглашение к решению, а не разрешение.
- Разбивка `extract_cache` на живое/мёртвое в этой переписи **не** пере-мерялась: связка
  «запись кэша ↔ версия документа» идёт через `document_version.raw_path`, а не через ключ
  кэша, и требует отдельного прохода. Здесь измерены только объём и число файлов.
- Один снимок подложки. Подложка пишется живым прогоном, поэтому `live_paths` между
  запусками сдвигается (в замере 23.11 два запуска с разницей 3 минуты дали 94 и 113
  промахов на `pangolin`).
