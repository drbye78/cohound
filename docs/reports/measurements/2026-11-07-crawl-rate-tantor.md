# Допустимый темп обхода `docs.tantorlabs.ru` (замер, 07.11.2026)

Вопрос владельца (07.11.2026): «вполне вероятно, что текущие лимиты — и верхний и нижний —
завышены». Замер отвечает числом: **при `rate_limit {min_s: 0.2, max_s: 0.5}` хост не отбил
ни одного запроса** (0 из 250 — ни `429`, ни `5xx`, ни повтора), достигнутый темп **1.57
запросов/с** против **0.32** у текущего объявленного `{1.0, 5.0}` — то есть текущий лимит
осторожен примерно **в 4.9 раза**, и осторожность эта не оплачена ничем: время ответа сервера
на всех трёх панелях совпало в пределах 3 мс (0.2 %).

- **Дата:** 07.11.2026 (окно UTC 06.11 22:38–23:02).
- **Срез дерева:** рабочая копия на 07.11.2026, коммита нет (в этой пробе git-команды
  запрещены, поэтому срез описан так, а не хешем).
- **Хост:** `docs.tantorlabs.ru` (один хост, `fetch: http`, браузер не участвовал).
- **Режим:** `hound crawl run --crawl-only --from-scratch` — frontier + фетч + retention;
  извлечения не было (документы легли в `extract_queue`), поэтому замер чистый: сеть, без
  docling. Это ответ на вопрос «с какой скоростью хост отдаёт», а не «сколько стоит корпус».

## 1. Стенд и что именно не тронуто

`COHOUND_HOME`/`COHOUND_PATHS_FILE` — на изолированный каталог
`~/.cohound/stands/crawl-pace` (свои `runs/`, `state/`, `index_store/`), пакет — **копия**
`packages/ru-pg-dbms` → `$D/packages/probe`. `corpus_raw`/`extract_cache`/`embed_cache`
смотрят на канонические каталоги намеренно: они append-only и content-addressed, повторная
запись тех же байтов ничего не портит. `packages/ru-pg-dbms/**`, `config/deploy.yaml` и
`passports/` не менялись; scope не расширялся (единственный хост в `--urls`).

Правки в копии пакета — только две оси, обе объявленные:
`run.yaml:crawl.rate_limit`, `run.yaml:crawl.max_documents` и
`domain_profiles.yaml:docs.tantorlabs.ru.max_documents` (per-site бюджет сильнее run-level, без
правки профиля панель вышла бы за 800 документов).

## 2. Сид: корень `/` больше не годится, взят `/tdb/`

Замерено 06.11.2026:

```
$ curl -sSI https://docs.tantorlabs.ru/ | head -5
HTTP/1.1 301 Moved Permanently
Server: nginx/1.24.0 (Ubuntu)
Location: https://tantorlabs.ru/docs/
```

Корень объявленного корпуса (`sources/corpus_urls.yaml:tantor: https://docs.tantorlabs.ru/`)
отдаёт 301 **на другой хост** — маркетинговую страницу `tantorlabs.ru/docs/`. При
объявленном профиле этого хоста (`max_depth: 8` ⇒ `enforce_redirect_scope=True`,
`corpus_ingest.py:2869`) такой сид получил бы `redirect_out_of_scope` и **ноль** документов:
обходить было бы нечего. Проверять это живым краулом я не стал намеренно — переход по
`Location` увёл бы запрос на `tantorlabs.ru`, то есть **за объявленный scope**; это
следствие кода, а не второй замер.

Поэтому все три панели стартовали с `https://docs.tantorlabs.ru/tdb/` — тот же хост,
`root_path_prefix=/tdb`, живой (301 уже внутри хоста → `…/18_6/se/differences.html`,
страница 200). Порядок обхода детерминирован (куча `(depth,url)`), поэтому панели брали
**один и тот же** список URL — проверено сравнением множеств `url` из
`crawl_session_items`: наборы B и C **совпали полностью** (250 = 250, разность пуста), и оба
являются подмножеством 300 адресов панели A. Различие между панелями — только объявленный
лимит, то есть сравнение честное.

## 3. Протокол и бюджет

| панель | `crawl.rate_limit` | документов | панель `max_documents` |
|---|---|---:|---:|
| A | `{min_s: 1.0, max_s: 5.0}` (текущее) | 300 | 300 |
| B | `{min_s: 0.5, max_s: 1.0}` | 250 | 250 |

Объявленные лимиты подтверждены провенансом сеанса
(`crawl_sessions.provenance_json:effective_limits.roots[0].rate_limits`), а не только файлом:
A `{min_s:1.0, max_s:5.0}`, B `{0.5,1.0}`, C `{0.2,0.5}`.

Бюджет пробы — 800 документов, израсходован ровно: 300 + 250 + 250. Сверх этого — **91
повторный фетч** тех же адресов после падения первой попытки панели A (см. §7.2), то есть
891 сетевой запрос на 800 различных документов (первые 91 из них — до сброса сеанса: они
видны в логе первой попытки и в срезе БД, снятом до `--from-scratch`, поэтому по ним цифры
приведены отдельно, а не как артефакт панели). Все три сеанса завершились усечением по
`max_documents`, а не исчерпанием фронта (`crawl_sessions.status = partial`,
`provenance_json:truncated = true`, `truncated_products = ["tantor"]`, в фазе —
«краул усечён политикой (max_documents); страниц=300/250/250»), — окно измерения полное, а
не оборванное.

**Стоп-правило ни разу не сработало:** отказов (`429`/`503`/любой `5xx`) — **0 из 891**
запроса. `404`/`410` — тоже **0**: все добытые адреса отвечали `200 text/html`, то есть
`4xx` не подмешивались к оценке.

## 5. Вывод о лимите

**Рекомендация: `crawl.rate_limit {min_s: 0.2, max_s: 0.5}` для `docs.tantorlabs.ru`.**

Основание — три факта из §4, а не «стало быстро»:

1. **Отказов нет:** 0 из 250 запросов при 1.57 запроса/с (и 0 из 891 за всю пробу).
   Стоп-правило (5 % `429`/`5xx`) не приблизилось даже к порогу.
2. **Сервер не деградировал:** собственное время ответа хоста ≈100 мс — и на 1.57, и на
   2.47 запроса/с (p50 104 мс на пути `http` в том же pipeline, §4), при неизменной структуре
   интервалов. Перегрузка выражается в росте латентности задолго до 429; роста нет. Строка
   `fetch_ms` панелей (1331 → 1328 мс) этого не доказывает — в ней 93 % наших задержек (§7.5).
3. **Вежливость соблюдена:** `observed_min_interval_s` = 0.201 при объявленных 0.2
   (`share_below_declared_pct` = 0.0), то есть лимит не «продавлен» — он исполняется.

Чего этот вывод **не** говорит: что 1.57 запроса/с — предел хоста. Потолок не найден:
проба кончилась на исчерпании бюджета в 800 документов, а не на первом отказе. 0.2–0.5 —
**нижняя граница того, что хост терпит**, а не его максимум. Поэтому следующий шаг — не
«ещё ускорить», а панель `0.05–0.2` с тем же прибором; пока её нет, 0.2–0.5 — самое быстрое
из **измеренного**.

**Куда положить число.** `rate_limit` — ось прогона, а замер — про один хост. Run-level
значение молча распространилось бы на непроверенные хосты (`edu.postgrespro.ru`,
`database.diasoft.ru`, `wiki.astralinux.ru`, browser-профили), поэтому честнее per-site ключ
`domain_profiles.yaml: docs.tantorlabs.ru: rate_limit` — до тех пор, пока другие хосты не
измерены так же. Ось входит в `crawl_config_digest` ⇒ смена — `execution_change` с новым
`run_id`, а не правка на месте.

Верхняя граница текущего лимита (5.0 с) не подтверждена ничем и раньше: панель A дала
медиану 3.15 с. Цена осторожности видна в балансе панели A: стена 944 с, сумма длительностей
ответов 396 с, суммарное ожидание лимитера по потокам 4825 с — обход был ограничен
**расписанием**, а не сетью. Критический путь когорты
(`2026-11-02-crawl-cohort-parallel.md`: `docs.tantorlabs.ru` — 5.02 ч из 5.5 ч стены) с
предлагаемым лимитом становится **≈0.9 ч**. Новая стена когорты этим замером не измерена
(после падения этого хоста её задаёт другой хост).

## 6. Что не измерено

- **Сколько запросов хост терпит в час/сутки.** Окно — 159–944 с на панель; самая быстрая
  панель держала 250 запросов за 2.7 мин. Час и сутки не проверялись, `429` не наблюдался
  вообще, поведение `Retry-After` не проверено.
- **Поведение при >1.57 запроса/с.** Потолок не найден по построению (бюджет 800 документов
  израсходован). Нужна панель `0.05–0.2` и, желательно, длинное окно.
- **Другие хосты.** Замер — про один хост. `tantorlabs.ru` (browser), `wiki.astralinux.ru`,
  `edu.postgrespro.ru`, `database.diasoft.ru` этим числом не покрыты; их лимиты остаются
  необоснованными, пока не измерены так же.
- **HTTP-хопы редиректов.** Прибор считает **попытки фетча** (элемент сеанса), а цепочка
  `301` внутри одной попытки идёт без отдельного `wait`: темп редиректных хопов не объявлен
  и не измерен (§7.3).
- **Влияние на решение, если упрёмся в хост.** Тогда рычаг — не лимит, а число полос
  (`crawl.host_concurrency`), расписание и приоритет корней; в этой пробе одного хоста
  полосы не работали (1 хост ⇒ 1 полоса).
- **Извлечение и полный прогон.** `--crawl-only`: docling не запускался, корпус не собирался,
  `run_id`-провенанс полного прогона не проверялся. Влияние лимита на `run_id` —
  `execution_change` по `crawl_config_digest`, но это свойство кода, а не замер.
- **`robots.txt`/sitemap.** Запросы вне `crawl_session_items`: у пути Scrapy лента
  перезапрашивается **на каждый документ** (301 → чужой хост → 404), у пути `http` —
  один раз на origin; сколько хопов делает роботс-читатель, прибор не считает (§7.5).
  `robots_disallow` не появился ни разу: лента недоступна ⇒ трактуется как разрешение по
  RFC 9309 §2.3.1.4 только для «404/410», а здесь 301-цепочка в 404 — то есть наблюдение
  «ленты нет».
- **Природа ~1.33 с на ответ — разобрана** (§4, §7.5): это наша обвязка (повторный
  `robots.txt` на каждый документ + `DOWNLOAD_DELAY` Scrapy), а не ответ хоста; хост отдаёт
  страницу за ~100 мс. Не измерено обратное: сколько из 1.33 с приходится на каждый из трёх
  запросов по отдельности — разложение сделано по вариантам настроек, а не по таймингам
  отдельных запросов.

## 7. Дефекты и наблюдения, встреченные по пути

1. **Объявленный сид `docs.tantorlabs.ru/` мёртв** (§2): 301 на `tantorlabs.ru/docs/`, то есть
   за scope. Полный прогон с этим сидом сегодня получит ноль документов с этого корня и
   `redirect_out_of_scope` в отказе. Это правка `sources/corpus_urls.yaml`/паспорта, а не
   настройка лимита — и она `execution_change`.
2. **`hound crawl resume` падает после убитого прогона:**
   `AssertionError: crawl-драйвер: полосы без отправленной волны и без права на host`
   (`core/pipeline/corpus_driver.py:555`). Воспроизведено на сеансе панели A: 91 документ
   добыт, процесс убит по таймауту оболочки, `crawl resume` с теми же аргументами напечатал
   `crawl product start: tantor`, счётчики замерли на `fetched=91`, затем AssertionError.
   Практическая цена: восстанавливаться пришлось `--from-scratch`, то есть 91 документ
   скачан повторно (бюджет пробы это учитывает). До починки «поднять лимит и продолжить»
   не является безопасным путём восстановления.
   **Починено 07.11.2026.** Причина — не состояние сеанса, а цикл драйвера: волна **без
   живого фетча** (resume из retained-байтов, блэклист, исчерпанные попытки) коммитится
   сразу, и корень тут же отдаёт следующую, но шаг (3) считал «нет отправленной волны»
   застоем, не проверяя, есть ли у полосы готовый план. Первая волна resume, целиком
   составленная из уже `FETCHED` URL (у убитого сеанса — всегда), падала на этом.
   Возврат к шагу допуска вместо падения (`corpus_driver.py`, шаг (3)); ассерт остался
   сторожем настоящего застоя — полосы без плана вовсе. Регресс:
   `tests/pipeline/test_corpus_concurrency.py::test_resume_after_interrupted_session_continues_without_refetch`
   (2 из 5 `FETCHED`, сеанс `interrupted` ⇒ resume добирает остаток, повторных фетчей 0).
3. **Хопы редиректов не пейсятся.** `rate_limiter.wait` вызывается один раз на попытку
   фетча (перед `crawler.fetch`), а цепочку `Location` ведёт транспорт
   (`core/util/redirects.py`): каждый `301` — отдельный HTTP-запрос вне объявленного
   интервала. На этом хосте редиректы обычны (`/tdb/` → страница версии, `…/15_18/…` →
   `…/15_19/…`), так что реальный HTTP-темп выше `requests_per_s` из таблицы на долю
   редиректных страниц; доля не измерена.
4. **Достигнутый темп упирается в драйвер, а не в хост.** При 0.35 с номинала получено
   1.57 запроса/с вместо 2.86: 25 интервалов из 249 длиннее 2× номинала — это простой на
   барьере волны (`max_workers: 10`), а не работа лимитера. Если понадобится больше
   1.6 запроса/с с одного хоста, рычаг — не `min_s`, а волна/конвейер.
5. **Скрытый второй пейсер и скрытая нагрузка на хост (найдено 07.11.2026 при разборе
   `fetch_ms`; объясняет ~1.2 с из 1.3).** Путь Scrapy на **каждый** `fetch` строит свежий
   `CrawlerRunner` (`core/adapters/crawl_scrapy.py:1198-1212`), поэтому:
   - `robots.txt` перезапрашивается **на каждый документ**. У этого хоста он отдаёт
     `301` → `https://tantorlabs.ru/docs/robots.txt` → `404` (проверено `curl`, 07.11.2026),
     то есть на документ уходит **два** запроса на `docs.tantorlabs.ru` (страница + лента) и
     **один на чужой хост** `tantorlabs.ru` — вне объявленного лимита, вне счетчика
     (`pacing.requests` считает попытки фетча) и вне `crawl_session_items`;
   - `DOWNLOAD_DELAY: 0.5` (рандомизированный 0.25–0.75 с) — **второй пейсинг** поверх
     `RateLimiter`, нигде не объявленный и не входящий ни в один дайджест. Свежий downloader
     на каждый `fetch` делает задержку бессмысленной как «вежливость» (она не соблюдает
     интервал между документами), но исправно начисляет 0.25–0.75 с **внутри** одной попытки,
     между запросами ленты и страницы.

   Цена: ~1.2 с собственной задержки на документ (на 5000 документов ≈1.7 ч одной полосы) и
   **двукратная нагрузка на хост при вдвое заниженном счётчике**. Замер, разложивший это:
   `plan.robots=False` → 147 мс; `robots=True` + `DOWNLOAD_DELAY=0` → 246 мс;
   `robots=True` + штатные настройки → **1409 мс**. Путь `http` этого не имеет: `RobotsGate`
   кеширует ленту на origin (`core/util/robots.py:368-375`), и тот же pipeline в тех же
   условиях даёт **104 мс** на документ при `in_flight_max = 1` и 2.47 запроса/с
   (run `ru-pg-dbms-06c4d8f5942f`, 60 документов, `rate_limit 0.2–0.5`).
   Не починено: правка (`DOWNLOAD_DELAY` = 0 либо кеш ленты на origin, плюс учёт
   `robots`/хопов в приборе темпа) — `execution_change`, решение владельца.

## 8. Воспроизведение

```bash
D=$HOME/.cohound/stands/crawl-pace            # изолированный стенд: runs/, state/ свои
# в копии $D/packages/probe: run.yaml:crawl.rate_limit / crawl.max_documents,
#                            domain_profiles.yaml:docs.tantorlabs.ru.max_documents
# --urls: {tantor: [https://docs.tantorlabs.ru/tdb/]}   (см. §2: корень / отдаёт 301 за scope)
COHOUND_HOME=$D COHOUND_PATHS_FILE=$D/paths.yaml ./hound.py crawl run \
  --run-yaml $D/packages/probe/run.yaml --package $D/packages/probe \
  --urls $D/urls-docs-tantor.yaml --crawl-only --from-scratch \
  --only-product tantor --follow
COHOUND_HOME=$D COHOUND_PATHS_FILE=$D/paths.yaml ./hound.py crawl status \
  --run-id {run_id} --per-host --json
```

`run_id` панелей: A `ru-pg-dbms-ee768b55d501`, B `ru-pg-dbms-8878d8e50dcb`,
C `ru-pg-dbms-59b25866a07f` (разные, потому что `rate_limit` входит в
`crawl_config_digest`). Логи прогонов и JSON `crawl status` — в стенде
`$D/logs/{panelA2,panelB,panelC}.log`, `$D/logs/panel{A,B,C}-status.json`; стенд
`runs/`/`state/` — данные, в дерево не коммитятся.
