# Продукт `gaussdb`: первый корпус профиля на китайском

Замер 22.11.2026. Приборы: `scripts/derive_llms_seeds.py` (seed-набор),
`./hound.py run --until corpus` (сборка), `scripts/measure_zh_retrieval.py` (находимость).
Стенд `~/.cohound/stands/ru-pg-dbms`, прогоны `ru-pg-dbms-7683e0a12112` (сборка) и
`ru-pg-dbms-0ada4b8f0adb` (переиспользование, `complete=1`).

## Зачем этот продукт в профиле

Не ради ещё одной СУБД: цель §1.1 — EN/RU/ZH, и до `gaussdb` китайский не был проверен
ни на одном живом корпусе. Профиль был двуязычным **по факту**, а не по объявлению.

## Корпус не обходится деревом, и это измерено, а не предположено

HTML-страница сайта вендора несёт только каркас. Замер `curl`
(`centralized-ref-v10-gaussdb/gaussdb-38-0001.html`):

| | значение |
|---|---|
| размер HTML | 77 578 байт |
| текста на странице | ≈1 900 символов |
| абзацев документации | 0 |
| длинных прогонов иероглифов | 1 (слоган шапки) |
| `<div id="content">` | пуст — содержимое подгружается скриптом |

Обход по `<a href>` собрал бы навигацию и дал бы `corpus_coverage.complete=True` на
корпусе **без материала** — то есть худший исход: отсутствие стало бы «доказуемым» на
пустом месте (I2d). Вендор публикует ту же страницу вторым представлением
(`rel="alternate" type="text/markdown"`, отдаётся `text/markdown`) и полный машинный
индекс `https://support.huaweicloud.com/gaussdb/llms.txt` (5 566 666 байт, 15 235
ссылок с описаниями).

Поэтому seed-набор — **вывод прибора** из индекса, а не список, написанный рукой, и он
статичен: `plan` считает `run_id` до сборки портов и без сети, а `seeds_digest` входит
в контракт.

## Перепись индекса и объявленный срез

Индекс: **15 235** документов в 40 разделах. В срез входит **5 911**.

| раздел | документов | в срезе |
|---|---|---|
| 参考（分布式_V2.0-10.x） | 1 426 | да |
| 参考（集中式_V2.0-10.x） | 1 635 | да |
| 开发指南（集中式_V2.0-10.x） | 850 | да |
| 开发指南（分布式_V2.0-10.x） | 774 | да |
| API参考 / 最佳实践 / 用户指南 / 常见问题 / 其余 10.x | 1 226 | да |
| 计费说明 | 16 | **нет** — биллинг не описывает возможность |
| 编辑器 8.x / 3.x / 2.x | 9 307 | **нет** — профиль измеряет одну редакцию |
| 特性指南 257, 兼容性参考 174, 工具参考 17 | 448 | **нет** — редакции 10.x у них нет вовсе |

Две последние строки — объявленная **граница**, а не пропуск: у этих руководств
редакции V2.0-10.x не существует, и объявить их «вне среза по недосмотру» было бы
неправдой. Число вне среза названо (9 307 + 16 + 448), чтобы «5 911» читалось как
доля, а не как «столько и есть».

Одна ссылка из среза **исключена прибором** — см. раздел про дефект ниже.

| | значение |
|---|---|
| seed-адресов | 5 911 |
| снято корней | 5 911 из 5 911 (`complete=1`, `observed_how=live`, `policy_matched=true`) |
| документов в корпусе | **5 555** |
| схлопнуто по `content_hash` | 356 (алиасы версий: один текст под несколькими адресами) |
| чанков | **50 813** |
| символов | 48 851 820 |
| время краула | 5 243.84 с = **1.13 запроса/с** на одном хосте |
| время эмбеддинга | 6 478 с, 50 813/50 813 чанков (16.09 чанк/с, 14 % из кэша) |
| размер `corpus_raw` | 163 МБ |
| `extractor_version` | `text-plain-2` |
| `chunker_version` | `md-ast-1:…policy-6+text-para-4` |

Темп объявлен в `domain_profiles.yaml` как `rate_limit 0.05–0.2` — это темп, который хост
**терпел** (40 запросов, 40 × `200`, ноль `429`/`5xx`, медиана 0.71 с / p90 1.29 с), а
не его потолок: потолок не искали, поэтому значение — нижняя граница терпимого.

`host_concurrency=5` объявлен на узле, но у продукта один хост ⇒ одновременно полос не
больше одной; это видно в прогоне строкой провенанса, а не выводится из конфигурации.

## Корпус действительно китайский — проверено, а не предположено

Медиана доли иероглифов в чанке — **0.364**; чанков, где иероглифы больше половины
символов, — **29.6 %**. Доля выглядит скромно, но это свойство **документации СУБД**, а
не признак сбоя: в чанк попадают SQL-примеры, таблицы параметров и латинские
идентификаторы, которые в китайском тексте остаются латиницей. Прозаические чанки
читаются как проза:

```
# 使用前必读
GaussDB是华为自主创新研发的分布式关系型数据库。该产品支持分布式事务，同城跨AZ部署…
```

Пустых документов (меньше 50 символов суммарно) — **5** из 5 555.

## Найденный дефект: битая ссылка вендора стоила доказуемости всего продукта

Индекс содержит одну склейку двух адресов в один:

```
https://support.huaweicloud.com/scenecode-gaussdb/https://codelabs.developer.huaweicloud.com/…
```

Метка пустая (`[]`), такая ссылка одна на 15 235. Сервер отвечает `404`, корень получает
`complete=0`, и — по I2d — **отсутствие перестаёт быть доказуемым у всего продукта**,
потому что носитель `bounded` требует снятия каждого объявленного корня. Прогон
`ru-pg-dbms-7683e0a12112` получил `coverage.complete=0` при **5 911 успешных снятиях из
5 912** и завершился `EXIT_ERROR` (`session_status=partial`).

Цена измерена, а не описана: одна ссылка из 15 235 отменила 5 911 снятий.

Прибор теперь различает два класса непригодного адреса: `credentials` (адрес с паролем —
признак, что индекс не тот ⇒ отказ) и `nested_scheme` (битая ссылка самого вендора ⇒
исключение **с публикацией счёта**: `исключено битых ссылок: 1`). После правки прогон
`ru-pg-dbms-0ada4b8f0adb` даёт `complete=1`, 5 911 корней `complete=1`, `blocked={}`.

## Что это значит для методологии

`robots` этого сайта закрывает `/*?*`, `/en-us/`, `/special/`, `/zhishi/`, `/guide/`,
`/theme/`, `/topic/` — ни один seed среза в эти шаблоны не попадает, отказов `robots` в
прогоне нет. Подача артефактов не понадобилась: корпус собран целиком тем, что сайт
отдаёт открыто.

Пропуск по расписанию (`scheduled/2160`, раз в 90 дней) в прогоне `0ada4b8f0adb` дал
`decision=reuse`, `network=deny`, `corpus=chunks` — и `coverage.complete=1`. Это ровно
семантика 0.7.0: полноту решают снятия корней, а не то, трогали ли сеть в этом прогоне.
