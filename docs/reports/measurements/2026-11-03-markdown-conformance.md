# Markdown-грамматика: conformance по блочной структуре

**Дата:** 03.11.2026. **Класс:** приёмка разбора (не меняет условия измерения сама по себе;
правка `md_ast`, найденная этим замером, — `execution_change`, потому что меняет покрытие
блоков). **Срез:** план `docs/architecture/18-markdown-chunker-plan.md` §7, «Conformance».
**Инструмент:** `scripts/conformance_md.py`.

## Что мерилось

Заявление «мы реализуем CommonMark + GFM» проверяется не примерами из головы, а наборами
спецификаций: CommonMark **0.31.2** (652 примера) и GFM (`cmark-gfm` `test/spec.txt`, 672
примера, 2 отключены в самом наборе). Спеки **не вендорятся** в репозиторий (лицензия
CC-BY-SA): они кэшируются вне дерева, в `$COHOUND_CONFORMANCE_DIR` (по умолчанию
`~/.cohound/conformance`), и скачиваются один раз. Нет кэша и нет сети — харнесс
**отказывается** с кодом 2 и печатает, чего не хватает; «0 примеров» он не выдаёт.

Меряется **блочная структура**, а не HTML: рендерера в проекте нет, а чанкеру нужны блоки
со спанами, а не разметка. Из ожидаемого HTML строится последовательность видов блоков
(`heading`/`paragraph`/`blockquote`/`list`/`table`/`fence`/`html`/`thematic_break`), и она
сравнивается с тем, что отдаёт `core.adapters.md_ast.parse_markdown(text, profile)`.
Отдельно проверяются два свойства, на которых стоит чанкер:

- **P13** — `counts["unknown_lines"] == 0`: каждая непустая строка принадлежит блоку;
- **P1-свойство** — каждый непустой символ источника покрыт блоком (иначе текст молча
  выпадает из чанков).

| набор | всего | отключено набором | сопоставимо | совпало | расхождения | исключено |
|---|---:|---:|---:|---:|---:|---:|
| CommonMark 0.31.2 | 652 | — | 635 | **635** | **0** | 17 |
| GFM (spec, cmark-gfm) | 672 | 2 | 653 | **653** | **0** | 17 |

| инвариант | CommonMark | GFM |
|---|---|---|
| P13 (`unknown_lines = 0`) | **652 / 652** | **670 / 670** |
| P1-свойство (символы покрыты) | **652 / 652** | **670 / 670** |

Исключения из сравнения — не «неудобные примеры», а названный класс с номерами:

| класс | CM | GFM | почему не сравнимо |
|---|---:|---:|---|
| `html_raw_container` | 7 | 7 | сырой HTML-элемент, внутрь которого браузер вложил отрендеренный markdown: границы блоков по финальному HTML не восстановить |
| `html_top_level_text` | 7 | 7 | значимый текст верхнего уровня (в т.ч. `tagfilter`), у которого в ожидаемом HTML нет блочной обёртки |
| `html_unparsed` | 3 | 3 | незакрытый тег: `HTMLParser` буферизует и теряет элемент — сигнал виден, а не выдан за пустой HTML |
| расхождение вида блока | 0 | 0 | — |

Все 17 исключений в каждом наборе — из раздела HTML-блоков (CM 148–191, GFM 118–160):
это примеры, где ожидаемый HTML содержит сырой HTML-контейнер или текст верхнего уровня.
Ни одного исключения из разделов «таблицы», «списки», «цитаты», «заборы», «ссылки» нет —
то есть выброшено не сложное, а то, что вообще не про блочную структуру markdown.

**Что именно проверяет P1-свойство.** Оно утверждает только отсутствие **непокрытых
символов** (любой непустой символ источника принадлежит какому-то блоку), а не корректность
границ спанов: перекрытие и точные смещения спанов этим замером не проверяются. Частично
это закрывает `measure_md_chunking.py` (P1 = конкатенация чанков равна входу, P4 = чанк —
подстрока), но он работает на корпусе, а не на примерах спецификации.

## Что нашёл харнесс — и что из этого исправлено

Первый прогон дал **0 расхождений структуры** и **6 нарушений P13/P1** в обоих наборах:
многострочные и экранированные определения ссылок (CM 193, 194, 195, 198, 208, 541; в GFM
те же случаи — 162, 163, 164, 167, 177, 549). Причина — не в грамматике, а в обходном
правиле: парсер определений ссылок не отдаёт токеном (они уходят в `env.references`),
поэтому `md_ast` восстанавливал их по разрыву покрытия **однострочной регуляркой**:
URL обязан быть в той же строке, экранированная `\]` не понималась. Всё, что не совпало,
объявлялось `unknown_construct` — то есть текст оставался вне блоков и вне чанков.

Исправлено сканером по §4.7 CommonMark (`_reference_definition_end` в
`core/adapters/md_ast.py`): метка может переноситься на следующие строки и содержать
экранированные скобки (≤ 999 символов), назначение и заголовок — стоять на отдельных
строках; определение обязано занять разрыв **целиком**, иначе он остаётся разрывом (P13
не перестаёт быть сигналом). После правки — 652/652 и 670/670 по обоим инвариантам,
структурных расхождений по-прежнему 0.

Стоимость правки для корпуса не нулевая по смыслу, но нулевая по числу: на измерительном
корпусе (`ru-pg-dbms-1e0b04d6d83a`) `unknown_lines` был равен нулю и до правки, то есть
эти 6 форм в нём не встречались. Правка меняет **что считается блоком** (`reference` вместо
дыры), поэтому она — `execution_change` для случаев, где такие определения есть.

## Чего эти числа не показывают

- **HTML-рендеринг.** Сверяется блочная структура, а не вывод. Это осознанная граница: у
  проекта нет рендерера, а чанкеру он не нужен.
- **Вложенность.** Сравнение верхнеуровневое: списки внутри цитат и таблицы внутри списков
  проверяются только по внешнему виду блока, не по составу детей.
- **`tagfilter`** не включён в профиль `gfm` — примеры с ним исключаются классификатором,
  а не считаются совпавшими.
- **Набор GFM пинован коммитом** (`cmark-gfm@27d942c8`), и оба набора сверяются с
  объявленным `sha256`: если содержимое под пинованным адресом изменится, харнесс
  откажется мерить, а не тихо пересчитает «другие 670 примеров».
- **Property-based (`hypothesis`), мутационная приёмка и оракул Pandoc** из §7 плана в этот
  замер не входят.

## Воспроизведение

```bash
.venv/bin/python scripts/conformance_md.py                       # оба набора из кэша
.venv/bin/python scripts/conformance_md.py --offline             # без сети; нет кэша → код 2
COHOUND_CONFORMANCE_DIR=/tmp/conf .venv/bin/python scripts/conformance_md.py --limit 20
```

Пины харнесса — `tests/adapters/test_md_conformance.py` (формат `spec.json`, формат
`spec.txt` с `→` и `disabled`, классификатор HTML, отказ без кэша, P13-поведение на
многострочном определении). Сеть в тестах не используется.
