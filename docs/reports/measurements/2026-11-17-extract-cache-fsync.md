# Цена `fsync` в `extract_cache`: разложение `put` на составляющие (O32, остаток)

**Дата:** 17.11.2026
**Дерево:** рабочее дерево на базе `aed4e53` + правка прибора `scripts/measure_extract_cache.py`
(разложение записи); `core/` **не** правился.

(нейтрален к предметной категории: пишет и читает файлы кэша, не зная, о чём документы).

## 1. Где именно стоит `fsync`

`core/pipeline/extract_cache.py:586-596` — единственная точка записи (`_write_atomic`,
вызывается из `put` на `:560`):

```python
            with handle:
                handle.write(payload)
                handle.flush()
                os.fsync(handle.fileno())
            os.replace(tmp, path)
```

Синхронизируется **файл** — дескриптор временного файла `.{key}.{rand}.tmp`, лежащего в
подкаталоге `{hash[:2]}/`; затем файл **переименовывается** через `os.replace`. Каталог —
ни подкаталог `{hash[:2]}`, ни его родитель — **не синхронизируется**: в модуле ровно одна
строка с `fsync` (`rg -n 'fsync' core/pipeline/extract_cache.py` → `:595`). Значит `put`
делает **один** `fsync`, и он платит за **содержимое**, а не за **имя** записи: падение после
`fsync`, но до фиксации метаданных каталога, оставляет либо старый файл, либо отсутствие
записи (промах — корректный исход для кэша), но не половину конверта. Цена закрытия этого
пробела измерена отдельной графой, потому что это цена того, что **не** платится.

## 2. Условия замера (без них число не читается)

| условие | значение | почему так |
|---|---|---|
| размер записи | **5 169 байт** (конверт настоящего `put` — тоже 5 169, совпадение точное) | p50 реального кэша (замер 15.11.2026). Запись на 120 байт синхронизирует другие грязные страницы и меряет другую цену |
| прогрев | **первые 20 записей каждой составляющей отброшены** | первый `fsync` на новом каталоге несёт создание inode, расширение журнала и заполнение страничного кэша ОС — это цена первого касания, а не записи |
| повторов | **100 на каждую составляющую в каждом прогоне; 6 прогонов** | публикуется медиана (по прогонам) и p95 (внутри прогона, медиана p95 по прогонам). Среднее не публикуется: хвост распределения оно не описывает |
| носитель | `ext4` на `/dev/sdd`, **WSL2** (виртуальный диск) | `fsync` уходит в журнал ФС поверх VHDX; на голом NVMe с другим кэшем записи число будет иным. Это **граница** числа, а не оговорка |
| питание | не объявлялось; GPU не участвовала | замер — диск и CPU. Скорость на этом хосте зависит от питания (16.11.2026: +14…42 % на GPU), поэтому число принадлежит этому хосту в этом режиме, а не «ext4 вообще» |

## 3. Разложение `put` (медиана по 6 прогонам × 100 записей, прогрев 20)

| составляющая | медиана | p95 | доля от полного `put` |
|---|---:|---:|---:|
| запись без `fsync` (`mkdir` + `mkstemp` + `write` + `flush` + `close` + `os.replace`) | **0.119 мс** | 0.219 мс | 6.0 % |
| **`put` без `fsync`** (парно: `put − fsync` из **одной** итерации) | **0.272 мс** | 0.589 мс | **13.7 %** |
| **`fsync` файла внутри `put`** | **1.673 мс** | 2.201 мс | **84.5 %** |
| `fsync` каталога внутри `put` (**код его не делает**) | **1.420 мс** | 2.182 мс | — |
| **полный `put`** (`ExtractionCache.put`, контроль) | **1.981 мс** | 2.795 мс | 100 % |

Разброс между прогонами (медианы): `put` 1.785–2.243 мс, `fsync` файла 1.550–1.865 мс, запись
без `fsync` 0.085–0.156 мс. Доля `fsync` в `put` по прогонам — **83.1–86.8 %**, то есть вывод
не держится на одном удачном прогоне.

**Абсолютные цены плывут с загрузкой хоста, отношение — нет.** Контрольный седьмой прогон,
снятый при занятом хосте (полный обход 0.541 с против 0.318–0.436 с в шести предыдущих), дал
`put` **2.311 мс**, `fsync` файла **1.939 мс**, остаток **8.1 %** — то есть все абсолютные числа
выросли на ~17 %, а доля `fsync` осталась **83.9 %**. Поэтому публикуется медиана по прогонам, а
не одно число, и «1.98 мс» — цена на незагруженном хосте, а не константа `ext4`.

Парная разница «`put` + `fsync` каталога» минус «`put`» (обе половины — настоящий `put`, один
носитель, одно состояние кэша ОС): **1.418 мс медиана, p95 2.337 мс** — столько стоило бы
сделать запись durable по имени, а не только по содержимому.

## 4. Контроль: сумма частей сходится с настоящим `put`

| | медиана |
|---|---:|
| `put` без `fsync` + `fsync` файла | **1.945 мс** |
| полный `put` | **1.981 мс** |
| остаток | **0.037 мс** — **8.6 %** от `put` (по прогонам 7.0–11.1 %) |

Остаток положителен и одного знака во всех шести прогонах. Это то, что `put` делает сверх
`_write_atomic`: `json.dumps` конверта (5 169 байт, `sort_keys`), вычисление пути, `stat`
записанного файла, немедленный выход `_evict_if_needed` при `budget=None`. Контроль сходится
на 91 %; остаток объяснён по составу, а не списан на шум.

**Метод был переделан по ходу замера, и это часть результата.** Первая редакция мерила `fsync`
втором независимом цикле записи. На втором прогоне остаток стал **отрицательным (−10 %)**:
`fsync` в отдельном цикле дал 1.469 мс, а в следующем — 1.840 мс, то есть два цикла меряли два
разных состояния ФС и складываться не были обязаны. Поэтому цена `fsync` теперь снимается
**внутри настоящего `put`** (обёртка вокруг `os.fsync`/`os.replace` в модуле
`core.pipeline.extract_cache`), а «`put` без `fsync`» получается парным вычитанием из той же
итерации. Аддитивность после правки держится во всех шести прогонах.

Сверка с ранее опубликованным: 15.11.2026 медиана `put` была **2.1 мс**, сейчас **1.98 мс** —
та же величина. Ориентир из `embed_cache` (≈5 мс/запись,
`2026-10-25-embed-cache-footprint.md`) на эту раскладку **не переносится**: другая ФС-раскладка,
другой размер записи, другая частота `fsync`; здесь `fsync` вдвое дешевле.

## 5. Сколько `fsync` делает один прогон и сколько это стоит

Число `put` за прогон = число **извлечённых** документов: на хите `put` не зовётся
(`core/pipeline/extract_consume.py:428-450` — `get` при хите, `put` только после экстрактора).
Счётчика `put` в `state.db` нет, поэтому источник — артефакт прогона:

| величина | значение | источник |
|---|---:|---|
| документов в корпусе прогона `ru-pg-dbms-145ad66ca3f9` | **19 324** | `corpus_docs` в `runs/ru-pg-dbms-145ad66ca3f9/cohound.db` |
| hit-rate кэша | **0.8353** | этот прогон прибора; 15.11 — то же число |

| `put` за прогон, **прогретый** кэш | **3 184** | 19 324 × (1 − 0.8353) |
| состав корпуса (он и решает ответ) | 17 387 `trafilatura-html-6` / 1 743 `docling-doc-3:layout_tables/cuda` / 194 `text-plain-2` | `corpus_docs.extractor_version` того же прогона |

## 6. Доля от времени извлечения — и почему ответ зависит от того, чья цена в знаменателе

Время фазы `corpus` этого прогона **не одно число**: `logs/corpus.jsonl` содержит четыре `start`
(12.11 22:36, 13.11 20:09, 14.11 13:01:00, 14.11 13:01:45) и один `end` (14.11 13:22:49,
`status=ok`, `pending=0`) — прогон возобновлялся. Отсюда две границы:

| знаменатель | значение | доля `fsync` (холодный) | доля `fsync` (прогретый) |
|---|---:|---:|---:|
| последний полный сегмент фазы | **1 264 с** (13:01:45 → 13:22:49) | **2.56 %** | 0.42 % |
| всё время от первого `start` до `end` (включая простой между возобновлениями) | 139 576 с | 0.02 % | 0.004 % |

При любом чтении журнала цена `fsync` за прогон — **меньше 2.6 %** времени фазы, в которой эти
записи делаются. Вывод «на масштабе прогона не материальна» держится на всём интервале, а не на
удачном знаменателе.

**Но на масштабе документа ответ другой, и это важнее.** Отношение цены `fsync` к цене
извлечения — это 1.67 мс против цены извлечения одного документа, а она различается на три
порядка:

| путь извлечения | цена | `fsync` файла в доле | источник цены |
|---|---:|---:|---|
| `text_layer` (pdfium), на **страницу** | 1.88 мс | **89 %** | `2026-11-15-nested-archive-member-ceiling.md` (3 990 стр. за 7.5 с) |
| `structured`/`layout_tables`, cuda, на **страницу** | 119 мс | 1.4 % | `2026-10-28-gpu-vs-cpu-extraction.md` (БП, 1 747–1 770 МГц) |
| фаза `corpus` целиком, на **документ** | 65.4 мс | 2.56 % | этот прогон: 1 264 с / 19 324 док. |

Для 90 % корпуса этого прогона (HTML через `trafilatura`) опубликованной цены на документ нет —
это `None`, а не «мало». Честная формулировка: **`fsync` — 84.5 % цены `put`, но сама `put` на
масштабе прогона в шуме; материальной она становится там, где извлечение дешёвое** — на pdfium
1.67 мс `fsync` против 1.88 мс извлечения на страницу, то есть тот же порядок.

## 7. Что из этого следует

1. **`fsync` — это и есть `put`.** 84.5 % медианы `put` — один вызов `os.fsync`; всё остальное
   (`write`, `flush`, `close`, `os.replace`, `json.dumps`, `stat`) — 15.5 %. Оптимизация записи,
   не трогающая `fsync`, оптимизирует шестую часть и не может дать больше.
2. **Каталог не синхронизируется, и это осознанная цена, а не бесплатность.** Запись durable по
   содержимому, но не по имени: после падения запись может исчезнуть (промах — корректное
   поведение кэша), но не может быть половинчатой. Закрытие пробела стоит **+1.42 мс на `put`**
   (p95 2.34 мс), то есть **+27.4 с на холодный прогон** — почти удвоение цены записи. Для кэша,
   чей промах стоит одного переизвлечения, это не покупается; число опубликовано, чтобы решение
   не выглядело бесплатным.
3. **Порог 1/16 бюджета (`EVICT_CHECK_BYTES_DIVISOR`) и `fsync` — величины одного порядка.**
   Один обход 44 796 файлов стоил в этот раз 0.318–0.436 с = 160–220 записей по 1.98 мс.
   Амортизация по байтам окупается уже на ~200 записях, то есть на любом реальном прогоне:
   это подтверждает решение из §7 отчёта 15.11 с другой стороны.
4. **Для профиля с дешёвым читателем (`text_layer`) `fsync` — не шум.** Если встанет вопрос
   «почему прогон на pdfium не ускорился во столько раз, во сколько ускорилось извлечение»,
   ответ уже есть числом: на страницу извлечение 1.88 мс, `fsync` 1.67 мс.

## Что не измерено

- **Цена `fsync` на голом NVMe / другой ФС.** Число принадлежит `ext4` внутри WSL2; другого
  носителя на этом хосте нет, сравнение не делалось.
- **Цена `fsync` при конкурентных писателях.** Мерялся один процесс. При `N` воркерах над одним
  корнем `fsync` конкурируют за журнал ФС, и число может вырасти — это названное свойство, не
  замер.
- **Цена `fsync` для записей-гигантов.** p99 реального кэша — 124 376 байт, max — 21 401 472;
  мерялся только p50 (5 169). Для 21 MB записи `fsync` может быть заметно дороже, но таких
  записей в кэше единицы, и на прогон они не влияют.
- **Число `put` за прогон — из артефакта, а не из счётчика.** Счётчика `put` в `state.db` нет.
  19 324 — это `corpus_docs`; «сколько из них реально извлекалось» восстанавливается через
  hit-rate (0.8353), который сам считается по `document_version` (17 874 строки). Оценка по
  `document_version` дала бы 2 944 прогретых `put` вместо 3 184 — разница 7 %, на вывод не влияет.
