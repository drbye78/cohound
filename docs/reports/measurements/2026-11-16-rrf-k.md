# D4: RRF-константа плеч R2 — насыщение при k ≥ 40, осью не становится (16.11.2026)

**Что измерялось.** Последний остаток решения D4: `DEFAULT_RRF_K = 60` (`core/pipeline/retrieve.py`)
зашита в код, а не объявлена. Вопрос был не «какая константа лучше по мнению», а «есть ли на
неё эффект, который стоит объявлять осью» (A3).

**Условия.** Прогон `ru-pg-dbms-145ad66ca3f9`, сборка `cb_5c090025af68b95615c87869`, эталон
документного уровня O14 (132 ячейки), `cutoff_k = 10`, бутстрэп 1000, seed 0, профиль `R2`
(RRF-слияние лексического и dense-плеча), `pool_multiplier = 1`. Сетка констант:
**10, 20, 40, 60, 100, 200** (`--rrf-ks`, прибор `scripts/measure_retrieval_docs.py`).

**Метод.** Парное сравнение каждой константы с дефолтом 60 по одним и тем же 132 ячейкам:
дискордантные пары и точный критерий МакНемара для `hit@10`, парный бутстрэп для дельты
`MRR`, плюс проверка того, что именно меняется — состав top-10 или порядок внутри него.

## Результат

| `rrf_k` | hit@10 | MRR | nDCG@10 | Δ hit | better/worse | p | Δ MRR | тот же порядок top-10 |
|---|---|---|---|---|---|---|---|---|
| 10 | 0.2121 | 0.1123 | 0.1363 | +0.0000 | 0 / 0 | 1.000 | −0.0025 [−0.0069; 0.0000] | 121 / 132 |
| 20 | 0.2121 | 0.1136 | 0.1374 | +0.0000 | 0 / 0 | 1.000 | −0.0013 [−0.0038; 0.0000] | 126 / 132 |
| **40** | 0.2121 | 0.1148 | 0.1383 | +0.0000 | 0 / 0 | 1.000 | +0.0000 | **132 / 132** |
| **60** (дефолт) | 0.2121 | 0.1148 | 0.1383 | — | — | — | — | — |
| 100 | 0.2121 | 0.1148 | 0.1383 | +0.0000 | 0 / 0 | 1.000 | +0.0000 | 132 / 132 |
| 200 | 0.2121 | 0.1148 | 0.1383 | +0.0000 | 0 / 0 | 1.000 | +0.0000 | 132 / 132 |

Ориентир: R0 (лексика) — hit@10 0.2576, MRR 0.1206, nDCG 0.1531.

**Два факта, которые важнее таблицы:**

1. **`hit@10` тождественен при всех шести константах** — 0 из 132 ячеек различимы. Причина
   видна прямым сравнением выдачи: **состав top-10 одинаков во всех 132 ячейках**, а порядок
   различается только при `k = 10` (11 ячеек) и `k = 20` (6). То есть RRF-константа на этом
   корпусе — перестановка внутри десятки, а не изменение того, что найдено.
2. **При `k ≥ 40` различие исчезает полностью**: 132 из 132 ячеек дают побитово тот же
   порядок. Дефолт 60 лежит в насыщении, а не на краю эффекта.

**Что это значит для D4.** Объявлять `rrf_k` осью нечего: единственное наблюдаемое различие
(малые константы хуже по MRR на 1–2 ячейках из 132) убывает к нулю внутри диапазона, где
дефолт уже находится. `DEFAULT_RRF_K = 60` остаётся константой кода, и это не «привычка» —
это измеренное насыщение. Смена константы на 40/100/200 не изменила бы ни одного вердикта.

**Граница, которую надо назвать.** Вывод получен на **одном** корпусе и одном наборе плеч:
`postgrespro` даёт 115 из 132 ячеек, dense-плечо — `bge-m3`. На корпусе, где плечи сильнее
расходятся по составу (сейчас их top-10 почти совпадают по составу), константа может начать
влиять — тогда её и надо будет объявить осью, с замером. Это условие пересмотра, а не
оговорка.

## Что сделано в коде

| где | что |
|---|---|
| `scripts/measure_retrieval_docs.py` | флаг `--rrf-ks` (сетка констант, только для R2), `rrf_k` в метке только когда он не дефолт, поле `rrf_k` в отчёте только при объявленной сетке (байтовая совместимость отчётов O12/O13/O14) |
| тесты | 4 новых: дефолт сетки, размножение только у R2, отказ на `0`/мусор, отсутствие поля без флага |

`run_id` не менялся: `rrf_k` входит в `retrieval_params_json` (S1), но не в
`EXECUTION_CONTRACT_FIELDS`.
