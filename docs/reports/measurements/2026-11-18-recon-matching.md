# Кросс-языковое сопоставление: где именно теряется `present` и что чинить

**Дата:** 2026-11-18 · **Корпуса:** reference-корпус PostgreSQL 11–18 (73 097 чанков;
PG18 — 9 763 чанка / 1 136 документов) и корпус когорты стенда (253 306 чанков) ·
**Каталог:** `packages/ru-pg-dbms/catalog.csv`, `catalog_digest` `60782db1…` (подписанная
авторская разметка, применена 18.11.2026) · **Приборы:** одноразовые пробники
`/tmp/opencode/param-semantics/*.py`, сводимые в `scripts/measure_recon_matching.py`

## 1. Постановка

Владелец поставил вопрос прямо: лексический поиск по английской документации предка с
русскими параметрами каталога **гарантированно** провалится, и недопустимо, чтобы из-за
слабости архитектуры делались выводы о недостаточности информации в корпусе.

Проверено тремя независимыми замерами: слой запроса, слой отбора и слой вердикта.
Ответ короткий: провалился не матчер и не язык корпуса, а **вход** (русский запрос по
английскому тексту) и **правило зачёта** (цитата засчитывалась по одному слову). Dense на
этой задаче проигрывает лексике.

## 2. Слой запроса

Три варианта запроса на PG18, `top_k` 20, 181 параметр. Числа — вывод прибора
`scripts/measure_recon_matching.py --variants code,en,phrase` (сборка
`ref_postgresql_18_3b7052ee`, 9 763 чанка, 1 136 документов). «Делится» — сколько **цитат**
обслуживают ≥2 параметра; в скобках — сколько параметров эти цитаты покрывают.

| запрос | `present` | уникальных цитат | делится (цитат / параметров) |
|---|---|---|---|
| **A.** как в коде до 18.11.2026: `title` + `concept_terms`, английский список пуст | **45/181** | 30 | **6 / 21** |
| **B.** мешок слов из авторских `terms_en` (каталог после 18.11.2026) | **180/181** | 159 | 16 / 37 |
| **C.** тот же запрос B, но цитатой считается только предложение с термином целиком | 44/181 | **44** | **0 / 0** |

Строка A воспроизводится прибором на каталоге **до** применения разметки
(`git show b56f184~1:packages/ru-pg-dbms/catalog.csv`), строки B/C — на текущем. Это разные
каталоги, и путать их нельзя: A — это «старый запрос + старое правило зачёта», B — «новый
запрос + старое правило», C — «новый запрос + правило-фраза».

Примеры дележа в A (8 параметров на одну цитату): `'Oracle Compatibility Mode #'`,
`'- createuser — define a new PostgreSQL user account'` — 4,
`'LDAP Lookup of Connection Parameters #'` — 3. Человеческая проверка A: подтвердились
**2 из 45** (точность 4.4 %).

Причина в коде одна и названа замером: `parameter_terms` (`core/pipeline/reference_corpus.py:453`)
собирает запрос из `title` + `concept_terms`, а у каталога `concept_terms["en"]` был `[]` у
всех 181 — по английской документации искались русские слова. У **110 из 181** параметра в
запросе не было ни одной латиницы.

Контроль C важен не числом, а направлением: русские слова по английскому корпусу дают
7/181 (проба `probe_ref_terms.py`, вариант `terms_ru`) — это и есть «структурный ноль»,
которого боялся владелец. Он воспроизводится только при русском запросе и исчезает, когда
запрос называет предмет.

**Сравнение A и B — главный вывод по слою запроса:** починка одного запроса поднимает
находимость с 45 до **180** параметров из 181. То есть «лексика не работает на английском
корпусе» — неверно; работал русский запрос по английскому тексту.

## 3. Слой отбора: dense против лексики

Прибор: `scripts/measure_recon_matching.py --dense` — объявленная модель
`BAAI/bge-m3@5617a9f6…`, `cuda`/`fp16`, сборка `ref_postgresql_18_3b7052ee`. Плечи
сравниваются на **одном** входе: запрос — `parameter_terms`, зачёт — `parameter_phrases`
(правило «фраза»). Различается только отборщик; иначе сравнение меряет два различия сразу.

| | лексика (BM25) | dense (косинус) |
|---|---|---|
| нашёл цитату | **37/181** | 32/181 |
| уникальных цитат | 37 | 32 |
| общих цитат | 0 | 0 |
| только этот отборщик | **11 параметров** | 6 параметров |
| обе стороны | 26 | 26 |
| ✅ судьи (n=25) | 3 (12.0 %, CI [4.2;30.0]) | **5 (20.0 %, CI [8.9;39.1])** |
| ❓ судьи | 16 | 16 |

Читается так: **dense находит меньше** (32 против 37; «только dense» — 6 параметров против
11 у лексики), но **доля подтверждённых у него не ниже**: 20 % против 12 %, интервалы
перекрываются. Значит замера, на котором dense **выигрывает**, нет; и «dense хуже по
качеству» этот замер тоже не показывает. Объединение плеч нашло бы 43 параметра из 181
(37 + 32 − 26) — это число, а не решение: качество объединения не мерилось.

Цена: эмбеддинг среза **2 000 чанков = 82.8 с** (24.2 чанк/с, тот же корпус и устройство,
прибор пишет `embed_seconds`) ⇒ 9 763 чанка ≈ 403 с; все 8 версий (73 097 чанков) ≈ 50 мин
GPU. Персист fp16 — 73 097 × 1024 × 2 Б = **149.7 МБ на все восемь версий** (≈19 МБ на
версию): это счёт, а не замер, и он назван счётом.

Вывод для §12: **персист эмбеддингов не включается** — выигрыша, который его окупил бы, не
показано (по находимости dense ниже, по подтверждённым различие не разделено на n=25).
Пересматривается тем же прибором на исправленном входе и правиле зачёта: у него теперь есть
`--dense`, и сравнение воспроизводится одной командой.

## 4. Слой вердикта: правило зачёта цитаты

Это и оказался главный дефект. `parameter_terms` режет термины на **слова** (`_terms`,
`:442`), а `select_quote` (`:543`) засчитывает цитату, если в предложении есть **любое**
из них. Многословный термин (`point-in-time recovery`) превращается в три слова и даёт три
повода совпасть случайно — то есть «подробный» термин работает **хуже** короткого.

Замер на подписанном каталоге (PG18, `top_k` 20). Кандидатов во всех трёх вариантах даёт
один и тот же запрос `parameter_terms`; различается только условие зачёта:

| правило зачёта | `present` | уникальных | делится | ✅ судьи (n=25) |
|---|---|---|---|---|
| **W1** любое слово термина (как было в коде) | **165/181** | 153 | **9 / 21** | 0 (0.0 %, CI [0.0;13.3]) |
| **W2** все слова термина, порядок не важен | 87/181 | 86 | 1 / 2 | 1 (4.0 %, CI [0.7;19.5]) |
| **P** термин целиком, дословно | **37/181** | 37 | **0 / 0** | **4 (16.0 %, CI [6.4;34.7])** |

Судья — настоящий `evaluate_cell` (`deepseek-v4.1-flash-1017:yellow`), выборка
детерминированная (`seed=0`), 75 вызовов, 0 отказов. Интервалы перекрываются: **на n=25
правила статистически не разделены**, и это надо сказать прямо.

Второй, независимый прогон тех же трёх правил на том же корпусе (пробник, другая выборка
цитат) дал **2 / 1 / 5** ✅ — то есть у одного правила (W1) две выборки дают 0 и 2. Разброс
между выборками того же правила **не меньше** разницы между правилами, и это второе
основание не выдавать судью за разделение. Разделение — структурное.

Разделены они **структурно**. Зачёт по слову даёт 165 `present` — то есть карта предка
объявила бы реализованными 91 % параметров на совпадении одного слова, и 9 цитат
обслуживали бы 21 параметр. Цитата, которая называет два разных параметра,
не называет ни одного; наследование по ней — ложный вывод, а он запрещён прямо.

Поэтому в код идёт правило **P** (фраза целиком), а не W1: не потому, что оно «лучше по
точности» (это не доказано), а потому, что оно единственное, у которого цитата
**адресует параметр**.

**Сделано 18.11.2026.** `parameter_phrases` (`core/pipeline/reference_corpus.py:480`)
собирает авторские термины **целиком** (языки в отсортированном порядке ключей, внутри —
авторский порядок; fallback на `title`, если авторских нет), и `derive_facts` (`:643`)
засчитывает цитату по нему. Запрос кандидатов остался на `parameter_terms`: recall даёт
индекс, точность — условие зачёта, и слить их значило бы либо потерять кандидатов, либо
вернуть зачёт по слову. Видимость дефекта встроена в `hound baseline recon`: payload несёт
`quotes`/`unique_quotes`/`shared_quotes`/`unique_quote_ratio` (`None` при нуле `present` —
«нечего делить» ≠ «всё делится»), и текстовая выдача печатает `цитат: N, уникальных M
(доля X.XX)` плюс до трёх общих цитат с параметрами.

**Живая проверка на стенде** (`--dry-run`, сборка `ref_postgresql_18_3b7052ee`, 9 763
чанка, 1 136 документов, 181 параметр): `present` **37**, `quotes` 37, `unique_quotes` 37,
`shared_quotes` **[]**, `unique_quote_ratio` **1.00**, `unclear` 144 — совпало с вариантом
P этого замера до единицы. Ничего не записано.

**Граница этого вывода.** Даже у P точность 16 % (4 из 25) — судья подтверждает примерно
одну цитату из шести. Человеческое
чтение подтверждённых нашло ошибку и в судье: №3 «версия PostgreSQL в качестве основы»
получил ✅ по цитате `This document describes version 3.2 of the protocol, introduced in
PostgreSQL version 18.` — протокол описан в версии 18, но это не утверждение, что продукт
вендора основан на 18. То есть 16 % — **верхняя** граница, и ложный ✅ судьи виден в цитате,
потому что цитата дословна.

## 5. Судья на найденном: почему счёт не решает

Тот же прибор, тот же вход, судья `evaluate_cell` на детерминированной выборке 25 цитат
каждого плеча (§3, последние две строки таблицы): лексика — **3 из 25** ✅, dense — **5 из
25** ✅, при 37 и 32 найденных соответственно. То есть «нашёл больше» и «нашёл верное» —
разные величины, и на этом корпусе они даже смотрят в разные стороны: у dense меньше
найденного, но выше доля подтверждённого (интервалы перекрываются, разделения нет).

Примеры ✅ (лексика): инкрементальный `pg_basebackup`, декларативное секционирование,
background worker, `JSON_TABLE`. Примеры ❓: «Разработчик» на странице `extend-how.html`,
«версия PostgreSQL в основе» на `protocol.html` — слова совпали, утверждения нет.

Отсюда второе следствие для архитектуры: **`present` без чтения цитаты не бывает
достоверным**. Три слоя разделены по ролям: запрос ищет, правило зачёта адресует цитату
параметру, чтение решает, что она утверждает.

## 6. LLM как генератор формулировок (разведка, не источник)

Взяты 133 параметра, которым авторские `terms_en` не дали цитату; случайные первые 40.
Модель `deepseek-v4.1-flash-1017` через `DiscoveryLLMPort` строит 3–6 английских фраз из
`title` + `semantics` + `rule`; документацию модель **не видит**. Затем тот же BM25,
тот же `top_k` 20, тот же `select_quote`.

- цитату нашли **30/40** (75 % остатка);
- судья: ❓24, ⚠️4, **✅2** (6.7 %);
- цена: 1 757 с на 40 параметров (40 вызовов генерации + 30 судьи) ≈ 44 с/параметр,
  то есть ≈ 1.6 ч на все 133.

Читается так: LLM-термины лечат **находимость** и не лечат **точность**. Роль — генератор
кандидатов для разметки (`status: candidate` → человек → `compile`), не источник
утверждения и не вход каталога напрямую.

## 7. Консилиум: четыре места, один порядок, три поправки

Состав: `gpt-6-luna`, `qwen/qwen3.8-max`, `z-ai/glm-5.3-flash`, `deepseek-v4.1-flash-1017`
(бриф — один файл, одни числа). Все четыре назвали один порядок: **запрос → вердикт →
отбор**, и все четыре отвергли «включить векторы» как лечение.

Расхождения и что с ними сделано:

| утверждение места | проверка | исход |
|---|---|---|
| glm: «`render_queries` до `en` не доходит **никогда**» | прогон на 181 параметре: из 73 с непустым `en` латиница доходит у **71** | механизм назван неверно, но названный риск **реален и хуже**: после подписи `terms_en` латиница попадает в запросы Ш6 и `map` только у **73 из 181** — у 108 параметров русские термины съедают все три слота (`max_queries = 3`, порядок ru→en). Измерено: `xlsx_002` → `['Год начала разработки', 'год', 'начала']` при `terms_en = ['first release', 'development started']` |
| qwen: порог успеха «≥60 % `present` при точности ≥50 %, p<0.05» | — | **отклонено**: выдуманный потолок, A3 запрещает. Публикуется интервал, решение о достаточности — владельца |
| deepseek и qwen: «базлайн 2/181» | замер A: найдено 45, подтверждено **2 из 45** | поправлено: «нашёл» и «подтвердил» — разные числа, и их смешение и есть дефект §4 |
| glm: персист «~150 МБ на версию» и «1.3 ч GPU» | 73 097 × 1024 × 2 Б = **149.7 МБ на все 8 версий**; 73 097 / 24.2 чанк/с ≈ **50 мин** | **ошибка была в брифе**, glm поймал: 150 МБ/версию и 1.3 ч неверны |
| все четыре: «`hound baseline map` на реальной сборке не исполнялся ни разу» | отчёт §5 подтверждает | принято как открытая дыра: именно `map` — место, где утверждается «предок реализует» |
| glm: «генератор и судья — одна модель, это замыкает проверку» | в замере §6 обе роли у `deepseek-v4.1-flash-1017` | принято как гигиена: у генератора и судьи должны быть разные модели; методологического требования нет, но совпадение делает «нашёл» и «подтвердил» взаимно подтверждающими |

## 8. Что из этого следует для архитектуры

1. **Запрос** строится из авторских терминов (`concept_terms`), а не из `title`: смена
   каталога 18.11.2026 это уже дала. Бюджет `max_queries = 3` при порядке ru→en оставляет
   81 параметр без латиницы — это объявленная ось (`retrieval_params_json` входит в
   `run_id`), и её изменение измеряется на reference-корпусе, где прогон стоит минуты.
2. **Правило зачёта** — фраза целиком (§4). Запрос остаётся мешком слов: recall даёт
   индекс, точность — условие зачёта.
3. **Вердикт** — чтение цитаты (`evaluate_cell` в `map`, человек в `recon`). Пока чтения
   нет, `recon` обязан публиковать не только `present`, но и **долю уникальных цитат**:
   это единственный дешёвый признак, отличающий «цитата про параметр» от «совпало слово».
4. **Dense и реранкер** — после 1–3, парным замером на исправленном входе. Первый такой
   замер сделан (§3): dense находит **меньше** (32 против 37), по подтверждённым различие не
   разделено на n=25 ⇒ персист не включается, и это решение пересматривается той же
   командой при появлении новых данных. Реранкер (`Qwen3-Reranker-0.6B`, Δ+0.0833,
   CI [+0.015;+0.144], p=0.0192) измерен на **когортном** корпусе, и 115 из 132 ячеек там —
   один продукт; переносить эффект на reference без замера нельзя (A3).
5. **LLM** — генератор формулировок (разведка) и читатель цитаты (`map`), но не источник
   терминов каталога и не судья собственных находок.

## 9. Как воспроизвести

```
# слой запроса (§2) и слой зачёта (§4), с судьёй на выборке 25 цитат
.venv/bin/python scripts/measure_recon_matching.py \
    --db ~/.cohound/stands/ru-pg-dbms/reference/ru-pg-dbms/postgresql/18/builds/{build}/reference.db \
    --catalog packages/ru-pg-dbms/catalog.csv \
    --variants code,en,phrase --rules any,all,phrase --top-k 20 \
    --judge-sample 25 --llm-model deepseek-v4.1-flash-1017:yellow

# слой отбора (§3): dense-плечо на объявленной в deploy модели, судья на обоих плечах
.venv/bin/python scripts/measure_recon_matching.py \
    --db …/reference.db --catalog packages/ru-pg-dbms/catalog.csv \
    --variants "" --dense --judge-sample 25 --llm-model deepseek-v4.1-flash-1017:yellow

# строка A §2 — на каталоге ДО применения разметки
git show b56f184~1:packages/ru-pg-dbms/catalog.csv > /tmp/catalog.old.csv
… --catalog /tmp/catalog.old.csv --variants code
```

Все числа §2–§5 получены этим прибором (18 вызовов судьи на правило/плечо — 25 выборка ×
3 правила и 25 × 2 плеча). §6 (LLM-термины) и §7 (консилиум) — отдельные разовые пробники,
которые в репозиторий не переносились: их числа здесь датированы и помечены как наблюдение
одного прогона.

## 10. Границы

- Выборка судьи n=25 на правило и на плечо: интервалы перекрываются, статистического
  разделения правил **нет**; решение принято по структурному признаку (общие цитаты), и это
  названо. Два независимых прогона судьи по одному правилу дали 0 и 2 ✅ из 25 — разброс
  выборок не меньше разницы между правилами.
- Замер §2–§5 сделан на PG18; другие версии не мерились.
- 16 % у правила P — верхняя граница: судья ошибается (§4), человеком проверены не все
  подтверждённые.
- Корпус когорты (253 306 чанков) в §2–§5 не участвовал: там мерился reference.
