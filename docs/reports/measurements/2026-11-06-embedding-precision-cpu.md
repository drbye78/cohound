# Точность эмбеддинга и параллелизм CPU на срезе корпуса — замер 06.11.2026

**Вопрос.** Продакшн-путь считает вектор в fp32 (`matmul_precision="highest"`,
`allow_tf32=False`, модель без `dtype`), отдаёт 2.8–5.7 чанка/с и является самой дорогой
фазой цикла после краула. Что даёт переход на tf32/bf16/fp16 — по скорости, по памяти и по
**согласию векторов** с fp32; и сколько ядер реально работает на CPU при разных
`torch.set_num_threads` × `batch_size`. Порогов и рекомендаций здесь нет (A3): публикуются
числа и арифметика, решение читает владелец.

**Стенд.** Каноническая раскладка хоста (`~/.cohound/data`), только чтение:
`runs/ru-pg-dbms-208472049479/cohound.db`. Ни одна команда `run`/`crawl run` не
запускалась, `core/`, `packages/`, `config/` не менялись. Замер снят на дереве
`4e394c1`; пока он шёл, ветка ушла вперёд до `293360c` (два коммита `core/` про краул и
гейт нулевого источника, `core/adapters/embed_local.py` не тронут), документ записан на
`293360c`. Инструмент — `scripts/embed_bench.py` из рабочего дерева (в коммит не входил).

| карта: занятость | 0 MiB до старта; в замере пик `reserved` 3968 MiB из 4096 |
| RAM: занятость | 5.7 GB доступно до старта |
| стек | Python 3.14, `torch 2.14.1+cu130`, `sentence-transformers 6.1.0`, `numpy 2.5.3` |

Срез выбирается **не** `random`: `row_number() OVER (ORDER BY chunk_id)`, затем каждый
`(i * total) // n`-й ряд. Повторный запуск на той же БД даёт тот же набор текстов — без
этого числа скорости и согласия не сравнить между запусками.

## 2. Метод

`scripts/embed_bench.py` (нейтрален, §1.3): модель грузится **один раз на вариант**,
прогрев — ровно один батч (в замер не входит), затем `--repeats` замеров. Батч вариантов
точности — 32, как `DEFAULT_BATCH_SIZE` продакшн-пути; нормировка и
`convert_to_numpy=True` — те же.

| метрика | определение |
|---|---|
| `chunks_per_s` | чанков/с первого замера после прогрева (`wall` без загрузки модели) |
| `peak_vram` | `torch.cuda.max_memory_allocated()` за вариант, **включая веса** (сброс пика перед загрузкой) |
| `peak_rss` | пик RSS процесса за окно замера: поток опрашивает `/proc/self/status` каждые 20 мс (не монотонный `ru_maxrss`) |
| `1 − cos` | согласие с fp32 на том же тексте; векторы перед сравнением ренормируются |
| `top-10` | средняя доля перекрытия top-10 соседей по самому сэмплу (сэмпл = набор запросов, сам сосед исключён) |
| `det` | `max |V_pass1 − V_pass0|` по компонентам, два замера одного варианта в одном процессе |
| `cpu_ratio` | `Δtime.process_time() / Δwall` за окно замера |

## 3. Варианты точности (cuda, батч 32, 512 чанков)

Замер 1 (первый запуск):

| fp16 (`autocast`) | **15.40** | 33.3 | 2903 | 3238 | 1749 | 4.17e-07 | 1.99e-06 | 8.34e-05 | 0.9980 | 0 |

Замер 2 (повторный процесс, та же выборка, те же флаги):

|---|---:|---:|---:|---:|---:|---:|---:|
| fp32 | 4.99 | 102.7 | 3231 | 1784 | 0 | 1.0000 | 0 |

Второй замер fp32 внутри себя дал 4.11 чанк/с (второй прогон после прогрева) — карта
троттлит, и это видно в разбросе, а не в настройках. Все варианты считались на одной и той
же выборке и одном и том же батче; между вариантами модель выгружалась и `empty_cache()`
вызывался явно, поэтому пики VRAM не наследуют мусор предыдущего варианта.

**Согласие.** `1 − cos` для tf32 и fp16 — на уровне 1e-7…1e-4 (то есть cos ≥ 0.9999 на
худшем чанке); у bf16 худший чанк 7.5e-04 (cos 0.99925), медиана 3.7e-05. Ранжирование
top-10 по самому сэмплу: tf32 и fp16 меняют **0.2 %** слотов соседей, bf16 — **1.07 %**
(в среднем **9.89 из 10** соседей совпадают с fp32).

**Память.** Все веса остаются fp32 (autocast не меняет dtype весов), поэтому bf16/fp16
экономят только активации: allocated 3231 → 2903 MiB (−10 %), reserved 3968 → 3238 MiB.
На карте 4096 MiB fp32-вариант с батчем 32 упирается в потолок `reserved` (3968 MiB =
96.9 % карты) — это факт запаса, а не свойство точности.

## 4. Параллелизм CPU (вариант fp32, 256 чанков)

CPU-развёртка идёт на fp32: `tf32`, `fp16` — механизмы cuda (`autocast`/`allow_tf32`), а
аппаратного bf16 у этого CPU нет (`/proc/cpuinfo`: `avx2`, без `avx512_bf16`), поэтому
«лучший по скорости вариант» на CPU — единственный исполнимый. Хост: 6 физических ядер /
12 потоков; `torch.get_num_threads()` по умолчанию **6** (физические ядра), строка
`threads=12` — намеренный oversubscription.

| потоки | батч | чанк/с | занято ядер (`cpu_ratio`) | пик RSS, MiB |
|---:|---:|---:|---:|---:|
| 1 | 32 | 0.179 | 1.01 | 3555 |
| 1 | 64 | 0.160 | 1.01 | 4326 |
| 1 | 128 | 0.142 | 1.01 | 5134 |
| 4 | 32 | 0.454 | 3.11 | 2649 |
| 4 | 64 | 0.394 | 3.06 | 3764 |
| 4 | 128 | 0.345 | 3.05 | 5227 |
| 8 | 32 | 0.618 | 7.08 | 2700 |
| 8 | 64 | 0.543 | 7.22 | 3816 |
| 8 | 128 | 0.466 | 7.29 | 5274 |
| 12 | 32 | **0.692** | 11.21 | 2803 |
| 12 | 64 | 0.614 | 10.87 | 3882 |
| 12 | 128 | 0.507 | 10.40 | 5331 |

Пик RSS включает веса модели (1.23 GB сразу после загрузки) и растёт с батчем: 32 → 128
даёт **+1.6…+2.5 GB** активаций; на 7 GB хоста батч 128 — это 5.1–5.3 GB процесса.
Клетки `threads=1` шли первыми и включают рост арены аллокатора, поэтому их RSS выше
соседних при том же батче (3555 против 2649 при батче 32) — это артефакт порядка, а не
свойство потока.

Что из этого следует по арифметике:

- **Потолок — физические ядра, а не объявленные потоки.** 12 потоков дают 0.692 чанк/с
  против 0.179 на одном — **3.87×**, тогда как `cpu_ratio` показывает **11.2 занятых
  ядер** (SMT-потоки считаются, но ускорения не дают). 4 потока — 2.54× (3.11 ядра),
  8 потоков — 3.45× (7.08 ядра): каждое удвоение потоков даёт 1.36–1.42×, а не 2×.
- **Батч на CPU вредит, а не помогает.** 12 потоков: 32 → 128 это 0.692 → 0.507 чанк/с
  (**−27 %**); на 1 потоке — 0.179 → 0.142 (−21 %). Причина видна в RSS: батч растит
  активации, а не параллелизм.
- **CPU против GPU (та же выборка, fp32):** 0.692 против 6.02 чанк/с = **8.7×**; против
  bf16 (16.15) — **23.3×**. Это арифметика двух замеров, не рекомендация: узкое место
  GPU-пути — не счёт, а троттлинг и батч 32.
- **Цена цикла на CPU:** 138 961 чанков `postgrespro` при 0.692 чанк/с — **55.7 ч**
  против 6.4 ч на GPU fp32.

`cpu_ratio` — это и есть ответ «одно ядро или больше»: `process_time` считает все потоки
процесса, поэтому отношение к `wall` показывает фактически занятые ядра (1.01 на
`threads=1`, 11.21 на `threads=12`), но занятое ядро ≠ полезное ускорение — SMT виден в
отношении и не виден в чанк/с.

## 5. Детерминизм

| проверка | результат |
|---|---|
| два замера внутри процесса, все 4 варианта (`det`) | **0.0** по компонентам |
| два запуска процесса (замер 1 против замера 2), матрицы 512×1024, все 4 варианта | **0.0** по компонентам |
| согласие `1−cos`/top-10 между запусками | совпало до последнего знака таблиц |

То есть fp32, tf32, bf16 и fp16 на этом стеке воспроизводимы побитово, и разброс скорости
между запусками — троттлинг карты, а не недетерминизм счёта.

## 6. Арифметика (без порогов)

- Скорость: bf16 быстрее fp32 в **2.6–3.1×** на первом замере (16.15 против 6.02;
  15.60 против 4.99), tf32 — в **1.26–1.39×**, fp16 — в **2.56–2.77×**.
- Цена одного цикла на этом срезе: 138 961 чанков `postgrespro` при 6.0 чанк/с — **6.4 ч**,
  при 5.0 — **7.7 ч**, при bf16 16.15 — **2.4 ч**. Это арифметика по измеренной скорости,
  не обещание: корпус шире выборки, а карта на длинном прогоне греется сильнее.
- Согласие: худший чанк bf16 отличается от fp32 на `1−cos` 7.5e-04; сколько это стоит в
  терминах вердиктов/ретривала, **этот замер не измеряет** — здесь нет golden и нет
  оценки качества поиска.
- VRAM: bf16 освобождает 328 MiB allocated (10 %), но веса остаются fp32; вариант с
  квантованными весами (не autocast) этим замером не покрыт.

## 7. Ограничения

- **Один хост, одна карта, один срез корпуса**: `postgrespro`, 512 чанков, средняя длина
  946 символов (корпус в целом — 920.5 по 138 961 чанку). Другие продукты и длины не
  мерились; стоимость линейна по длине текста, поэтому чанки короче/длиннее сдвинут
  чанк/с.
- **Троттлинг**: карта под `SW power cap`, 86 °C, частота 1057–1072 MHz из 2100. Числа
  скорости — нижняя граница для «холодной» карты; разброс между двумя запусками это
  показывает (fp32: 6.02 против 4.99).
- **`chunks_per_s` — не пропускная способность пайплайна**: замер идёт на прогретой
  модели и без конкуренции с краулом/экстракцией; продакшн-числа 2.8–5.7 чанк/с включают
  эту конкуренцию и первый батч.
- **Согласие векторов — не качество**: метрика говорит, насколько вектор сдвинулся, а не
  ухудшился ли retrieval. Для последнего нужен golden и отдельный замер.
- **CPU-развёртка — 256 чанков** (а не 512): батч 32 при 1 потоке — это ~8 замеренных
  батчей; больше текста стоило бы часа на одну клетку при том же ответе.
- **bf16 на CPU не мерился**: у CPU нет `avx512_bf16`, эмуляция показала бы не то железо,
  которого нет.
- **CPU-развёртка прогнана по одному разу на клетку**: детерминизм проверен на вариантах
  точности (там он побитовый), а не на каждой клетке CPU. Разброс между запусками на CPU
  не измерен; клетки шли последовательно, при простое GPU, но CPU грелся, поэтому числа
  CPU — один срез, а не среднее.
- **Разные продукты не мерились**: только `postgrespro`. Другие продукты того же прогона
  (`digital_q_database`, `pangolin`, `tantor`, `jatoba`) имеют близкую среднюю длину
  (850–912 символов), но это свойство корпуса, а не проверенный результат.

## Воспроизведение

```bash
# варианты точности (cuda) и развёртка CPU — раздельно, чтобы не делить карту
.venv/bin/python scripts/embed_bench.py \
  --db ~/.cohound/data/runs/ru-pg-dbms-208472049479/cohound.db \
  --product postgrespro --sample 512 \
  --variants fp32,tf32,bf16,fp16 --repeats 2 --variant-batch 32 \
  --mode precision --dump-vectors /tmp/embed_vectors_precision

.venv/bin/python scripts/embed_bench.py \
  --db ~/.cohound/data/runs/ru-pg-dbms-208472049479/cohound.db \
  --product postgrespro --sample 512 --cpu-sample 256 \
  --threads 1,4,8,12 --batch-sizes 32,64,128 --mode cpu
```

Перед запуском проверить `nvidia-smi` (0 MiB) и не запускать два замера одновременно:
`peak_vram`/`chunks_per_s` тогда описывают чужую нагрузку, а не вариант.

Сырые JSON этого замера — в каталоге `2026-11-06-embedding-precision-cpu/`
(`precision_run1.json`, `precision_run2.json`, `cpu.json`); матрицы векторов (.npy, 8 файлов
по 2 MB) не коммитятся — они воспроизводятся флагом `--dump-vectors`.
