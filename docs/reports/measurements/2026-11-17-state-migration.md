# Перенос `state.db` 12 → 13: дельта, цена и проверка результата

**Дата:** 17.11.2026. **Дерево:** `46b9148` + незакоммиченные полосы рабочего дерева.
**Файл замера:** копия `~/.cohound/stands/ru-pg-dbms/state/ru-pg-dbms/state.db`
(482 209 792 байт, объявляет `schema_meta.schema_version = '12'`), снятая в
`/tmp/opencode/state-migrate/`. **Оригинал не изменялся.**
**Инструмент:** `scripts/migrate_state.py` (stdlib + `core.store.state_sqlite` только на
чтение констант и на создание эталона в временном каталоге).

## 1. Вопрос

`state.db` пакета — durable-состояние, переживающее прогоны. Штатное открытие
(`connect_state`) файл другой версии **отвергает** и миграций при открытии не делает
(решение владельца 01.11.2026: тихий догон объявлял бы файл текущим, не будучи им).
Файл стенда объявляет **12**, код ждёт **13**, а в нём лежит то, что живым краулом
собирается часами и гигабайтами. Вопрос: **что именно переносится, сколько это стоит и
чем доказывается, что перенос получился**.

## 2. Дельта — измеренная, а не предполагаемая

Схема чистого v13 (`connect_state` во временном каталоге) сравнивалась с файлом стенда
структурно: набор объектов `sqlite_master`, `PRAGMA table_info`/`foreign_key_list` по
каждой таблице, `PRAGMA index_list`/`index_info` по каждому индексу, нормализованный
текст триггеров. Отличие **одно**:

| объект | в v12 | в v13 |
|---|---|---|
| `chunk_meta` | 11 колонок | 11 + `table_ref TEXT` |
| индексы / триггеры / прочие таблицы | — | без изменений (33 объекта, триггеров 0) |

Отсюда перенос = `ALTER TABLE chunk_meta ADD COLUMN table_ref TEXT` +
`schema_meta.schema_version = '13'`. Данные не конвертируются: `table_ref = NULL`
документирован в DDL как «адрес неизвестен» — законное значение, а не ложь. Старые наборы
кусков (`policy-5`, `md-heading-4`) прогон `policy-6` всё равно не переиспользует
(см. §3, «мёртвый вес»).

**Измеренная ловушка фикстуры.** `ALTER TABLE chunk_meta DROP COLUMN table_ref` на чистом
v13 в этом `.venv` (SQLite **3.50.4**) **не работает**: `error in table chunk_meta after
drop column: incomplete input`. Причина — переписывая объявление таблицы, SQLite оставляет
запятую после `char_end INTEGER,` перед блоком комментариев и закрывающей скобкой, а
висячая запятая в списке колонок недопустима. Поэтому тестовая фикстура v12 собирается из
текста `STATE_DDL` без объявления `table_ref` (это и есть определение v12 = v13 минус одна
колонка), а не из готового файла. На перенос это не влияет: `ADD COLUMN` текст объявления
не переписывает, а дописывает (проверено на файле стенда, §3).

## 4. Что именно проверяет сверка схемы

Проверка — не «DDL применился» (он идемпотентен, `IF NOT EXISTS`, и не заметит ни чужого
шима, ни недостающего индекса, ни колонки, объявленной иначе), а **структурное равенство
результата чистому v13**. Сравниваются:

1. набор `(type, name)` объектов `sqlite_master` без `sqlite_*` — обязан совпасть
   (лишний объект = чужой шим, отсутствующий = недоприменённая схема);
2. для каждой таблицы — `PRAGMA table_info`: `name`, `type`, `notnull`, `dflt_value`,
   `pk`, **и порядок** (при совпадающем составе);
3. для каждой таблицы — `PRAGMA foreign_key_list`: ссылка, колонки, `ON UPDATE`/
   `ON DELETE`/`MATCH`;
4. для каждого индекса — `PRAGMA index_list` + `PRAGMA index_info`: уникальность,
   происхождение (`c`/`u`/`pk`), частичность, состав; авто-индексы (`sqlite_autoindex_*`)
   входят сюда же, хотя в `sqlite_master` их нет;
5. триггеры — нормализованный текст (пробельные серии схлопнуты) + `tbl_name`
   (в `state.db` триггеров 0, поэтому этот пункт на данном файле вакуумный — и это
   сказано, а не замаскировано);
6. `PRAGMA integrity_check` = `["ok"]`;
7. `PRAGMA foreign_key_check` пуст;
8. число строк **в каждой** таблице до и после совпадает;
9. `chunk_meta.table_ref IS NOT NULL` = 0;
10. `schema_meta.schema_version` = `'13'`.

Текст SQL не сравнивается намеренно: перенесённая таблица приходит из `ALTER TABLE`, и её
объявление в `sqlite_master` законно отличается от `CREATE TABLE` в `STATE_DDL` — сравнивать
строки значило бы ловить форматирование вместо структуры. Обе стороны (дельта в
`--dry-run` и проверка после переноса) считаются **одной** функцией
(`compare_signatures`) — второго сравнения нет, чтобы они не разошлись на первой правке.

## 5. Границы

* Замер сделан на **копии** файла стенда на этом хосте; оригинал не тронут. Значения
  длительности — цена этого хоста на этом файле, а не свойство продукта.
* Инструмент знает **одну** пару (`12 → 13`). Если код уйдёт вперёд, он откажет, а не
  перенесёт в промежуточную версию (`TARGET_VERSION != "13"` → код 2).
* Перенос не проверяет **смысл** данных: он не сверяет `chunk_ids_digest` документов с
  содержимым `chunk_meta` и не подтверждает, что `url_state` соответствует последнему
  прогону. Это не его предмет: он переносит носитель, а не пересчитывает корпус.
* Непустой `-wal` рядом с файлом — отказ (подмена основного файла под живым писателем —
  единственный способ потерять данные). На файле стенда `-wal` был 0 байт, поэтому отказ
  не сработал; сама ветка проверена тестом `test_non_empty_wal_blocks_the_swap`.

## 6. Воспроизведение

```bash
cp -a ~/.cohound/stands/ru-pg-dbms/state/ru-pg-dbms/state.db* /tmp/opencode/state-migrate/
.venv/bin/python scripts/migrate_state.py --db /tmp/opencode/state-migrate/state.db            # dry-run
.venv/bin/python scripts/migrate_state.py --db /tmp/opencode/state-migrate/state.db --apply
```

Тесты (фикстуры строятся кодом, сеть не нужна):
`.venv/bin/python -m pytest -q tests/scripts/test_migrate_state.py`.
