# Markdown-чанкер: политика `md-heading-5` на реальном корпусе

**Дата:** 03.11.2026. **Класс:** `execution_change` (`chunker_version` в
`EXECUTION_CONTRACT_FIELDS`). **Срез:** план `docs/architecture/18-markdown-chunker-plan.md`,
L1b-1. **Корпус:** `ru-pg-dbms-1e0b04d6d83a` (БД читается только на чтение).

## Что мерилось

Замена построчного автомата (`md-heading-4`) на нарезку по AST (`md-heading-5`) меняет
chunk-set, поэтому приёмка — не «стало красивее», а числа на одном и том же корпусе:

```bash
# единый инструмент приёмки: инварианты P1/P4/P8/P13 + геометрия
python3 scripts/measure_md_chunking.py --db ~/.cohound/data/runs/{run_id}/cohound.db \
    --limit 400 --chunk-size 1500 --out-json /tmp/md-chunk.json
```

2 379 документов (23 482 505 символов, 10 хостов когорты) прошли одинаковый путь:
retained-байты → `HtmlExtractor` → чанкер. Старый чанкер взят из `git show
HEAD:core/adapters/chunker_markdown.py` и прогнан на тех же текстах.

## До/после на одном корпусе

| величина | `md-heading-4` | `md-heading-5` |
|---|---|---|
| чанков | 29 407 | **26 473** (0.90×) |
| символов в чанках / вход | 104.99 % | **100.00 %** |
| чанк начинается строкой таблицы без шапки | 1 190 | **0** |
| `context_prefix` ≠ `heading_path` | 0 | **3 025** (11.4 %) |
| p50 / p90 / p99 длины чанка | 1011 / 1481 / 1498 | 1011 / 1476 / 1499 |
| максимум | 1500 | 1510 |
| чанков короче 20 символов | 0 (отброшены) | **324** (1.2 %) |

Три числа требуют объяснения, потому что читаются как регресс, а регрессом не являются.

**104.99 % → 100.00 %.** Старый чанкер `strip()`-ил текст и резал с перекрытием 200
символов: сумма текстов чанков была больше входа за счёт дублей, а строка заголовка из
`text` терялась. Теперь каждый `chunk.text` — точный срез, `"".join(chunk.text)` равен
нормализованному входу (P1). Это и есть причина, по которой I22 («цитата — подстрока
текста») перестаёт зависеть от терпимости сверки.

**1 190 → 0 табличных чанков без шапки.** Продолжение таблицы получает в `context_prefix`
шапку с разделителем и выравниванием (P9): `| id | смысл |` + `|:--|--:|`. Проверка на
корпусе: из 1 403 чанков, начинающихся со строки таблицы, шапку несут 1 144; остальные
259 — не таблицы вовсе (в тексте есть `|`, но разделителя нет: так выглядят абзацы
документации PostgreSQL с экранированными трубами). Прежние 1 190 — это и были настоящие
продолжения таблиц, начинавшиеся с безымянных строк.

**0 → 324 чанка короче 20 символов.** Порог фрагмента раньше **выбрасывал** такой текст;
P1 этого не допускает. Порог теперь работает иначе: хвост разреза приклеивается к
предыдущему куску той же секции, а самостоятельно объявленная единица документа
(однострочная секция) остаётся чанком. Число публикуется, а не прячется: 1.2 % чанков —
это цена того, что из корпуса больше не пропадает текст. Если окажется, что они мешают
ретривалу, это будет измерено отдельно (отсев — слой L2.5 плана, не порог).

## Инварианты

| инвариант | нарушений |
|---|---|
| P1 — конкатенация чанков ≠ вход | **0** |
| P4 — `chunk.text` не подстрока входа | **0** |
| P8 — чанк начинается с пунктуации **из-за реза** (проза) | **0** |
| P13 — строки вне блоков (`unknown_construct`) | **0** |

У P8 два источника, и они разделены после замера 03.11: на том же срезе 9 чанков
начинаются со знака **потому что так начинается абзац источника** (`<p>. Согласно
стандарту…</p>`, `?column?` в заголовке). По P1 чанкер не имеет права сдвинуть этот
символ, поэтому такие случаи считаются отдельно (`source_punct`), а не как нарушение.
Метрика, которая их смешивала, показывала бы дефект там, где чинить нечего.

P8 сначала показал 5 «нарушений»; все пять — строки SQL внутри fence (`} spgChooseResultType;`).
Разрез внутри кода начинается с `)`/`}` законно, поэтому метрика считает прозу, а не код;
после разделения — 0. Второе уточнение (03.11) — то же самое, но с другой стороны: знак,
стоящий в начале блока источника, не является следствием реза и считается отдельно
(`source_punct` = 9).

**Повторный замер после выноса границ в `core/util/text_utils.py`.** Правила разреза
(`SENTENCE_END_CHARS`, `CLOSING_CHARS`, `is_cut_boundary`) стали общими для markdown- и
абзацного чанкера и пополнились западными `,.!?;:`. Числа воспроизведены на том же срезе
без изменений: 2 379 документов, 26 473 чанка, P1/P4/P8(рез)/P13 = 0, 324 чанка короче
порога, 4 длиннее бюджета, 43 из 606 резов внутри абзаца. Это и есть проверка, что перенос
правил не изменил нарезку, — иначе новый `run_id` описывал бы не тот корпус.

## Геометрия

| величина | значение |
|---|---|
| чанков длиннее бюджета | 4 (0.015 %) — приклеенный хвост, не больше 1510 символов |
| чанков без `heading_path` | 1 639 (6.2 %) — документы без заголовков и текст до первого |
| чанков с контекстом продолжения | 3 025 (11.4 %) |
| резы внутри абзаца, оборвавшие предложение | **43 из 606** (7.1 %) |

Строка про обрыв предложения — единственная, которая мерилась дважды. Сначала выбор
разреза шёл «самый крупный, помещающийся в бюджет», и 459 из 595 резов внутри абзаца
(77 %) кончались посреди фразы. Добавленное предпочтение конца предложения (`。！？;` — тоже,
иначе CJK-абзац режется по любому пробелу) снизило это до 43 из 606 (7.1 %). Остаток —
абзацы, у которых во второй половине окна нет ни одного конца предложения (длинная фраза,
перечисление через запятую): там выбор только между пробелами.

Таблица в §3 плана не включает предложение как минимальную единицу, поэтому 7.1 % — не
нарушение инварианта, а измеренная цена бюджета 1500. Меряется она потому, что обрыв
фразы — единственный дефект нарезки, который видит оценщик, а не только индекс.

## Кросс-язык

Синтетика с одинаковой структурой (200 предложений под одним заголовком, бюджет 1500):

| язык | чанков | обрывов предложения |
|---|---|---|
| RU | 6 | 0 |
| EN | 6 | 0 |
| ZH | 3 | 0 |

До правки китайский абзац без пробелов резался жёстко по номеру символа: замер на 2 000
иероглифов давал чанк, кончавшийся «…会失败并且», и следующий, начинавшийся «需要回滚。».
Теперь рез идёт по `。` (знаки конца предложения включают полноширинные формы).

## Чего эти числа не показывают

- **Качество ретривала.** Изменился chunk-set — сравнение recall/MRR требует новой
  индексной сборки (`hound experiment retrieval`), она появится после прогона.
- **Стоимость эмбеддинга.** Чанков стало на 10 % меньше, но токенов на чанк больше
  (в чанк входит строка заголовка); фактическая стоимость — из журнала прогона.
- **κ оценщика и `fabricated_support`.** Меняется вход оценщика (`context_prefix` теперь
  доходит до промпта только после L1b-2), это отдельный замер.
- **Бюджет в токенах.** Здесь всё в символах; токенизатор эмбеддера — L4 плана.
- **Абзацный чанкер на живом CJK.** `text-para-3` понимает `。！？；` и клаузы `，、：`,
  но корпус когорты — RU/EN: проверено только синтетикой (710 иероглифов без пробелов →
  4 чанка, все кончаются терминатором). Настоящий CJK-корпус — отдельный замер.

## Воспроизведение

```bash
git show HEAD:core/adapters/chunker_markdown.py > /tmp/old_chunker_markdown.py  # до L1b-1
python3 scripts/measure_md_chunking.py --db ~/.cohound/data/runs/{run_id}/cohound.db --limit 400
```

Инструмент не пишет в БД, не ходит в сеть и не меняет `core/`; `--out-json` даёт машинный
отчёт для сверки чисел в этом документе.
