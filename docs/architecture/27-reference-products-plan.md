# 27. Reference-продукты профиля: разведка, факты, карта и обновление по версиям

**Статус:** план (14.11.2026, ред. 2). Не реализовано.

Решения владельца, на которых держится весь документ:

1. baseline-продукты — **часть профиля**, но **не часть когорты**;
2. профиль обязан знать не только актуальную версию reference-продукта, но и **историю
   мажорных версий**; список версий объявляется профилем **явно** (14.11.2026);
3. reference-продукты **по умолчанию не входят** в результаты сравнения когорты — только
   по отдельному запросу;
4. `absent` в документации upstream — **наблюдение**, а не утверждение об отсутствии
   функции; `❌` из него не следует и оценку продукта он не подавляет (14.11.2026);
5. план рассчитан на **оба архетипа — A и B** (14.11.2026): несколько reference-продуктов,
   матрица «параметр × базлайн», наследование от нескольких предков;
6. полная **карта reference-продукта** (`Capability`/`Coverage`) нужна **сразу**, не
   откладывается (14.11.2026);
7. обратная совместимость не требуется: формат, схема БД и раскладка переделываются
   свободно.

---

## 1. Что строится

Четыре вещи, и все четыре — про одно: превратить наследование из **предположения** об
upstream-факте в **измерение** с датой, цитатой и хешем.

| | что | носитель |
|---|---|---|
| **Декларация** | какие reference-продукты у профиля, какие у них версии и корни документации | `sources/reference_products.yaml` (git) |
| **Измерение** | факт «параметр P в версии V описан здесь» — дословная цитата + хеш текста | `sources/baseline_facts.csv` (git, вход прогона) |
| **Карта** | `Capability`/`Coverage` reference-продукта по каталогу профиля | `reference/{pkg}/{product}/{version}/maps/{map_id}/` (данные хоста) |
| **Корпус** | чанки документации версии, из которых берутся цитаты | `reference/{pkg}/{product}/{version}/reference.db` (данные хоста) |

**Что НЕ строится:** ничего. Раньше здесь стояла отложенная карта — владелец её вернул в
объём (решение 6). Единственное, что остаётся вне объёма, — эмбеддинги reference-корпуса
(§12): BM25 решает задачу, а векторы добавили бы recall-зависимость в провенанс факта.

### 1.1. Ключевое свойство: наследование — ускоритель, а не ворота

Нет факта, факт `pending`/`rejected`/`absent` — **ячейка не наследуется, и параметр
оценивается обычным путём** (Ш5/Ш6 по корпусу продукта). Ни `❓`, ни `❌` из этого не
следует: отсутствие ускорения — не наблюдение о продукте.

Отсюда риск подсистемы ограничен: худшее, что даёт неверный факт, — лишняя работа и
неверная провенанс-запись, а не пропущенная ячейка. Поэтому факты вводятся постепенно,
не блокируя прогоны.

## 3. Модель

### 3.1. Декларация reference-продуктов

```yaml
# packages/{case_id}/sources/reference_products.yaml   (schema reference_products/1)
schema: reference_products/1
products:
  - baseline_id: upstream-pg            # связь с baselines.csv и passport.upstreams
    product_id: postgresql              # slug reference-продукта (namespace общий с когортой)
    canonical_name: PostgreSQL
    versions:                           # объявляется явно (решение 2), не «все подряд»
      - version: "11"
        docs_roots: ["https://www.postgresql.org/docs/11/"]
      - version: "18"
        docs_roots: ["https://www.postgresql.org/docs/18/"]
    current_version: "18"               # версия, по которой строится карта и наследование
  - baseline_id: upstream-mysql
    product_id: mysql
    canonical_name: MySQL
    versions:
      - version: "8.4"
        docs_roots: ["https://dev.mysql.com/doc/refman/8.4/en/"]
    current_version: "8.4"
```

**Нет поля `kind: upstream | sibling`** — и это осознанно. В архетипе A «предок/параллель»
совпадает для всех продуктов, в B — **нет**: MySQL будет предком для продукта X и
параллелью для продукта Y. Отношение принадлежит паре «продукт × reference», а не
reference-продукту, и живёт в паспорте продукта (`upstreams`, §3.4). `hound baseline list`
**вычисляет** роль и публикует её:

```
upstream-pg   postgresql  ancestor of: postgrespro, digital_q_database, jatoba, tantor
upstream-mysql mysql      parallel (ни один продукт когорты не объявляет его предком)
```

Вычисленная роль, а не объявленная: два источника одного факта разошлись бы (A3).

`product_id` reference-продукта **не пересекается** с `product_id` когорты — линтер
проверяет. Namespace общий намеренно: два смысла одного slug'а в одном пакете — источник
молчаливых ошибок.

### 3.2. Несколько предков у продукта (архетип B)

`Passport.upstream: Upstream | None` → **`Passport.upstreams: list[Upstream]`**.
**Порядок списка — объявленный приоритет**, а не порядок вставки:

```yaml
# passports/{product_id}/{date}.yaml
upstreams:
  - baseline_id: upstream-fork      # ближайший предок — расширение/форк
    version: "2.1"
    evidence: {url: "…", quote: "…"}
  - baseline_id: upstream-pg        # линия, на которой стоит форк
    version: "18"
    evidence: {url: "…", quote: "…"}
```

Правило разрешения (одно, детерминированное, без тай-брейка по часам/вставке):

> Для параметра P перебираются `upstreams` **в объявленном порядке**. Наследует **первый**,
> у которого есть строка `baselines.csv` **и** принятый факт `present` на его версии.
> Если ни один не даёт — наследования нет, и причины **всех** предков публикуются.

Это и есть «матрица параметр × базлайн» из §1.5 регламента: строки `baselines.csv` уже
ключуются `(baseline_id, param_id)`, менять формат не нужно.

Проседание к следующему предку **разрешено и правильно**: если форк параметр не описывает,
а PostgreSQL описывает, то возможность пришла из PostgreSQL — продукт объявил обе линии.
Опасность была бы в обратном — объявить чужую линию, — и это авторское решение, которое
проверяется не кодом, а публикацией: базис показывает, **от какого предка** унаследован
каждый параметр.

**Архетип A** — частный случай: список из одного элемента. Линтер требует ровно один
`upstreams` для A и ≥1 для B; архетип C не заполняет `baselines.csv` (существующее правило
`lint.py:147`).

`PackageManifest.baseline_participant: str | None` → **`baseline_participants: list[str]`**:
в B базлайн-участников несколько (по одному на линию), и одно поле их не выражает.
У архетипа C — пустой список (прежнее `None`).

### 3.3. Факт

```csv
# packages/{case_id}/sources/baseline_facts.csv   (форма baseline_facts/1)
baseline_id,param_id,version,status,url,quote,content_hash,observed_at,corpus_build_id,review,reviewed_by,note
upstream-pg,pg_json_type,18,present,https://www.postgresql.org/docs/18/datatype-json.html,"…jsonb…",sha256:…,2026-11-14T09:12:00Z,ref_pg_18_a1b2c3d4,accepted,roger,
```

* `status` — `present` | `absent` | `unclear`. Не `Status` ячейки: это наблюдение о
  документации, а не вердикт о продукте (решение 4). `absent` — «в документации этой
  версии параметр не описан»; `❌` из него не следует и оценку продукта он не подавляет.
* `quote` — **дословная** подстрока текста чанка (проверка как I22: `quote ∈ chunk.text`).
* `content_hash` — `content_hash` того чанка (I19: хеш текста, не URL).
* `review` — `pending` | `accepted` | `rejected`. **Наследует только `accepted`.**

### 3.4. Разделение «политика / наблюдение»

`baselines.csv` — **политика**: что наследуем, в каком режиме, с каким полом версии
(авторское решение). `baseline_facts.csv` — **наблюдение**: что у upstream есть в версии V
(замер с датой и цитатой). Разные носители, потому что разные сроки жизни и разные
владельцы: политику пишет автор профиля, наблюдение — прибор плюс подпись человека.

Следствие: `min_version` может быть **выведен** из фактов, но никогда не пишется туда
автоматически (§9).

## 4. Раскладка

```
packages/{case_id}/sources/
  reference_products.yaml              # декларация (git)
  baseline_facts.csv                   # объявленный вход прогона (git, ~300 КБ на 181×8)
  reference/{product_id}/{version}/corpus_urls.yaml    # корни документации (git)
```

Корпус и карта — **данные хоста**:

```
COHOUND_HOME/reference/{package_id}/{product_id}/{version}/
  current.json                    # указатель на «текущую» сборку (атомарная запись)
  .lock                           # один писатель на (пакет, продукт, версия)
  raw/{sha256}.bin                # retained-байты, общие для сборок версии (I19)
  builds/{build_id}/
    reference.db                  # corpus_docs + corpus_chunks (та же схема, отдельная БД)
    manifest.json                 # build_id, версии, content_digest, объёмы, провенанс прохода
    maps/{map_id}/                # карта: cells.jsonl + score.json + manifest.json
```

Свойства:
* **иммутабельно**, как `index_store/{package}/{build}/{product}`: новая сборка — новый
  `build_id`, правка на месте запрещена;
* `build_id = ref_{product}_{version}_{hash(content_digest)[:8]}`;
* раскладка **per-build** (17.11.2026): две сборки одной версии сосуществуют, а не
  перезаписывают друг друга. Пока `reference.db` лежал прямо в каталоге версии,
  «пересобрали» означало «стёрли прежнее» — вместе с доказательством того, что читалось
  раньше. Байты при этом **общие** (`raw/`): retention content-addressed, поэтому
  сосуществование сборок диска не удваивает;
* выбор сборки — `current.json` > единственная > отказ (`resolve_build`), **никогда** по
  `mtime`: порядок записи на диск не является ни объявленным входом, ни наблюдением;
* `manifest.json` публикует и провенанс прохода (`complete`/`incomplete_reasons`/
  `skipped`/`errors`/`roots`): `absent` в фактах допустим только при `complete=true`
  (§8.3, I2/I2c). Провенанс в `build_id` **не** входит — он функция содержимого;
* **не в `runs/`**: reference-корпус живёт дольше прогона (документация PostgreSQL 11 не
  меняется никогда) и переиспользуется между циклами;
* карта — **отдельная сборка** внутри версии: смена модели/промпта меняет карту, но не
  корпус, поэтому `maps/{map_id}/` адресуется своим `map_id` (§7.3).

## 5. CLI

Группа `hound baseline`, отдельно от `hound package` (там — авторские CRUD над пакетом;
здесь — измерение).

```bash
# сборка reference-корпуса версии (корни — из декларации, не из --urls)
hound baseline build --package {case_id} --baseline upstream-pg [--version 18] \
  [--max-documents N] [--max-depth N] [--rate-limit 0.5] [--exclude-path GLOB] \
  [--document-level full] [--pdf-pipeline structured] [--dry-run] [--json]

# что объявлено и в каком состоянии: роль предка, состояние корпуса, следующая команда
hound baseline list --package {case_id} [--json]

# разведка: факты по каталогу из выбранной сборки (лексический индекс, без LLM)
hound baseline recon --package {case_id} --baseline upstream-pg \
  [--version 18] [--build {build_id}] [--param pg_json_type] [--dry-run] [--json]

# карта reference-продукта: Capability/Coverage по каталогу профиля
hound baseline map --package {case_id} --baseline upstream-pg [--version 18] \
  [--build {build_id}] [--dry-run] [--json]

# факты с фильтрами (read-only)
hound baseline facts --package {case_id} [--baseline …] [--version …] [--param …] \
  [--review pending] [--json]

# человеческая корректировка
hound baseline review --package {case_id} --baseline upstream-pg \
  --param pg_json_type --version 18 --accept|--reject --actor {кто} [--note "…"]
hound baseline review --package {case_id} --baseline upstream-pg \
  --version 18 --accept-all --actor {кто} [--dry-run]

# новая мажорная версия: перемер + diff, без записи
hound baseline refresh --package {case_id} --baseline upstream-pg --version 19 [--apply]

# что унаследовано и кем; карта — рядом, но отдельно
hound baseline report --package {case_id} [--baseline …] [--with-map] [--json]
```

Правила: `--actor` обязателен для любой записи; `--dry-run` ничего не пишет и **говорит**,
что записал бы; запись идёт через `.authoring/apply_log.jsonl` (существующий контур I1);
ни одна подкоманда не пишет в `runs/` и не трогает прогон.

**Порядок — цепочка, а не набор команд**: `build` → `recon` → `review` → `report` → `map`.
Каждая команда, которой не хватает предыдущего шага, отказывает **и называет его**; `list`
печатает для продукта ту же следующую команду. Оси сборки — объявленный вход: `--max-depth`
по умолчанию не ограничена (граница — path-prefix объявленного корня), `--max-documents`
без потолка, а объём и полнота прохода публикуются в манифесте сборки и в сводке `build`.

Две вещи, которых в первой редакции этого раздела не было и без которых цепочка не
работала:

* **порядок работы — цепочка**, и каждая команда называет следующую:
  `build` → `recon` → `review` → `report` → `map`. Корпус не появлялся ниоткуда: `recon`
  умел только читать `reference.db` и отказывал, если файла нет, — производителя не было.
  `build` берёт корни **из декларации** (`versions[].docs_roots`), а не из `--urls`:
  декларация — единственный источник, иначе корпус описывал бы не объявленную версию;
* **сборка выбирается явно** (`--build`) либо раскладкой (`current.json` > единственная >
  отказ с перечнем). `--corpus-db` остаётся аварийным входом для чужого файла.

## 6. Волна Ш4: что меняется

### 6.1. Сегодня

```
для продукта P с passport.upstream = {baseline_id: B, version: V}:
  для строки row из baselines.csv, где row.baseline_id == B:
    direct: если V >= row.min_version → ячейка с evidence из passport.upstream.evidence
```

Одна цитата (`_derived_evidence`, `inheritance.py:152`) обслуживает все параметры. У
`postgrespro` это «Российская СУБД корпоративного уровня на базе PostgreSQL с расширенной
функциональностью». Формально I1/I8 проходят; содержательно `support_not_about_subject`
(`inheritance.py:194`) почти на всех.

### 6.2. Станет

```
для продукта P с passport.upstreams = [(B1,V1), (B2,V2), …]   # объявленный порядок
  для параметра row из плана:
    for (B, V) in upstreams:
      policy = baselines[(B, row.param_id)]         # может не быть
      if policy is None: continue                   # эта линия параметр не объявляет
      if policy.mode is BLOCKED: continue
      if policy.mode is CONDITIONAL: → pending-кандидат, дальше не идём
      if not V >= policy.min_version: причина `below_min_version`; continue
      fact = facts[(B, row.param_id, major(V))]
      if fact is None:           причина `baseline_fact_missing`;        continue
      if fact.review != ACCEPTED: причина `baseline_fact_{review}`;       continue
      if fact.status != PRESENT:  причина `baseline_fact_{status}`;       continue
      → ячейка с evidence из факта; break          # первый давший — победил
```

Три исхода «не наследовали» публикуются **по продукту и параметру** в `inheritance_basis`
(расширение существующего отчёта, не новый носитель), с указанием **предка**, который был
рассмотрен. Это важно: «объявлено 181, выпущено 140» без причин читается как дефект
конвейера, а не как «41 факт ещё не разведан».

### 6.3. Evidence из факта

```python
CellEvidence(
    source_kind=SourceKind.INHERITANCE,
    evidence_type=EvidenceType.DERIVED,
    source_id=f"upstream://{baseline_id}#{param_id}@{version}",   # версия в адресе
    source_url=fact.url,
    citation_quote=fact.quote,          # I22: непустая и дословная
    content_hash=fact.content_hash,     # I19: хеш текста чанка
)
```

`@version` — не косметика: один параметр в v11 и v18 — два разных факта, и адрес обязан
их различать (I15: детерминированный lookup).

### 6.4. Фолбэк на паспортную цитату убирается

`direct` без reference-продукта **не производится**. Линтер блокирует пакет, где
`baselines.csv` непуст, а `reference_products.yaml` не объявляет нужный `baseline_id`:

```
baseline-without-reference-product: строка (upstream-pg, pg_json_type) наследует от
baseline_id 'upstream-pg', но reference-продукт для него не объявлен (§27.6.4)
```

Осознанно жёстко: фолбэк на одну цитату — тот способ, которым 181 ✅ превращаются в
фикцию. Пустой `baselines.csv` (`ru-pg-dbms` сегодня) правило не задевает.

## 7. Идентичность и версии

### 7.1. Два новых поля контракта

`EXECUTION_CONTRACT_FIELDS`: 32 → **34**.

| поле | материал дайджеста | почему в контракте |
|---|---|---|
| `baselines_digest` | отсортированные `(baseline_id, param_id, min_version, mode)` | **дефект сегодня**: правка `baselines.csv` меняет вердикты под тем же `run_id` |
| `baseline_facts_digest` | отсортированные `(baseline_id, param_id, version, status, review, sha256(quote))` | определяет, какие ячейки наследуются |

Не входят (провенанс, не измерение): `observed_at`, `corpus_build_id`, `reviewed_by`,
`note`, `url`. `url` исключён намеренно: переезд документации при том же тексте вердикт не
меняет, а `content_hash` уже фиксирует текст. `review` **входит**: снятие `accepted`
меняет набор унаследованных ячеек.

Порядок `upstreams` входит в `passports_digest` автоматически (дайджест считается по
байтам паспорта, `digests.py:420`) — отдельного поля не нужно, но **перестановка предков
даёт новый `run_id`**, и это правильно: она меняет, кто из них победит.

Оба новых поля — `execution_change`. Разово и явно, не «под капотом».

### 7.2. Версии

* `upstream.version` приводится к **мажорной**: `"18.4.1"` → `18`. Нечисловая версия —
  **линт-ошибка**, не «пропустим».
* Факт ищется **ровно на объявленной версии**, не «где-нибудь ≤ V»: если в v18 параметр
  исчез, а в v17 был, наследовать нельзя — это регрессия upstream, и она должна быть
  видна.
* `min_version` — **пол применимости строки**, а не диапазон поиска. Семантика не меняется.

### 7.3. Идентичность карты

Карта — измерение, и у неё своя идентичность, **не** `run_id` когорты:

```
map_id = short_hash({
  reference_build_id,            # какие чанки
  baseline_facts_digest,         # какие факты (карта и факты обязаны быть про одно)
  catalog_version,               # какой каталог (181 параметр)
  llm_scenarios,                 # модель + версия (I21)
  prompt_template, evaluation_policy,
})
```

Почему не `run_id`: у карты нет когорты, сидов, паспортов когорты и покрытия продуктов —
она описывает **один** reference-продукт. `run_id` заставил бы её тащить весь контракт
прогона и создал бы ложное впечатление, что она часть цикла. `map_id` — честная
content-addressed идентичность сборки, как `partition_build_id` у `pb`.

## 8. Разведка: поток и граница LLM

### 8.1. Шаги

```
1. Декларация      reference_products.yaml (versions[].docs_roots) — автор
2. Краул           те же краулер/SSRF/robots/scope, что у продукта, но корни — свои
3. Экстракция      тот же extractor_factory(level, pdf_pipeline) — объявленный, не дефолт
4. Чанкинг         тот же чанкер (chunker_version в manifest.json)
5. Лексический     in-process BM25 по чанкам (LexicalSearcherPort); векторы НЕ нужны (§8.4)
6. Кандидаты       для каждого param_id каталога: запрос из title + rule + concept_terms,
                   top_k=RECON_TOP_K кандидатов от индекса
7. Отбор цитаты    (a) детерминированно: первый кандидат, из которого select_quote берёт
                   дословную цитату;
                   (b) опционально LLM — выбрать чанк и вернуть дословную цитату
8. Проверка        quote ∈ chunk.text (как I22); иначе факт = unclear + причина
9. Запись          baseline_facts.csv со status=pending, review=pending
10. Карта          (--map) оценка по чанкам тем же evaluate → Capability/Coverage
11. Человек        hound baseline review --accept|--reject
```

Шаги 1–5 исполняет `hound baseline build`, шаги 5–9 — `hound baseline recon`; до 17.11.2026
шагов 1–5 не было вовсе (корпус мог появиться только руками). Шаг 6–7 — **не** линейный
проход по корпусу: замена измерена (`docs/reports/measurements/2026-11-17-recon-top-k.md`):
исход совпадает уже при `K=2`, а главное — линейный проход на корпусе пилота цитировал
**6** различных чанков на 181 факт (один чанк дал 152 цитаты), индекс — **165**.

### 8.2. Граница LLM — та же асимметрия, что у разведки

LLM в шагах 7 и 10 — **разведочный** контур: он выбирает, *что* цитировать, и оценивает
карту, но не выносит вердикт о продукте когорты. Поэтому:

* модель читается из `COHOUND_LLM_*`/слота, как у `package scout` (args > env > slot), и
  **не** входит в `run_id` когорты — намеренная асимметрия AGENTS §8. В `map_id` она
  **входит** (§7.3): карта без модели — не измерение;
* выход шага 7 — кандидат с `review=pending`; цитата проверяется механически;
* без LLM шаги 1–9 работают (детерминированный отбор), карта — нет;
* LLM **никогда** не пишет `status=present` без цитаты: нет цитаты → `unclear`.

### 8.3. Что считается `present`

`present` = в документации объявленной версии есть место, дословно описывающее параметр, и
это место цитируется. Это **не** утверждение «функция работает» — ровно как у
`direct`-наследования по регламенту («переносит возможность проверить применимость»).

`absent` = проход по корпусу версии не нашёл такого места **и** охват корпуса полный
(иначе `unclear` — та же дисциплина, что I2/I2c: неполнота не даёт отсутствия).

### 8.4. Почему факты без векторов

Задача факта — «найти в документации одного продукта одной версии место про параметр P».
BM25 по корпусу ~1–2 тыс. страниц на версию. Векторы дали бы приблизительный recall,
зависящий от сборки, — то есть ровно то, чего не должно быть в провенансе факта.

Карта (§9) — другой предмет: там LLM читает те же чанки, и вопрос «нашли ли» решается
оценщиком, а не близостью векторов.

### 8.5. Цена (экстраполяция от измеренного)

Краул: замеренный темп **1207 док / 209 с = 5.78 req/s** (`docs.tantorlabs.ru`,
07.11.2026). Документация PostgreSQL — порядка 800–1200 страниц на мажорную версию;
8 версий ≈ 7–10 тыс. страниц ≈ **20–30 мин** краула одноразово, плюс HTML-экстракция
(дешёвая: HTML — не PDF). Это экстраполяция: фактический объём версий не считался.

Карта: замеренный темп оценщика **4.2 с/ячейку** при `--llm-concurrency 4` (905 ячеек,
08.11.2026). 181 параметр ≈ **13 мин** на версию на reference-продукт. Для 3 продуктов ×
8 версий ≈ 4 344 ячейки ≈ **5 часов** — и это только если карты нужны по всем версиям.
По умолчанию карта строится для `current_version` (§5): 3 продукта ≈ 40 мин.

## 9. Карта reference-продукта

### 9.1. Что это

`Capability` и `Coverage` reference-продукта по **каталогу профиля** — то есть ответ на
вопрос «какую долю наших 181 параметров PostgreSQL покрывает и насколько уверенно».
Считается тем же кодом, что у продуктов когорты (`_compute_from_cells`,
`compute.py:268`), по ячейкам, полученным оценщиком на reference-корпусе.

### 9.2. Что она НЕ делает

* **не входит в сравнение когорты**: артефакт лежит в `reference/…/maps/`, а не в
  `runs/{run_id}/outputs/`; отчёт когорты его не читает;
* **не смешивается** с Capability продуктов: разные носители, разные идентичности
  (`map_id` против `run_id`);
* **не даёт `❌` продуктам когорты**: карта — про документацию предка, а не про продукты.

Сторож — тест: отчёт когорты не содержит `product_id` reference-продукта; линтер
запрещает пересечение namespace (§10).

### 9.3. Зачем она нужна сразу (решение 6)

Три вещи, которые без неё не измерить:

1. **Цена покрытия**: «PG покрывает 150 из 181» — это число, которое объясняет, почему
   наследование вообще окупается. Без карты профиль не знает, сколько ячеек можно
   унаследовать, пока не разметит все факты.
2. **Качество дешёвого пути**: факты (`present/absent`) строятся детерминированно, карта —
   оценщиком. Их **расхождение** и есть замер: насколько BM25-путь согласован с
   полноценной оценкой. Публикуется как agreement (κ) между `fact.status` и вердиктом
   карты по тем же параметрам. Если согласие высокое — дешёвый путь обоснован; если
   низкое — это видно числом, а не мнением.
3. **Основание для `min_version`**: «параметр появился в v13» подтверждается картой по
   версиям, а не догадкой.

### 9.4. Форма артефакта

```
maps/{map_id}/
  manifest.json   # map_id, reference_build_id, catalog_version, llm_scenarios,
                  # prompt_template, evaluation_policy, версия, counts
  cells.jsonl     # по параметру: status, evidence (цитата+хеш), validation_notes
  score.json      # Capability, Coverage, module_scores, failure_rate, причины неизвестности
```

`score.json` — та же форма, что `ScoreBundle` когорты (`compute.py`), с добавленным
`subject: reference`. Один формат на два предмета: читатель не учит второй.

### 9.5. Согласие «факты ↔ карта»

Обязательная публикация в `hound baseline report --with-map`:

```
параметров: 181   фактов accepted: 140   карта: 137 (present 120 / absent 12 / unclear 5)
согласие факт↔карта: κ = 0.83 (n=137); расхождений 23 (факт present, карта ❌: 18)
```

Расхождения — не дефект, а **измерение прибора**: факт ищет место, карта решает, доказан
ли параметр. Разница между ними — цена дешёвого пути, и она называется числом.

## 10. Исключение из сравнения

Reference-продукт **не попадает** в `cohort.yaml`, `run.yaml:products`,
`sources/corpus_urls.yaml` — поэтому по построению отсутствует в `cells`, `Capability`,
`Coverage`, `Comparability` когорты. Фильтровать нечего: reference-корпус — отдельная
подсистема, а не продукт прогона.

Линтер (блокирующий):
* `product_id` из `reference_products.yaml` не может встречаться в `cohort.yaml` или
  `run.yaml:products`;
* `baseline_id` из `baselines.csv` обязан быть объявлен в `reference_products.yaml`, если
  строки есть;
* `baseline_id` из `passport.upstreams` обязан быть объявлен там же;
* архетип A: ровно один `upstreams`; B: ≥1; C: `baselines.csv` пуст и `upstreams` пуст.

Посмотреть на reference-продукт — `hound baseline report` (read-only, прогон не нужен):
покрытие каталога по версиям, распределение `present/absent/unclear`, принято/на ревью,
карта, согласие факт↔карта, кто из продуктов когорты что унаследовал и от какого предка.

## 11. Тесты

**Ядро (без сети):**
* `baselines_digest` / `baseline_facts_digest`: смена `min_version` → новый `run_id`;
  смена `reviewed_by`/`observed_at` → **тот же**; смена `review` → новый; перестановка
  `upstreams` → новый (через `passports_digest`).
* Ш4, архетип A: `direct` + `present` + `accepted` → ячейка с цитатой факта; `pending`/
  `rejected`/`absent`/нет факта → ячейки нет, причина в базисе.
* Ш4, архетип B: два предка, факт у второго → наследовано от второго, причина по первому
  опубликована; факт у обоих → победил **первый объявленный** (пин порядка); ни у одного →
  ячейки нет, причины по обоим.
* I22: цитата факта — подстрока текста чанка; выдуманная отвергается.
* Версии: `"18.4.1"` → факт на 18; `"abc"` → линт-ошибка; факт v17 при объявленной v18 не
  наследуется (регрессия не замазана).
* Линтер: непустой `baselines.csv` без reference-продукта → блок; reference-продукт в
  когорте → блок; A с двумя `upstreams` → блок; C с `upstreams` → блок.
* `refresh`: `added`/`removed`/`changed` классифицируются верно; `removed` не пишется;
  `min_version` предлагается, `baselines.csv` не меняется.
* Карта: `map_id` меняется от модели/промпта/каталога и **не** меняется от `observed_at`;
  `score.json` той же формы, что `ScoreBundle`; согласие факт↔карта считается и публикует
  `n` (при `n=0` — `None`, а не 0.0).

**Без сети, на фейковых портах:** recon на 3-страничном корпусе → факт с цитатой; `absent`
при полном охвате; `unclear` при неполном; карта на фейковом оценщике.

**Живой (по разрешению владельца):** recon PostgreSQL 18 → факты; `--map` → карта;
`baseline report --with-map`; затем прогон с `direct`-строками: сравнить число
унаследованных ячеек и долю `support_not_about_subject` до/после.

## 13. Обновление: `refresh` и вывод `min_version`

`hound baseline refresh --version 19`:

```
1. recon v19 (если корпуса нет) → факты v19
2. diff против принятых фактов предыдущей версии:
     added      present@19, нет@18          → кандидат строки; предложить min_version=19
     removed    present@18, absent@19       → РЕГРЕССИЯ: не применять, показать человеку
     changed    present в обеих, другая цитата → кандидат на замену цитаты
     unchanged  → ничего
     unclear    → в очередь review
3. печать diff (числа + список параметров), --apply пишет только `added`/`changed`
4. `baselines.csv` НЕ трогается: предложенные `min_version` выводятся отдельным списком
5. карта v19 — отдельным шагом (`--map`), со своим `map_id`
```

Почему `min_version` не пишется автоматически: это авторское решение о применимости
строки, и неверный пол молча **пере**наследует (порог ниже реального) или **недо**наследует
(выше). Оба исхода меняют карту без наблюдения. Предложение + подтверждение человеком —
единственная форма, оставляющая решение владельцу профиля (A3).

`removed` — не автоприменение: исчезновение описания может быть (а) реальной регрессией
upstream, (б) переездом документации, (в) дефектом извлечения. Различить может только
человек, и различие определяет, снимать ли строку.

### 16.1. Что уточнено по ходу (и почему)

* **Контракт — 35 полей, не 34.** План считал от 32; фактически было 33 (`embed_spec` уже
  входил). Оба новых поля — `execution_change`: прежние `run_id` несравнимы.
* **Продукт A-пакета без предка не блокируется** — публикуется предупреждением
  `upstream-presence` (строка линта — `upstreams-by-archetype`). «Вендор не называет версию» — честное состояние; блок остаётся на
  противоречие (два предка в A, предок в C, необъявленный `baseline_id`).
* **Цитата наследования берётся из факта, а не из паспорта**: `source_id =
  upstream://{baseline_id}#{param_id}@{version}`, `citation_quote`/`source_url`/`content_hash`
  — из `BaselineFact`. Паспортная цитата как фолбэк снята: она описывала заявление вендора,
  а не наблюдение.
* **`BaselineFact` при `status=present` требует непустой `url`** (I15): производное
  доказательство обязано резолвиться в адрес. Разведка, нашедшая цитату в чанке без URL,
  публикует `unclear` с причиной `quote_found_without_url`, а не `present`.
* **`build_id` reference-сборки — от содержимого** (`reference_content_digest` по
  отсортированным хешам чанков), не от пути БД: иначе две одинаковые сборки стали бы разными.
* **Движок лексики карты выбирает composition root** (порт `LexicalSearcherPort` в
  `ports/lexical_index.py`): `pipeline` не импортирует `adapters` (матрица 01 §1).
* **Производитель reference-корпуса — отдельный модуль, и писатель хранилища в нём
  инъектируется** (17.11.2026). `recon` умел только читать `reference.db`; сборки не было
  вовсе. `pipeline/reference_build.py` собирает её портами (`CrawlerPort`/`ExtractorPort`/
  `ChunkerPort`) и `Frontier` — второй формулы scope нет. `SqliteStore` приходит фабрикой
  из composition root, потому что `pipeline` не импортирует `core.store`; без фабрики
  сборка отказывает видимо (`ReferenceBuildUnavailable`), а не собирает «в памяти».
  Раскладка стала per-build (см. §4) — это `reference-corpus/2`: две сборки одной версии
  сосуществуют, `current.json` выбирает текущую, `mtime` не выбирает никогда.
* **CLI доведён до цепочки, а не до набора команд** (17.11.2026): `build` собирает корпус
  (корни — только из декларации), `recon`/`map` берут `--build` и разрешают сборку
  раскладкой, `list` показывает состояние корпуса (сборки, объёмы, охват) и **следующую**
  команду, а каждая ошибка «нечего читать» называет команду, которая это создаёт.
  `recon` перестал быть линейным проходом: кандидатов отбирает `Bm25Index`, и замена
  измерена (`docs/reports/measurements/2026-11-17-recon-top-k.md`) — исход совпадает уже при
  `K=2`, а цитаты перестали приходить из одного чанка (6 источников на 181 факт → 165).
* **Полнота прохода — носитель I2/I2c, а не косметика манифеста**: `complete=false` с
  машинными причинами (`truncated:max_documents`, `skipped:robots`, …) запрещает `absent`
  в фактах. `complete` при этом **не** входит в `build_id`: он описывает проход, а не
  содержимое, иначе один упавший запрос давал бы «другую сборку» той же документации.
* **Глубина обхода по умолчанию не ограничена, и это исправленный дефект** (17.11.2026).
  `CrawlLimits.max_depth=0` значит «только seeds оператора» — верно для краула когорты, но
  для reference-корпуса это читало **одну** страницу руководства и объявляло
  `complete=True`, то есть давало `recon` право публиковать `absent` по одной странице
  (I2/I2c). Граница пространства здесь — объявленный корень (`docs_roots` = path-prefix),
  а не выдуманный потолок (A3); `max_documents` остаётся `None` по той же причине — объём
  публикуется в манифесте. Ссылки теперь извлекаются **всегда** (иначе frontier не увидел
  бы, что упёрся в границу), поэтому явный `--max-depth 0` — законное объявление «только
  корни» с видимой ценой: `truncated:max_depth` ⇒ `complete=false`.
* **Архетип B не требует объявленной линии** — отличие от буквы §3.2 плана, и это
  откат принятого ранее правила. Регламент §1.5: базлайн-участник в когорту включается
  «если он существует», а кросс-линейные параметры B измеряются только корпусом, поэтому
  «ни у одного продукта нет предка» — штатная форма B, а не противоречие методу. Цена
  обратного правила измерена: канонический валидный пакет профиля
  (`tests/config/fixtures/package.yaml` — B, `baselines: [baseline_a]`, продукты без
  предков) перестал проходить линтер. В B проверяется **состояние продукта**
  (`upstream-presence`, предупреждение), а не метод пакета.

### 16.2. Что осталось открытым

1. **Этап 11** — данные. Без него в пилоте нет ни одного факта (`baseline_facts.csv` пуст),
   поэтому доля наследования не измерена; это цена, а не дефект: механизм проверен на
   синтетике (`tests/pipeline/test_reference_products.py`, `test_reference_corpus.py`,
   `test_reference_map.py`, `test_reference_build.py`), но живой сборки reference-корпуса
   не было ни одной — ни `build` на реальном краулере, ни `map`/`report --with-map` на
   реальной сборке.
2. **Открытые вопросы §15** не закрыты: объём git-фактов при 200 профилях, карта по всем
   версиям vs `current_version`, порог согласия факт↔карта (порог не вводится — A3).
3. **Лексический индекс reference-корпуса не материализуется** (§4 предусматривал
   `lexical/` рядом с `reference.db`): `recon` собирает `Bm25Index` в памяти на вызов
   (замер: `index()` 29.0 с на 253 306 чанках, поиск 181 параметра 308.9 с). Для корпуса
   версии (1–2 тыс. страниц) это секунды, поэтому материализация отложена до появления
   профиля, где цена станет заметной (§12 — триггер тот же: измеренная доля `unclear`).
4. **`map`/`report --with-map` не исполнялись на живой сборке** — проверены только
   синтетикой CLI-тестов; порядок «сборка → карта → согласие» на реальном корпусе
   остаётся непроверенным до этапа 11.
