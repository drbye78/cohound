## 1. Как задан темп сейчас

- Ось — `crawl.rate_limit: {min_s, max_s}` (`RateLimitSpec`, `core/domain/models.py:480`).
  Резолвится цепочкой `defaults < run < profile < product < site`
  (`core/pipeline/crawl_sources.py:145-151`), едет в `FetchPlan` **на каждый URL**.
- Примитив — не token bucket, а **резерв слота по origin**: `target = max(now, last[origin])
  + uniform(min_s, max_s)`; `last[origin] = target`; сон — вне лока
  (`core/util/rate_limit.py:235-272`). Origin — host без пути (`normalize_host`), поэтому
  три корня `postgrespro.ru` делят одну очередь.
- Ждёт сам сетевой вызов, а не постановка в frontier: воркер пула спит перед `active.fetch`
  (`local_fetch` в пулевом пути, `fetch_and_commit` в inline — оба в
  `core/pipeline/corpus_ingest.py`).
- Ширина пула полосы — `max_workers` (`core/pipeline/corpus_drain.py`), число
  полос — `host_concurrency` (`core/pipeline/corpus_driver.py`). Полоса — право на **host**;
  внутри хоста резервы сериализуются лимитером.
- `crawl_rate_limit` — одно из 32 полей `EXECUTION_CONTRACT_FIELDS` (`core/pipeline/digests.py:128`)
  и берётся **только из `run.yaml`** (`core/cli/execution_axes.py:1061`). Отдельно от него
  **разрешённый** темп (site > run) входит в `crawl_config_digest` через
  `CrawlLimits.as_dict()` (с 07.11.2026, решение владельца): per-site значение перекрывает
  объявленную run-level ось, то есть без этого ключа его можно было бы нейтрализовать для
  конкретного хоста, не сдвинув `run_id`. Прежнее утверждение «вежливость не меняет состав
  корпуса» (`core/pipeline/corpus_commit.py:276-278`) оказалось верным только для
  run-level слоя: измеренный всплеск `504` и усечение `max_documents` показывают обратное.

## 2. Дефект HEAD: два резерва на один фетч в пулевом пути — ✅ ИСПРАВЛЕН (`b80e131`)

`local_fetch` звал `limiter.wait(...)` **и** `limiter.wait_reserved(...)`;
оба двигают `_last[origin]` на новую `uniform(min_s, max_s)`. Фактический интервал =
сумма двух значений: при объявленных 1–5 с среднее **6.0 с** вместо 3.0, диапазон 2–10 вместо
1–5. Inline-путь делает один резерв — два пути пейсили по-разному при одной политике.

Цена на полигоне (`docs.tantorlabs.ru`, бюджет 5000 документов):

| режим | с/док | пол на 5000 |
|---|---|---|
| объявлено (среднее `uniform(1,5)`) | 3.0 | 4.17 ч |
| замер 02.11 (один резерв) | 3.61 | 5.02 ч |
| HEAD (два резерва) | 6.0 | 8.33 ч |

Правка — восстановление **объявленной** семантики, а не новый режим: `run_id` не меняется
(правка не меняет объявленных значений; на момент 07.11.2026 темп входит в
`crawl_config_digest`, но здесь он остался прежним — см. §1/§3). Замеры 02.11 сняты до
появления `wait_reserved`, поэтому живьём удвоение не наблюдалось. **Пере-замер сделан**
(07.11.2026, `2026-11-07-crawl-rate-tantor.md` §9): на `{0.05, 0.2}` весь корень `/tdb/` —
1207 документов за 209 с = **5.78 запроса/с** при номинале 6.67 (87 %), `fetch_ms` p50 113 мс.
Удвоения интервала нет; остаток до номинала — работа очереди, а не лимитера.

## 3. Два разных ресурса: пауза и число потоков

Пропускная способность одного хоста — `rate = min(1/delay, in_flight / latency)`, где
`delay` — объявленная пауза, `in_flight` — сколько фетчей этого хоста в полёте, `latency` —
время ответа. Отсюда требуемое `in_flight ≥ rate × latency` (закон Литтла), и «больше
потоков» помогает **только** когда связывает второй член.

Измерено 02.11: `fetch_ms` p50 = 1.52 с, p95 = 7.63 с; объявленная пауза даёт 0.33 док/с.
Один поток даёт 1/1.52 ≈ 0.66 док/с — значит **на объявленном темпе потоки не связывают**, и
именно поэтому 92 % стены обхода было паузой, а не CPU (0.054 с CPU/док после правки
`done()`; драйвер держит ~20 док/с).

Порог, за которым потоки начинают связывать (закон Литтла, по измеренной латентности):

| допускаемая пауза | rate | `in_flight` при p50 1.52 с | при p95 7.63 с |
|---|---|---|---|
| 3.0 с (текущее среднее) | 0.33 док/с | 1 | 3 |
| 0.5 с | 2 док/с | 4 | 16 |
| 0.2 с | 5 док/с | 8 | 38 |

**Устарело с 07.11.2026:** прежде `in_flight` на хост был равен `max_workers` из пакета (3) —
одно число для всех хостов. Теперь ширина краула объявлена **на узле**
(`config/deploy.yaml: crawl.max_workers: 10`, `host_concurrency: 5`), пакет её не объявляет;
`lanes_limit = 1` только при `host_concurrency is None` (`core/pipeline/corpus_driver.py:245`).
Замер того же дня: на `{0.05, 0.2}` пул 1/2/5 даёт 1.87/2.20/2.40 запроса/с, весь корень
`/tdb/` — 1207 документов за 209 с (5.78 запроса/с), поэтому ширина 10 подтверждена числом,
а не выбрана «на глаз» (`2026-11-07-crawl-rate-tantor.md` §9). `host_concurrency`
по-прежнему распределяет **полосы** (право на host), а не потоки внутри хоста.

> **Поправка 07.11.2026 — латентность в этой таблице была нашей, а не хостовой.**
> `fetch_ms` оборачивает весь `crawler.fetch()`, и в scrapy-пути внутри лежали ~1.2 с
> собственных задержек: перезапрос `robots.txt` на каждый документ и `DOWNLOAD_DELAY: 0.5`
> Scrapy как **второй, необъявленный пейсер** (измерено: `plan.robots=False` → 147 мс;
> `robots=True` + `DOWNLOAD_DELAY=0` → 246 мс; `robots=True` со штатными настройками →
> **1409 мс**, при ответе хоста **≈100 мс**; `docs/reports/measurements/2026-11-07-crawl-rate-tantor.md`
> §4/§7.5). Значит закон Литтла надо считать от **хостовой** латентности: при 0.5 с паузы
> нужно `in_flight ≈ 0.2`, при 0.2 с — `≈0.5`, то есть один воркер насыщает лимитер вплоть
> до ~10 запросов/с, а «4–16 потоков» из таблицы выше были ценой нашей же задержки.
> Прежде чем выводить `in_flight` из латентности, прибор обязан публиковать **её отдельно
> от обвязки** — это часть §10.

Вывод для фичи: адаптивный темп — это **две** величины (пауза и число потоков на хост), а не
одна. Вторая выводится из первой и измеренной латентности, а не назначается.

## 4. Что объявляется, а что наблюдается

- **Вход (идентичность):** политика темпа (стартовый интервал, границы, шаг, правило
  вывода `in_flight`, потолок попытки) — как `crawl.rate_limit` сегодня.
- **Провенанс (наблюдение):** фактические интервалы, латентность, `429`/`Retry-After`,
  число фетчей в полёте, счётчики отказов. Носитель уже есть:
  `crawl_session_items.fetch_started_at/fetch_ms/http_status` и per-host метрика
  (`core/pipeline/crawl_metric.py:289-381`), публикуется `hound crawl status --per-host`.
- **Почему так:** при 429 меняется **состав корпуса** (URL уходит в `failed`), а не только
  время; необъявленная адаптация — тот же класс дефекта, что необъявленный `--max-depth`.
  Прецедент разделения — `refresh_policy` (идентичность) против per-root
  `network_mode`/`corpus_source` (провенанс), план 19/20.
- **Дыра закрыта 07.11.2026.** Per-site `rate_limit` из `domain_profiles.yaml` менял
  фактический темп, не меняя `run_id` (резолвился в `FetchPlan`, но не в контракт).
  Теперь разрешённый темп (`site > run`, **та же формула**, что исполнение) входит в
  `CrawlLimits.as_dict()` → `crawl_config_digest` → `run_id` (`core/pipeline/crawl_frontier.py`).
  Ключ появляется только при объявлении оси, поэтому прогоны без темпа сохраняют прежний
  дайджест; run-level канон остаётся отдельным полем `crawl_rate_limit`. Пин «одна формула»
  (`tests/pipeline/test_crawl_frontier.py`) не даёт `FetchPlan` и `CrawlLimits` разойтись молча.

## 5. Прибор: проба, а не прогон

Проба меняет паузы, то есть **объявленные входы**, поэтому ею нельзя «пробовать» внутри
прогона, из которого берётся корпус (иначе бюджет/оси прогона задним числом подгоняются под
результат). Разделение как с `embed_bench.py`: отдельный инструмент публикует замер, прогон
идёт с уже объявленным числом.

Минимальная спецификация пробы:

1. вход — фиксированный список URL одного хоста (sitemap либо первые N из уже наблюдённых);
2. ступени паузы сверху вниз (начиная с robots `Crawl-delay`, если он есть, иначе с
   объявленной), число фетчей на ступень одинаково;
3. критерии остановки ступени: появление `429`/`503`, рост p95 латентности, рост доли
   не-2xx; фиксируется **первая** ступень с отказом;
4. публикуется: интервал, который хост держал без ошибок, p50/p95 латентность, признак
   `Retry-After`, и по закону Литтла — требуемый `in_flight`;
5. результат — файл в `docs/reports/measurements/` с датой и хостом; повтор на другом хосте —
   отдельный замер (правило «один продукт на одном хосте ещё не правило»).

## 6. Что код не делает (проверено 07.11.2026, факты, не пожелания)

- `Retry-After` разобран (`core/util/retry.py`), но его читают **только** поисковые
  адаптеры. На корпусном пути он **недоступен по носителю**: `RawPage` заголовков не несёт —
  только `etag`/`last_modified`/`not_modified` (`core/ports/types.py:91-142`), поэтому повтор
  ждёт слот объявленного лимитера (`core/util/fetch_retry.py:113` — `limiter.wait_reserved`),
  а не указание хоста. Шов отдаёт `retry_after` только как back-pressure **подачи** работы
  (`core/adapters/remote_crawl_executor.py:186`, ответ `crawl/submit`), а не как ответ
  страницы, — то есть под `split` постраничный `Retry-After` тоже не читается.
- `429` в HTTP-пути — **повторяется** (`core/util/fetch_retry.py`, `FETCH_RETRY_TIMES = 2`,
  то есть до трёх попыток, каждая берёт свой слот лимитера; `429` — транзиентный статус,
  `core/ports/crawl_errors.py:72`); после исчерпания — `failed/source_unavailable`
  (`crawl_http.py`). Класс по-прежнему не блокирующий (`core/domain/enums.py:203-212`),
  поэтому пачка отказов формально не портит покрытие — но теперь она **видна**: число
  повторов публикует `crawl status --per-host` (`pacing.retries`,
  `core/pipeline/crawl_pacing.py:49`). До `9a8440a`/`c3e5b8d` это была тихая деградация в
  счётчиках.
- Браузерный `honest`-путь статус не наблюдает (`http_status=NULL`), `429` невидим;
  `hybrid` видит `CHALLENGE_STATUSES` и повторяет 3 раза (`crawl_browser.py:679-730`).
- robots `Crawl-delay` корпусным пейсингом не читается вовсе — только браузерным адаптером и
  только при `rate_limit is None` (`crawl_browser.py:566-573`).

## 7. Границы и открытые вопросы

- Потоки по хосту — **только** HTTP-путь. `BrowserCrawler` не потокобезопасен, honest-рендер
  CPU-bound и конкурирует с пулом экстракции: для браузерных хостов нужен отдельный замер и,
  вероятно, пул контекстов, а не потоков.
- Потолок `in_flight` не назначается «для безопасности»: он выводится из измеренной
  латентности и проверенного отказа хоста; число публикуется.
- `Crawl-delay` из robots — **пол**, а не цель: старт с него, дальше решает измерение.
- Не вводится значение `auto`: политика называет алгоритм и границы, наблюдение называет
  факт.
## 8. Прибор темпа (реализовано 07.11.2026): измерение без адаптации

§5 описывает пробу, которая меняет объявленный вход и потому не может идти внутри
прогона. Отдельно от неё нужен **наблюдатель** текущего прогона: без него «сколько
документов в секунду даёт хост» не опубликовано нигде, и любой потолок темпа остаётся
числом без замера. Прибор добавлен как провенанс исполнения и **не** меняет политику:

- `core/pipeline/crawl_pacing.py` (`CrawlPacing`) — под локом считает запросы **в полёте**
  на origin и их пик (high-water), окно (первый старт → последний финиш), длительности и
  агрегаты по продукту/прогону. Пик фиксируется только вокруг сетевого вызова
  (`local_fetch`/`fetch_and_commit`), поэтому ожидание лимитера в «полёте» не участвует.
- `RateLimiter.wait_stats` — кумулятивное ожидание по origin (`waits`, `waited_s`);
  считает сам лимитер, там где известны `delay`/`remaining`.
- Носитель — `crawl_sessions.provenance_json`, блок `pacing`
  (`hosts`/`products`/`total`: `requests`, `requests_per_s`, `in_flight_max`,
  `limiter_waits`, `limiter_waited_s`, `fetch_ms` p50/p95, `window_s`,
  `first_request_at`/`last_request_at`). Читают **оба** потребителя: `metrics.json`
  (`resources.crawl`) и `hound crawl status --per-host` (строка host'а и таблица).
- Идентичность не тронута: ни одно поле не входит в `EXECUTION_CONTRACT_FIELDS`,
  `run_id` и `crawl_config_digest`; схема БД не меняется (это JSON-провенанс).
- Первый измеренный факт, который прибор уже даёт: браузерный маршрут сериализован, его
  `in_flight_max == 1`; внутрихостовая параллельность HTTP-пути видна числом (пин —
  `tests/pipeline/test_corpus_concurrency.py`).
- **После исправления пейсера (07.11.2026, `c81f74b`) прибор считает ещё и фактические
  HTTP-запросы** (`http_requests`) и запросы на чужие хосты (`foreign_hosts`) — попытки
  фетча их не показывали. Проверено на живой пробе: 60 документов ⇒ `requests=60`,
  `http_requests=63` (страницы + один `robots.txt` + два хопа), `foreign_hosts={tantorlabs.ru: 1}`
  за весь проход — до правки было по одному лишнему запросу на нужный хост и на чужой **на
  каждый документ**.
- **Ширина пула при фиксированном лимите (тот же стенд, `{0.2, 0.5}`, 60 документов, движок
  `scrapy` после правки):**

  | `max_workers` | `req/s` | окно, с | `in_flight_max` | `fetch_ms` p50 | `limiter_waited_s` |
  |---:|---:|---:|---:|---:|---:|
  | 1 | 1.87 | 32.1 | 1 | 116 | 21.8 |
  | 2 | 2.20 | 27.2 | 1 | 115 | 29.5 |
  | 5 | 2.40 | 25.0 | 1 | 116 | 61.9 |

  Номинал лимитера — 2.67 запроса/с. То есть потоки внутри хоста поднимают темп с 70 % до
  90 % номинала и **ни разу не выводят на хост больше одного одновременного запроса**:
  интервал (0.375 с) много больше ответа (0.116 с), поэтому конкурентность к хосту
  структурно ≈0.3, а не «5». Рычаг — пауза и полосы по хостам, не ширина пула.

## 9. Тираж: остальные http-корни пилота (после полигона)

проверяется исправление скрытого пейсера (§2-поправка, §3-поправка) — повторные панели A/B/C

Протокол на корень — §5 без изменений (лестница пауз сверху вниз, равное число фетчей на
ступень, стоп-правило «5 % `429`/`5xx` останавливает ступень», публикация файла в
`docs/reports/measurements/` с датой **на каждый хост**). Специфика тиража:

- **Один хост — один файл замера.** Сводить разные хосты в одну таблицу можно только как
  сводку со ссылками, не как одно число.
- **Результат кладётся per-site** — `domain_profiles.yaml: <host>: rate_limit` (+ генератор
  `sources/build_package.py` и пин `tests/packages/test_build_package.py`), а не в `run.yaml`:
  ось входит в `crawl_config_digest` ⇒ это `execution_change` с новым `run_id`, а не правка
  на месте.
- **Потолок, не найденный за бюджет, публикуется как нижняя граница** («терпит ≥ N»), а не
  как «предел хоста».
- **Robots `Crawl-delay` — пол**, а не цель: если лента его объявляет, лестница начинается
  с него (§7), а не с объявленного `rate_limit`.
- **`in_flight` не назначается:** он выводится из измеренной **хостовой** латентности по
  закону Литтла и публикуется числом рядом с лимитом (§3-поправка). Пока прибор не отделяет
  хостовую латентность от обвязки, выводить его не из чего — отсюда §10.

## 10. CLI: разведка темпа как функция, а не ручной стенд

Замер 07.11.2026 делался вручную: изолированный `COHOUND_HOME`, копия пакета, правка
`rate_limit`/`max_documents` в копии, три прогона `crawl run --crawl-only`, затем чтение
`crawl_session_items` и `provenance_json`. Ручной путь уже стоил двух дефектов, найденных
попутно (мёртвый сид корня, падение `crawl resume`), и одной ошибки чтения (`fetch_ms`,
принятый за время ответа хоста). Тираж на ≥100 профилей таким способом не масштабируется —
разведка темпа должна стать **функцией** с воспроизводимым входом и публикуемым артефактом.

Предлагаемая форма (имя и флаги — к обсуждению, семантика — нет):

```
hound crawl probe --host docs.tantorlabs.ru --root /tdb/ \
  --engine http|scrapy \
  --panels "1.0-5.0,0.5-1.0,0.2-0.5,0.05-0.2" \
  --documents-per-panel 250 --budget-requests 1200 \
  --out docs/reports/measurements/ --json
```

Обязательные свойства (каждое — из уже случившегося дефекта):

1. **Проба — не прогон.** Свой изолированный стенд (`state`/`runs`), запись **только** в свой
   каталог и в артефакт замера; `run.yaml`/`domain_profiles.yaml` пакета не правятся.
   Предложение значения печатается как YAML-фрагмент (`--propose`), а применяет его человек —
   потому что это `execution_change` (§13), а не побочный эффект замера.
2. **Воспроизводимость.** Входы пробы (хост, корень, лестница, движок, число документов,
   версия кода) → `probe_id`; число в отчёте без `probe_id` не переиспользуется. Это тот же
   принцип, что `run_id = f(объявленных входов)`, но для замера, а не для корпуса.
3. **Две латентности, а не одна.** Публикуются **хостовое** время ответа (TTFB/полный ответ)
   и полная длительность `fetch()` отдельно, плюс `http_requests` (страница + `robots.txt` +
   хопы редиректов) и `foreign_hosts` — иначе `req/s` занижается, а чужие хосты невидимы
   (измерено: 1.57 против ≈3.1 запроса/с, `docs/reports/measurements/2026-11-07-crawl-rate-tantor.md` §7.5).
   Пока эти два числа не разделены, `in_flight` по закону Литтла выводить нельзя.
4. **Стоп-правило и бюджеты объявлены заранее.** `--budget-requests` обязателен: проба без
   потолка запросов к чужому сайту не запускается; ступень останавливается на 5 %
   `429`/`5xx` и это фиксируется как результат, а не как сбой.
5. **Скоп не расширяется.** Хост и корень — явные аргументы; `redirect_out_of_scope` считается
   и публикуется (иначе мёртвый сид корня снова даст «ноль документов» без объяснения).
6. **Один артефакт на (хост, дата)** — markdown для чтения + JSON для повторного анализа;
   строка в `docs/reports/measurements/README.md` генерируется, а не пишется руками.
7. **Browser — отдельно и позже:** `--engine browser` отказывает, пока нет замера браузерного
   маршрута (§7: не потокобезопасен, honest-рендер CPU-bound, `in_flight_max == 1`).
8. **Панель публикует применённый лимит, а не запрошенный.** Две серии из четырёх 07.11.2026
   оказались невалидными по одной причине: панель правила только run-level `rate_limit`, а
   per-site значение хоста сильнее (site > run), поэтому все «разные» панели молча работали на
   одном значении. Отсюда два обязательных свойства: правка панели **идемпотентна** (профиль
   каждый раз восстанавливается из канонического источника, затем правится один ключ) и после
   прогона печатается `declared_min_interval_s` из `crawl status --per-host` — он должен
   совпасть с панелью, иначе число в отчёт не идёт. Ручной стенд этого не гарантировал; CLI
   обязан гарантировать по построению.
