# Политика краула по областям и замороженный корпус (план)

**Тип:** план. **Владелец:** Roger. **Начало:** 04.11.2026, срез `1c76e6e`.
**Отслеживание:** чеклист слоёв ниже; статус пункта — по факту кода, а не по обещанию
(правило маркеров — как в `README.md` этого каталога: ✅ / ⬜ / ➖ / ❔).

## 1. Зачем

Запрос владельца (04.11.2026), дословно по смыслу:

1. Для **продукта, хоста, корня или произвольной маски пути внутри корня** можно задать режим
   краулинга: `auto` (как сейчас), `manual` (первичный дискавери — автоматический, обновление —
   по ручному запросу через CLI), `blocked` (ни дискавери, ни обновление).
2. Прогон может **считать ранее собранные данные краула неизменными** — все продукты когорты
   как будто в режиме «обновление по ручному запросу», включается флагом CLI.

Зачем это нужно по существу, а не «для удобства». Сегодня прогон обходит все корни когорты и
решает «обновлять/не обновлять» только глобально (`--refresh`), а отказ от обхода выражается
лишь `exclude_paths` (это «не обходить», без per-host статуса и без различения дискавери и
обновления). Из этого следуют две вещи, которые уже стоили времени:

* **Нельзя измерить новый стек на старом корпусе.** `--refresh offline` переиспользует **чанки**
  из `state.db` и отказывает при смене `chunker_version`, то есть новый чанкер/экстрактор им не
  измерить вовсе; приходится ждать пере-краула, которого может не быть неделями.
* **Нельзя сказать «этот хост мы сейчас не обновляем»** так, чтобы это было видно в отчёте:
  корень либо обходится целиком, либо не обходится никак, и разница между «нечего обходить»,
  «нет seed'ов» и «политика запрещает» не выражается.

## 2. Решения владельца (04.11.2026)

| вопрос | решение | следствие |
|---|---|---|
| где живёт политика | **`state.db` оператора**, пакет задаёт дефолты | режим меняется без правки пакета и коммита; эффективная политика прогона входит в идентичность |
| что значит «данные неизменны» | **ни одного запроса; корпус из сохранённых байтов** | нужен режим, отличный от `offline` (тот переиспользует чанки и отказывает при смене версий) |
| что блокирует `blocked` | **только сеть**; продукт остаётся на карте | измеряется по сохранённым данным, в провенансе — `crawl_blocked` и время снятия |
| полнота в замороженном прогоне | **сохраняется как на момент снятия**, `❌` публикуется | это условие измерения, а не новая методология: `coverage.complete` — факт, установленный протоколом при снятии; прогон его **переиспользует**, а не переопределяет |

| видимые отказы корня и продукта | `out_of_scope_subdomains`/`accepted_foreign_hosts` (`crawl_frontier.py:1149`), `product_skipped` (`corpus.py:3989`), `zero_source_reasons` | нет токена «запрещено политикой» |

Ключевой вывод разведки: **ни один существующий носитель не даёт «продукт × хост × путь»
без ложной идентичности** — `crawl_sources.yaml` знает продукт, но не входит в `run_id`;
`domain_profiles.yaml` входит в `run_id`, но не знает продукта. Поэтому политика живёт в
`state.db`, а в контракт входит **резолв** (см. §6).

## 4. Модель данных

**Области и приоритет.** Область задаётся парой (вид, значение):

| вид | значение | пример |
|---|---|---|
| `product` | `product_id` | `postgrespro` |
| `host` | хост (без схемы) | `edu.postgrespro.ru` |
| `root` | seed-корень: хост + префикс пути | `https://docs.example/db/` |
| `path` | `host` + маска пути внутри корня | `edu.postgrespro.ru/docs/legacy/**` |

Разрешение — **самое специфичное побеждает**: `path` > `root` > `host` > `product`. Внутри
одного вида: самый длинный совпавший литеральный префикс, затем более поздняя запись
(`created_at`, затем `policy_id`). При равной специфичности **`state.db` переопределяет
дефолт пакета**. Правило детерминировано и проверяется тестом-матрицей, а не «по смыслу».

**Хранение (state.db).** Новая таблица, append-only (правка = новая строка + `superseded_by`),
без `ALTER`-шимов: `STATE_SCHEMA_VERSION` `7` → `8`, старая БД отвергается
`SchemaVersionMismatch` — как требует §9 AGENTS.

```sql
CREATE TABLE crawl_policy (
    policy_id      INTEGER PRIMARY KEY,
    product_id     TEXT NOT NULL,
    scope_kind     TEXT NOT NULL CHECK (scope_kind IN ('product','host','root','path')),
    host           TEXT,          -- NULL только при scope_kind='product'
    path           TEXT,          -- NULL при 'product'/'host'; маска при 'path'
    mode           TEXT NOT NULL CHECK (mode IN ('auto','manual','blocked')),
    note           TEXT,
    actor          TEXT NOT NULL,
    created_at     TEXT NOT NULL,
    superseded_by  INTEGER REFERENCES crawl_policy(policy_id)
);
CREATE INDEX crawl_policy_scope ON crawl_policy (product_id, scope_kind, host, path);
```

**Дефолты пакета** — `packages/{case_id}/crawl_policy.yaml` (необязательный, `extra="forbid"`),
та же тройка слоёв, что у `crawl_sources.yaml`: `defaults` → `products[id]` →
`sites[id][host+path]`. Дефолт без записи в `state.db` действует как есть и виден в отчёте.

## 5. Семантика

| режим | discovery (в `url_state` нет известных URL корня) | update (baseline есть) |
|---|---|---|
| `auto` | идёт | идёт (условный GET по политике прогона) |
| `manual` | **идёт** — первичный дискавери автоматический | **только** если корень/область названы флагом `--refresh-scope` в этом прогоне |
| `blocked` | нет | нет, даже если названы флагом (видимый отказ) |

**Ручной запрос — флаг прогона, не отметка в БД.** `--refresh-scope <product|host|url|mask>`
(повторяемый) разрешается тем же матчером, что и политика. Отметка «обновление запрошено» в
`state.db`, «съедаемая» прогоном, запрещена: два прогона с одинаковыми объявленными входами
получили бы разные корпуса под одним `run_id` (A2/§9).

**Композиция с политикой прогона.** `--refresh` остаётся глобальным и действует **внутри**
областей, разрешённых политикой:

* `auto` / `revalidate` / `refresh` — как сейчас, для областей `auto` и для `manual`-областей,
  названных `--refresh-scope`;
* `offline` — ноль запросов, reuse **чанков** (сегодняшнее поведение; сохраняется);
* **`frozen`** — ноль запросов, корпус из **`corpus_raw`** с пере-извлечением под текущие
  `extractor_version`/`chunker_version`; `--frozen-source chunks` возвращает поведение
  `offline` (быстро, но только при совпадении версий).

В режиме `frozen` области `auto` и `manual` обрабатываются одинаково (сеть запрещена всем), а
`blocked` остаётся `blocked` (различие — в провенансе, а не в запросах). Корень без
сохранённых байтов — видимая причина `stored_bytes_missing`, а не тихий пропуск и не `failed`.

## 6. Идентичность прогона

Что меняет корпус — обязано менять `run_id`:

1. **`crawl_policy_digest`** — новый дайджест **резолва** эффективной политики для когорты
   (отсортированные `(product_id, scope_kind, host, path, mode)` после применения приоритета и
   дефолтов пакета). Входит в `EXECUTION_CONTRACT_FIELDS` (`core/pipeline/digests.py:88`),
   29 → 30 полей: смена режима даёт другой корпус, значит другой `run_id`. Прецедент —
   `deploy_profile`: тот же `run_id` над двумя исполнениями был бы ложью об условиях.
2. **`refresh_policy`** уже входит в `run_id` отдельным слагаемым (`plan.py:112`) — новое
   значение `frozen` и ось `frozen_source` обязаны попасть туда же (сейчас `frozen_source`
   не существует).
3. **`hound crawl run` перестаёт хардкодить `RefreshPolicy.AUTO`** (`core/cli/commands/crawl.py:427`):
   иначе `run` и `crawl run` адресуют разные сеансы при одном объявленном входе.
4. Отметка времени снятия (`corpus_captured_at` на корень) — **провенанс**, не идентичность
   (как `extractor_version`): она не входит в `run_id`, но попадает в `pb`/манифест.

## 7. Слои работ

### P1 — хранилище, разрешение, CLI, дайджест (поведение не меняется)

- ⬜ Таблица `crawl_policy` (STATE 8), `StorePort`-методы, append-only правка через `superseded_by`.
- ⬜ `packages/{case_id}/crawl_policy.yaml` + загрузчик рядом с `crawl_sources.yaml`.
- ⬜ Матчер и разрешение (`resolve_crawl_policy`): приоритет, дефолты пакета, детерминизм;
  тест-матрица на все пары «область × специфичность × источник».
- ⬜ `hound crawl policy set|list|clear --package … --actor … [--dry-run]` по образцу
  `hound package profile attest` (lock, append-only, идемпотентность, `--dry-run` ничего не пишет).
- ⬜ `crawl_policy_digest` в контракте; `plan` печатает резолв («что было бы запрещено»), но
  **не исполняет** его — слой намеренно только показывает, чтобы разница `run_id` была видна
  до включения исполнения.

**Приёмка P1:** две записи политики с разными режимами дают **разные** `plan`-`run_id` при
прочих равных; `list` показывает эффективный режим и источник (пакет/оператор); `--dry-run`
не меняет БД (сверка `schema_version` и `count(*)`).

### P2 — исполнение: `manual` и `blocked`

- ⬜ `RootPlan.work_mode ∈ fetch | reuse | blocked` (`core/pipeline/corpus.py:2617,2663`).
- ⬜ `reuse`-корень проходит обобщённый offline-путь (`corpus_ingest.offline_reuse_product:3124`,
  обобщение «продукт → корень»), а не второй проход.
- ⬜ `blocked`-корень: фронтьер не строится, в провенанс корня — `crawl_blocked` + `policy_scope`.
- ⬜ `--refresh-scope` (флаг прогона, паритет `plan`/`run`, тест инвентаря как у осей краула).
- ⬜ Наблюдаемость: `crawl_manual_not_requested`, `crawl_blocked`, `policy_scope` рядом с
  `out_of_scope_subdomains`; строки в `results[].notes` (иначе «нет seed'ов» и «запрещено» неотличимы).

**Приёмка P2:** фейковый краулер считает вызовы — для `blocked` и `manual` без
`--refresh-scope` их **ноль**; для `manual` + `--refresh-scope` — только названные корни;
`skipped_by_policy` в провенансе совпадает с числом корней, а `P1` (текст чанков) не нарушен.

### P3 — `frozen`: корпус из сохранённых байтов

- ⬜ `RefreshPolicy.FROZEN` + ось `frozen_source ∈ bytes|chunks` (в `run_id` вместе с политикой).
- ⬜ Путь `bytes`: `corpus_raw` → `finalize_extracted_text` → экстракция текущей версией →
  чанкинг текущей версией; `extract_cache` переиспользуется по ключу
  `(content_hash, extractor_version, level)`.
- ⬜ Отсутствие байтов у известного URL — `stored_bytes_missing:{n}` (видимая причина), корень
  не роняет прогон; корень без записи в `url_state` в `frozen` — `unknown_roots` (как сейчас в
  `offline`), потому что «снять нечего».
- ⬜ Полнота: `coverage.complete` и `observed_sources` берутся **из записи снятия**; в манифест
  и `pb` — `corpus_captured_at` (`url_state.last_checked_at` по корню) и `frozen_source`.
  Правило публикации `❌`: только для корней, у которых запись снятия была `complete=True`;
  иначе ячейка идёт по общим правилам I2c/coverage.

**Приёмка P3:** прогон `--refresh frozen --frozen-source bytes` на сохранённом срезе:
**ноль сетевых вызовов** (фейковый краулер/`http`-шпион), чанки построены **текущей** версией
чанкера (`chunker_version` в провенансе равен объявленному), `P1/P4/P13 = 0`, число
`stored_bytes_missing` названо; `plan`-`run_id` отличается от `auto` и от `offline`.

### P4 — документы и отчёт

- ⬜ AGENTS §6/§9: режимы, приоритет, `frozen`, что входит в `run_id`; запись о том, что
  `blocked` — сетевая политика, а не исключение продукта.
- ⬜ Манифест/отчёт: эффективная политика, `refresh_policy`, `frozen_source`,
  `corpus_captured_at`, счётчики отказов по политике.
- ⬜ `docs/status-dictionary.yaml` — машинные токены причин (операционное перечисление).

### P5 — сквозная проверка

- ⬜ Тест: смена одной записи политики меняет `run_id` и **не** меняет ничего, если режим тот
  же; `crawl run` и `run` дают один `run_id`.
- ⬜ Тест: `frozen` без сети на подготовленном `state.db` + `corpus_raw` даёт корпус,
  неотличимый по чанкам от `auto`-прогона на тех же байтах (кроме провенанса).

## 8. Приёмка плана (сводно)

- Матрица приоритетов: все пары «область × специфичность × источник» — таблица ожиданий, не
  «похоже работает».
- Идентичность: `crawl_policy_digest` стабилен при перестановке записей и меняется при смене
  режима; `plan`/`run`/`crawl run` паритетны (тесты инвентаря флагов).
- Сеть: в `blocked` и `frozen` — **ноль** вызовов краулера/HTTP (счётчик в фейке), а не «мало».
- Видимость: каждый пропуск по политике имеет машинный токен и место в провенансе; ни один не
  выглядит как `failed` (I4) или как отсутствие seed'ов.
- Инварианты I1–I23 не пересматриваются; `core/` остаётся нейтральным (режимы — операционные
  перечисления, продукт/хост/путь — данные).

## 9. Риски и чего план не обещает

1. **`frozen` не делает корпус свежим.** Прогон честно называет время снятия; соблазн читать
   его как «актуальное состояние» — риск отчёта, а не кода. Лечится провенансом, не молчанием.
2. **Пере-извлечение меняет текст.** `html-6`/`policy-5` на старых байтах даёт другой корпус,
   чем прежний прогон: это `content_change`+`execution_change`, а не «тот же прогон».
3. **`reuse`-путь может не найти чанк-совместимую запись** (сменился чанкер) ⇒ в
   `--frozen-source chunks` это видимый отказ; лечится `bytes`.
4. **Не делаем:** расписаний/периодичности (`next_check_at` по-прежнему не читается),
   приоритетов URL внутри корня, per-URL режимов, автоподбора режима по частоте изменений.
5. **Не обещаем** экономию запросов там, где режим `auto`: цель плана — управляемость и
   измеримость, а не оптимизация обхода.
