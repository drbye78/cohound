# Критический разбор архитектуры CLI coHound

> **Статус реализации на 2026-10-28** (HEAD `f6100c7`): PARTIAL — из 11 дефектов (5
> структурных §2 + 6 поведенческих §4.7) закрыто 5: **2.2** (`4acb5aa`), и **четыре пункта §4.7**
> — read-only БД, код отказа гейта, фильтр `crawl list`, документация `03` — все в `35e4373`.
> Открыто 6: 2.1 (частично — есть `runs`/`status`, нет единого адреса), 2.3, 2.4, 2.5,
> 4.7 (`report` с `ok: true`), 4.7 (Ш3/Ш4/Ш8 без команды). Предложение §4 выполнено только в
> читающей части; единый адрес прогона, `approve`/`reject`, `package edit`, `store gc`, оси
> `run` в `run.yaml` — не сделаны. Ниже у каждого пункта маркер ✅/⬜/➖/❔ с доказательством
> `путь:строка`.

**Дата:** 2026-10-25
**Повод.** Владелец: «есть подозрение, что она сумбурна и далека от актуальных потребностей
и потенциальных сценариев работы с coHound, сложна для восприятия».

**Вердикт: подозрение подтверждается, и причина конкретная.** CLI строился как **отражение
внутреннего устройства** (фазы, модули, порты, милстоуны), а не как язык для сценариев
оператора. Симптом — арифметика: пользователю показывают 18 команд, а вызывать можно **73**,
и на них **684 флага**. Это не «сложно», это неверная единица проектирования.

И это не только форма: второй проход по поведению нашёл четыре дефекта, которые делают
интерфейс **небезопасным для скриптов** — read-only команды создают БД на диске,
`gate --verdict rejected` возвращает 0, `crawl list --run-id` молча не фильтрует,
`report` публикует заглушки с `ok: true`. Плюс документация описывает три команды неверно.
Форма и поведение здесь связаны: когда у команды нет одного способа адресовать прогон,
защитные инварианты тоже негде разместить — они расползаются по местам.

Ниже — измерения, пять структурных дефектов и предложение. Обратная совместимость не
предполагается (по вашему указанию), поэтому предложение — не «пометить deprecated», а
перестроить.

| фаз конвейера | 15 |
| ручных решений-гейтов на прогон | 4 (g1, g2, g3, g4) |

Самые тяжёлые листья: `run` (36 флагов), `crawl run` (29), `crawl resume`/`crawl restart`

## 2. Пять структурных дефектов

**Оговорка о форме кода (2026-10-28).** Внутри `core/cli/` теперь есть реестр `COMMANDS`
(`core/cli/commands/__init__.py`), тонкий `main.py` (322 стр.: `main` + два хелпера
`_apply_env_file`/`_system_exit_code` + реэкспорт),
`parser.py` (сборка) и `context.py`/`wiring.py` (DI/composition root). Это разбор **кода**, а не
интерфейса: ни один из пяти дефектов ниже им не закрыт — пользователь по-прежнему видит 76
листьев, 4 способа адресовать прогон и те же коды выхода. Реестр сделал дешёвой **правку**
поверхности (`runs`/`status` встали в него без роста `main.py`), а не саму поверхность.

### 2.1 Одна сущность адресуется четырьмя способами

⬜ не сделано — адресация не унифицирована: `--db` принимают 18 листов, `--runs-dir` — 21,
`--run-id` — 17, и пара `--run-yaml`+`--package` по-прежнему обязательна вдвоём
(`plan --run-yaml … --package …`; без `--package` — `error: the following arguments are
required: --package`). Закрыт **один** из трёх подпунктов: «нет команды показать прогоны» —
✅ сделано (`core/cli/commands/runs.py`, `core/cli/commands/status.py`, `35e4373`);
`hound runs` печатает таблицу/`--json`, пропуская БД чужой схемы пометкой `skipped`.

Прогон можно назвать: `--db PATH`, `--runs-dir DIR --run-id ID`, `--run-yaml FILE --package
DIR`, и **позиционными аргументами** (`diff run_a run_b`). Матрица из парсера:

| команда | `--db` | `--runs-dir` | `--run-id` | `--run-yaml` | `--package` |
|---|---|---|---|---|---|
| `resolve` | **обязателен** | — | — | — | — |
| `plan` | — | — | опционален | **обязателен** | **обязателен** |
| `run` | опционален | опционален | опционален | **обязателен** | **обязателен** |
| `report`/`review`/`gate`/`promote`/`golden`/`sensitivity` | опционален | опционален | опционален | опционален | опционален |
| `diff` | опционален | опционален | — | — | — (позиционные) |

Следствия, проверенные вызовами:

- **`--run-yaml` и `--package` избыточны.** `plan --run-yaml packages/ru-pg-dbms/run.yaml`
  → `error: the following arguments are required: --package`. Пакет — это каталог, в котором
  лежит run.yaml; второй флаг не добавляет информации, но обязателен в 5 командах.
- **Нет команды «показать прогоны».** `report --runs-dir runs` → `usage: --runs-dir требует
  --run-id`. При этом в `runs/` сейчас 18 прогонов, а `run_id` требуют 16 команд. Единственный
  способ узнать идентификатор — `ls runs/`. Это не мелочь: идентификатор, который нельзя
  обнаружить, — это идентификатор, который придётся копировать руками, и однажды скопируют
  не тот.
- `diff` — единственная команда с позиционными аргументами; всё остальное через `--run-id`.

### 2.2 Идентификаторы майлстоунов внутри пользовательских флагов

✅ сделано (`core/cli/commands/plan.py:36`, `4acb5aa`) — флаг удалён, а не переименован:
`plan --dry-run` теперь `exit 2 / unrecognized arguments: --dry-run`, поля `dry_run` в
`--json` нет вовсе. Докстринг называет причину («флаг ничего не менял»).

```
plan --dry-run   help="линт + план без записи (состояние W5: запись черновика — W10/T10.4)"
```

Проверено: `--dry-run` у `plan` меняет **ровно одно поле JSON** и ничего больше.

```
$ diff <(plan --json) <(plan --dry-run --json)
4c4
<     "dry_run": false,
---
>     "dry_run": true,
```

Это флаг, оставшийся от плана работ, который не случился. Он не пишет, не читает, не
влияет ни на что — но занимает место в интерфейсе и обещает поведение, которого нет.
Хуже: сам `plan` объявляет `"dry_run": false` при том, что он **никогда не пишет**. Семантика
перевёрнута: поле говорит «не сухой прогон» о команде, которая только и делает, что сухой прогон.

### 2.3 Одна и та же вещь называется командой и фазой

⬜ не сделано — расхождение осталось дословным: `plan`/`review`/`report`/`run` есть и в
`PHASES` (`core/pipeline/runner.py`), и как команды; `run --until` принимает **все** 15 фаз
включительно с `plan` (`core/cli/commands/run.py:1387`), то есть «посмотреть план без записи»
и «записать прогон до фазы plan» по-прежнему две команды с одним словом.
Статус `status` называет следующую команду — это отвечает на «что дальше», но не устраняет
двоение имён.

`PHASES` = 15 фаз: `normalize, lint, plan, g1, discovery, g2, registry, inheritance, corpus,
evaluate, review, g3, compute, g4, report`.

Четыре из них существуют одновременно как **фаза** и как **команда**: `plan`, `review`,
`report`, и `run` (который эти фазы исполняет). При этом:

- `hound plan` **не пишет** (документировано: «без записи»);
- `hound run --until plan` **пишет** БД прогона и возвращает `run_id`.

Две команды с одинаковым словом в названии, одна из которых создаёт состояние, а другая нет,
и **из имён это не выводится**. Пользователь, который хочет «посмотреть план», выбирает
между ними наугад.

Остальные 11 фаз отдельными командами недоступны — то есть правило «фаза = команда»
не выполняется ни в одну, ни в другую сторону. Это не архитектура, это осадок истории.

2026-10-28, два разных способа «прогона нет»:

| команда | БД-файла нет | БД есть, строки прогона нет |
|---|---:|---:|
| `report` | 4 | **2** |
| `review` | 4 | **2** |
| `sensitivity` | 4 | **2** |
| `diff` | 4 | 4 |
| `status` | 4 | 4 |

То есть `35e4373` закрыл **один** путь: отсутствующий файл БД → `EXIT_NOT_FOUND`

Для скрипта это одно и то же событие с двумя кодами — в зависимости от того, кто создал файл.

Историческая часть ниже (проверка на момент разбора):

Объявлено пять кодов: `0 ok`, `1 error`, `2 usage`, `3 blocked`, `4 not_found`.

Проверено вызовами:

| ситуация | код |
|---|---|
| `report --runs-dir runs` (нет `--run-id`) | 2 |

`EXIT_NOT_FOUND` используется только в `resolve` и `crawl`. Для прогона — самой частой
сущности — «не найден» неотличим от «неправильно вызвал». Скрипт, который гоняет прогоны,
не может отличить «подожди, прогон ещё не создан» от «ты опечатался».

### 2.5 `package` — не команда, а ящик

⬜ не сделано — 25 подкоманд второго уровня (столько же, сколько в разборе) и **50** листьев
под `package`; четыре CRUD-семейства на месте: `module` 6, `role` 5, `param` 5, `baseline` 5
листьев `add/get/list/remove/update` (`core/cli/package/parser.py`). `index-gc`, `builds-gc` и
`crawl-probe` остались в пакете. Подпункт «READ/WRITE выражен единообразно» не закрыт, а
ухудшился: `--dry-run` у **27** листьев, `--apply` у 3 (`package add-product`, `package
index-gc`, `package builds-gc`), `--write` у 2 — и он по-прежнему значит разное: «записать
JSON-план в файл» (`package candidates`, `core/cli/package/parser.py:528`) против «внести измеренные оси в
`domain_profiles.yaml`» (`package crawl-probe`, `:668-671`).

25 подкоманд, из них:

- **4 семейства с идентичной CRUD-формой** — `module`, `role`, `param`, `baseline`:
  `add / update / remove / list / get`. Это **24 листовых команды**, отличающихся только
  именем CSV-файла. Правило одно, скопировано четыре раза.
- **три подкоманды вообще не про пакет**: `index-gc` (прунинг индексных сборок),
  `builds-gc` (прунинг композиций), `crawl-probe` (зонд осей краула). Они попали сюда
  потому, что «работают с чем-то, что лежит рядом».
- **`add-product`** внутри себя делает SERP + scout + ключи доменов — это конвейер,
  а не операция над пакетом.
- READ/WRITE не выражен единообразно: `--apply` (3 раза), `--dry-run` (6 раз),
  `--write` (2 раза), причём **`--write` в двух местах значит разное**: в `crawl-probe` —
  «записать JSON-план в файл», в другом месте — «действительно записать».

Половина подкоманд имеет в help слова «без записи» — то есть пользователь должен читать
описание каждой, чтобы понять, изменит ли она файлы.

## 3. Что из этого следует для сценариев

⬜ не сделано — сценарий остался девятишаговым. Частичный ответ появился: `hound status`
печатает **готовую** следующую команду (`core/cli/commands/status.py`, `_run_command`), поэтому
«собирать команду руками» больше не нужно. Но вызовов не убавилось: решения гейтов по-прежнему
отдельные (`gate`), а `run` в каждом вызове требует `--run-yaml` + `--package` (+`--urls`).

Регламент описывает сценарии Ш1–Ш9 и четыре гейта. Реальная работа оператора выглядит так
(собрано из runbook и из этой сессии):

```
plan → run (падает на g1) → gate G1 → run (падает на g2) → gate G2 → run
     → … → gate G3 → run → gate G4 → run (report) → review
```

**Девять вызовов**, из которых четыре — ручные решения, и каждый требует `subject_digest`,
который лежит в `runs/{run_id}/gates/{gate}-request.json`. Между вызовами нужно помнить
`run_id`, `--package`, `--run-yaml` и `--urls`, потому что без них прогон не продолжится.

При этом ни одна команда не отвечает на вопрос «где я и что дальше». `run` печатает
`stopped_at: g1` и подсказку, но подсказку надо прочитать и собрать команду руками.

Между тем это ровно то, что можно спросить у системы: **состояние прогона + следующее
действие**.

## 4. Предложение

Не «причесать флаги», а сменить единицу проектирования: **сценарий вместо фазы**.

### 4.1 Один способ адресовать прогон

⬜ не сделано — из трёх команд сделаны две: ✅ `hound runs` (`core/cli/commands/runs.py`) и
✅ `hound status <run_id>` (`core/cli/commands/status.py`, `35e4373`). Третий пункт —
`hound run --package <dir>` без `--run-yaml` — не сделан, и «убрать `--db`/`--runs-dir`/
`--run-id` у 16 команд» не начато: флаги не только на месте, их стало больше
(`--db` у 18 листов, `--runs-dir` у 21, `--run-id` у 17).

`run_id` — единственный идентификатор. Всё остальное выводится:

```
hound runs                       # список прогонов: id, пакет, фаза, статус, время
hound status <run_id>            # где прогон, что дальше, какая команда это делает
hound run --package <dir>        # run.yaml берётся из пакета
```

`--db`, `--runs-dir`, `--run-id` как отдельные флаги у 16 команд — убрать. Каталог прогонов —
один, из раскладки (`paths.py`), переопределяется переменной окружения, а не флагом в каждой
команде.

### 4.2 Фаза не равна команде

⬜ не сделано — `hound plan` остался на месте (и не переименован), `run --until plan` остался
(`core/cli/commands/run.py:1387`, `choices=PHASES`), `review` и `gate` — отдельные команды, а не
фазы, `hound approve`/`hound reject` не появились. Сделана только читающая часть сценария —
`hound status <run_id>`, которая печатает готовую команду продолжения.

Пользователю нужны не 15 фаз, а три операции:

```
hound run --package X [--until PHASE]     # исполнить (в т.ч. продолжить с места)
hound status <run_id>                     # прочитать состояние и «что дальше»
hound report <run_id>                     # артефакты
```

`hound plan` остаётся (это полезно — «что получится»), но переименовывается в то, чем он
является: **`hound plan` — сухой прогон без записи**, и тогда `run --until plan` не нужен
вовсе (он и есть `plan`, но с записью; пусть запись будет отдельным явным флагом
`--save`, если понадобится).

`review`, `gate`, `compute` как отдельные команды не нужны: это фазы. `gate` нужен, потому
что это **решение человека** — но он должен называться так, как в жизни: `hound approve` /
`hound reject` с `--actor` и `--notes`, а не `gate --gate G1 --verdict approved`.

### 4.3 Гейты: одно действие вместо четырёх флагов

⬜ не сделано — `hound approve`/`hound reject` отсутствуют. Один из четырёх аргументов
§4.3 закрыт: `--subject-digest` больше не нужен руками — по умолчанию берётся из
`runs/{run_id}/gates/{gate}-request.json` (`core/cli/commands/gate.py:76-92`). Осталось
обязательным: `--gate` (choices G1–G4) и `--actor`; `--verdict` по умолчанию `approved`
(`:232-237`). Действие по-прежнему называется `gate`, а не глаголом решения, и предмет всё
равно передаётся косвенно (`--gate`), а не выводится из состояния прогона.

Сейчас: `hound gate --gate G1 --actor X --subject-digest D --verdict approved --notes "…"`.

Предложение:

```
hound approve --package X --note "…"      # одобрить то, что сейчас ждёт решения
hound reject  --package X --note "…"
```

Гейт, предмет и дайджест **определяются из состояния** — система знает, на каком гейте
стоит прогон и какой у него `subject_digest`. Передавать их руками значит позволять
записать решение не о том предмете; сейчас это защищено сверкой дайджеста, но цена —
четыре обязательных аргумента на каждое решение.

### 4.4 `package` разложить по существу

⬜ не сделано — `package edit <artifact>`/`store gc` не появились (ни одного листа с именем
`store`), `add-product`/`scout` остались в `package`. ✅ `scope attest|show` существуют, но
сделаны до этого разбора и не им (`c232e70`), т.е. как исполнение §4.4 не считаются.

```
hound package new|show|validate|list        # пакет как целое
hound package edit <artifact>               # один редактор артефактов: module/role/param/
                                            #   baseline/cohort/golden — вместо 24 листьев
hound package scope attest|show             # аттестация (I2b/I2c)
hound package adopt product|candidates      # пополнение когорты (add-product/scout/apply)
hound store gc [--builds|--compositions]    # index-gc/builds-gc — это хранилище, не пакет
```

`edit <artifact>` с общим набором `--add/--set/--remove/--list/--get` заменяет 24 команды

### Команды «только для чтения» создают БД
