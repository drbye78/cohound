# Довести Ш6 до конца: класс сбоя ячейки и повторная попытка оценки

**Дата:** 2026-11-07 · **Повод:** живой прогон `ru-pg-dbms-2a5b51af5778`.

Дефект: 674 из 905 ячеек остались без вердикта, потому что оценщик был недоступен
30 минут. Факт сбоя **записан**, но класс сбоя в машиночитаемом виде не записан, и
механизма «попробовать эти ячейки ещё раз» нет. Оператор видит `failure_rate` и
`cells_by_state.failed = 674`, но не видит, что 312 из них — недоступность оценщика,
а 362 — отсутствие корпуса.

## 1. Что измерено (07.11.2026, стенд `~/.cohound/stands/ru-pg-dbms`)

| факт | значение | источник |
|---|---|---|
| ячеек всего / с вердиктом / без | 905 / 231 / 674 | `cohound.db:cells` |
| без вердикта, `failure_kind` **NULL** | **312** | `cells` |
| без вердикта, `failure_kind=no_sources` | 362 (`jatoba` 181, `pangolin` 181) | `cells` |
| текст причины у 312 | `оценщик недоступен: EvaluationError: HTTP-вызов оценщика не удался: HTTP 503` | `cells.validation_notes` |
| вызовов оценщика / из них `http_error` | 1 187 / 957 | `logs/llm_calls.jsonl` |
| окно недоступности endpoint | 15:40:30 → 16:10:59 UTC | журнал |
| цена одной ячейки | 36.5 с при 1 в полёте; 2.95× при 4 | `2026-11-07-llm-concurrency-scaling.md` |

Отсюда цена повторной попытки: 312 ячеек ≈ **1.1 ч** при `--llm-concurrency 4`,
674 (если `jatoba`/`pangolin` уже имеют корпус) ≈ 2.4 ч.

## 2. Дефект: класс сбоя не доходит до ячейки

`cells.failure_kind` пишется **двумя** путями и не пишется третьим:

- сбой ретривала — `_record_cell_failure(store, failed, SEARCH_FAILED)`
  (`core/pipeline/evaluate.py:4115`);
- отсутствие источников — тот же вызов (`:4024`);
- **сбой оценщика — не пишется вовсе.** `_unresolved_outcome` (`:3318-3357`) знает класс
  (`kind`) и возвращает его в `EvaluationOutcome.failure_kind`, но `_persist` в нём
  сохраняет только саму ячейку: колонка остаётся NULL.

Следствие: класс сбоя живёт только свободным текстом в `validation_notes` и в
`evidence_scope.denial_strength = instrument_failed`. Машина его не читает, и
`cell_diagnostics.csv` (единственный артефакт, куда такие ячейки попадают) не имеет
колонки класса.

**Это не «нет данных» — это данные без адреса.** I4 при этом не нарушен: `state=failed`,
`status=NULL` — вердикта нет, и он не выдумывается.

## 3. Дефект: повторной попытки нет ни у одной команды

| путь | почему не подходит |
|---|---|
| `hound run --reset --until evaluate` | перемеряет **все** 905, включая 231 уже оценённую: 9 ч вместо 1.1 ч, и это новое измерение уже измеренного |
| `hound revalidate` | `select_stale_cells` возвращает только `stale_reason is not None`, а `_stale_skip_reason` отвергает `failed` (`STALE_SKIP_STATE:failed`) — ячейка без вердикта невидима для ремонта |
| `--only-failed` | это работа краула (FAILED-элементы сеанса), к ячейкам не относится |

## 4. Решение: команда `hound retry`

Отдельная команда на **существующем** `run_id`, по образцу `revalidate` и по его же
аргументу: флаг прогона, сужающий набор измеряемых ячеек, обязан войти в
`execution_contract_digest` (иначе под одним `run_id` живут разные наборы), а доведение
недоделанной Ш6 до конца условий измерения не меняет. `run_id` не меняется, новый не
создаётся.

**Почему не флаг `hound run`.** Тогда `--reset --until evaluate` значил бы «перемерить
всё» либо «дооценить недоделанное» в зависимости от скрытого состояния карты ячеек —
ровно то неявное поведение, которое запрещено (A3: видимое число вместо тихого режима).

**Почему не расширение `revalidate`.** У `revalidate` правило сохранения пометки — «снять
`stale_reason` только при вердикте по текущей сборке». У `failed`-ячейки пометки нет, а
есть `state=failed` и класс сбоя; смешать два правила в одном отчёте значит потерять
различие «устарело» / «не измерено».

### 4.1. Что записывается (половина «фиксировать факт»)

1. `cells.failure_kind` — на **единственном** write-site (`_persist`) для любого
   `failed`, включая сбой оценщика. Буфер записи (`_CellWriteBuffer`) получает
   `record_cell_failure`, иначе параллельный путь Ш6 потеряет класс.
2. `outputs/cell_diagnostics.csv` — колонка `failure_kind` (машиночитаемо, рядом с
   `validation_notes`).
3. `metrics.json` — блок `cells_by_failure_kind` (сколько ячеек и почему без вердикта).
4. `logs/retry.jsonl` — по строке на попытку: `run_id`, `product_id`, `param_id`,
   `attempt`, `outcome`, `failure_kind`, `duration_s`. Журнал вызовов модели
   (`logs/llm_calls.jsonl`) пополняется тем же путём, что у Ш6.

### 4.2. Кого выбирает селектор `select_failed_cells`

Только `state=failed` и `source_kind=documentation` (вердикты чужих контуров не
переписываются). `evaluated`/`reviewed`/`preliminary` не возвращаются никогда.
Внутри — класс сбоя:

| класс | повторяемо? | почему |
|---|---|---|
| `evaluation_failed` | **да** | отказ инструмента: сеть/5xx/таймаут; следующий вызов может дать вердикт |
| `validation_failed` | **да** | ответ не прошёл эшелон §10; новый сэмпл может пройти |
| `search_failed` | **да** | сбой ретривала — прибор, не корпус |
| `no_sources` | **только если у продукта сейчас есть корпус** | иначе повтор даст тот же `no_sources`; факт называется `corpus_absent`, а не «попробовали» |
| `failure_kind IS NULL` + `evidence_scope.denial_strength=instrument_failed` | **да** | так выглядят прогоны до этой правки (312 ячеек) |
| `failure_kind IS NULL` без признака | нет | класс не записан — не выдумываем |
| прочее (`not_found`, `robots_disallow`, `payload_too_large`, …) | нет | терминальный класс: тот же вход даст тот же исход |

Отказ по каждой неотобранной ячейке **называется** (`skipped_cells` с причиной), а не
растворяется в счётчике.

### 4.3. Что делает попытка

Тот же конвейер, что Ш6 (`retrieve_for_cell` под условиями **самой ячейки** → промпт →
оценщик → эшелон §10), с `--llm-concurrency` (буфер записи + `replay`, как в фазе):

- вердикт получен → ячейка перезаписывается `state=evaluated`, `stale_reason=None`,
  `failure_kind=NULL`; класс сбоя **снимается** — иначе карта показывала бы сбой у
  измеренной ячейки;
- снова нет вердикта → `state=failed`, `status=NULL` (I4), `failure_kind` обновляется,
  в `validation_notes` добавляется маркер попытки (`retry:attempt=N`), старая причина
  сохраняется;
- `index_build_id` пишется текущий: вердикт описывает текущую сборку.

Модель оценщика — **объявленная** (`llm_scenarios` прогона), не из флага и не из env
(I21/§7.4). Endpoint/ключ/таймаут — операционные, из deploy/env.

### 4.4. Отчёт и код возврата

`failed_total / retryable / retried / recovered / still_failed / skipped`, построчно —
что стало с каждой ячейкой. Код возврата: `EXIT_OK` — все отобранные получили вердикт
либо отбирать было нечего; `EXIT_ERROR` — попытки были, вердикта нет ни у одной
(«не прошло» — валидный исход, но не успех). Частичный успех — `EXIT_OK` с числами:
оператор видит остаток и повторяет команду.

## 5. Чего здесь нет (осознанно)

- **Фаза `evaluate` не становится resume-aware.** «Пропускать уже оценённые ячейки при
  повторном входе в фазу» — отдельное решение: оно меняет смысл прогона фазы (полный
  проход ↔ достройка), а не только добавляет команду. Названо, не сделано.
- **Никакого порога числа попыток** (A3: не ограничивать, а измерять): команда
  идемпотентна, оператор решает, сколько раз её позвать; каждая попытка видна в журнале.
- **`evaluated`-ячейки не пересчитываются** даже при `--reset`: повтор уже полученного
  вердикта — новое измерение, и оно остаётся за `run`/`revalidate`, а не за ремонтом.

## 6. Проверка

Тесты (см. реализацию): класс сбоя доезжает до `cells.failure_kind` на пути фазы;
селектор отбирает ровно повторяемые классы; `evaluated` не трогается (шпион на
оценщике); `no_sources` без корпуса — `corpus_absent` без вызова модели; успешная
попытка снимает класс; неуспешная обновляет и сохраняет старую причину; `run_id` не
меняется; повтор без провалов — no-op.
