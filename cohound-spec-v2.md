# coHound — методологический регламент и технический проект (v2.1)

**Статус:** основание для детального проектирования и реализации (MVP).

**Кодовое имя:** **coHound** (утверждено; «co-» = competitive intelligence / cohort comparison; «hound» = идёт по следу до исчерпанного протокола). Товарные знаки и домены — отдельной задачей до внешнего запуска, M0 не блокирует.

## 0. Руководящие аксиомы

**A1. Сначала доказательство ценности, потом оптимизация.** Сначала доказать, что coHound воспроизводимо получает качественную сравнительную карту на маленьком корпусе детерминированными и минимальными средствами; только потом оптимизировать ретривал, масштабирование и инфраструктуру. Следствие: правдоподобная, но дорогая инфраструктура не берётся «на вырост» — только по измеримому триггеру (§14).

**A2. Moat — методология измерения, не AI-пайплайн.** Конкурентное преимущество — семантика каталога, absence/inheritance-правила, сателлитная модель, evidence-модель, политика валидации, модель ошибок, воспроизводимость. Ретривал, LLM, хранилища — заменимые commodity. **Правило:** если реализация требует изменить методологию — это сигнал об ошибке в реализации; если commodity-слой протекает в evidence-модель (например, внешний поиск внутри оценщика) — это изменение методологии, а не оптимизация.

**Правило замыкания A2 ↔ A3.** A2 запрещает **неявный и commodity-driven** дрейф методологии (смена правил как побочный эффект реализации, удобства кода или оптимизации commodity-слоя). A2 **не запрещает** *measurement-driven* эволюцию методологии: если измерение (sensitivity, golden, ручная калибровка §11.5) показывает неверность методологического элемента, он меняется — но **только явно, через версионную границу §13** (bump `methodology_version`/`scoring_policy_version`, обязательный `golden-full`, при необходимости — пере-аннотация golden). Иными словами: любой предикат или порог, влияющий на публикуемый вывод, обязан быть **определён в регламенте/словаре до реализации**; код — только исполнение. Изменение методологии — решение владельца методологии, а не следствие правки кода.

**A3. Эпистемология единообразна на всех уровнях** — включая инфраструктурные выборы: «установлено» отличается от «предположено» не только в ячейках, но и в регламенте. Дефолты помечаются как assumption/candidate; замена дефолта происходит по измерению, не по предвидению. Следствие: выбор модели, ретривал-профиля, порогов и раскладки индекса — измерительные задачи, а не предрешения.

**Операционализация A3.** Требование «дефолты помечаются» проверяемо: `run_manifest.yaml` обязан для каждого **тюнящегося** параметра (модель под сценарий, `retrieval_profile`, `retrieval_cutoff_K`, `retrieval_params_json`/fusion, пороги, `partial_score`, `unknown_policy`) нести признак происхождения значения — `provenance: default | measured`. Для `measured` — ссылка на измерительный прогон (`experiment_id`/`golden_run_id`). Иначе невозможно доказать, что значение было *предположением* (а не измерением), и R7 вырождается. Это §13-граница: введение признака = минорный bump `methodology_version`.

## 1. Назначение, границы, режимы

### 1.1. Назначение

coHound принимает четыре входа — **якорь, каталог параметров, перечень продуктов (когорта), фокус сравнения** — и производит сравнительную техническую карту программных продуктов.

**Философия:** coHound не пытается узнать «истину о продукте». Он измеряет **степень публично доказуемой функциональности по фиксированному протоколу** и строит воспроизводимую карту того, какие утверждения о продукте можно подтвердить публичными доказательствами — отдельно показывая: что подтверждено (Resolved Capability), насколько полно исследовано (Coverage), где осталась неопределённость (❓ / NDA-вопросник), почему сделан вывод (evidence), насколько результат сопоставим (Comparability-аннотация).

Свойства карты: каждый статус имеет публичную проверяемую ссылку или детерминированный вывод; «не установлено» (❓) отличается от «подтверждённое отсутствие» (❌) и «неприменимо» (N/A); функции сателлитов засчитываются корректному компоненту; все продукты оцениваются по одинаковым правилам; покрытие публикуется рядом с баллом.

### 1.2. Не-цели

coHound не является: нагрузочным бенчмарком · заменой PoC внедрения · юридическим заключением о сертификации · заменой NDA-опросника (он его *готовит*) · источником рейтинга без покрытия · системой, утверждающей что-либо о функциональности сверх публично доказуемой.

### 1.3. Категорийная нейтральность

Ядро (`core/`) не содержит терминологии предметных категорий; вся специфика — пакет категории (данные). CI-грепп-тест. Переносимость — приёмочное требование MVP (§11.4): пять кейсов **портфеля** дают **первичное эмпирическое подтверждение** гипотезы нейтральности (формулировка сознательно не «доказательство»).

### 1.4. Режимы прогона

Одна политика обработки валидации, не два конвейера: невалидированный отклик в strict → failed, в preliminary → кандидат.

| | **strict** (публикационный) | **preliminary** (аналитический) |
|---|---|---|
| Назначение | Итоговые карты, баллы, публикация | Рабочий материал; предварительный этап к окончательной оценке; место для интерпретации |
| Цитатная валидация | Обязательна (механическая) | Не обязательна; mismatch → `validation_notes` |
| ❓ | После исчерпания полного протокола (I3) | Допустим по сокращённому (`protocol: partial`, I3b) |
| ❌ | По absence-правилу параметра: `registry_absence` — по построению; `explicit` — явное отрицание; `parameter_reference`/`distribution_absence` — + `source_scope: exhaustive` (I2, I2b) | Кандидат-отрицания (помечены) |
| Inheritance conditional | Через ревью | Автоматический кандидат |
| В расчётах | Да | **Нет — I13** |
| Артефакт | `battle_card.xlsx` | `preliminary_findings.xlsx` |

Инвариантно: N/A только человеком · URL только системный резолв · failed никогда не статус · границы зачёта только из каталога · равное усилие · строгая переаттестация при promote. Preliminary-статус никогда не повышается автоматически; цикл кандидата: `promote · set-status (actor=human) · fix-evidence · reject`; пакетно `promote --validated-only`.

### 1.5. Архетипы категорий

Категории различаются наличием сильного OSS-upstream (архетип), что определяет применимость наследования:

| Архетип | Признак | Наследование | Калибровочный пол |
|---|---|---|---|
| **A** | Явный OSS-лидер — общий upstream | `baselines.csv` per-продукт | базлайн-участник (если существует) |
| **B** | Несколько OSS-альтернатив + коммерческие на их основе | матрица «параметр × базлайн»; кросс-линейные — только корпус | базлайн-участник (если существует) |
| **C** | Без сильного OSS-лидера | не заполняется (осознанно; непустой `baselines.csv` — **ошибка линтера**, §4.2) | **эталона нет и не вводится**; golden + дисциплина правил; сопоставимость несёт Comparability-аннотация |

Минимум один кейс на архетип. Каждый кейс = пакет категории + прогон чеклиста нейтральности v2 (§11.4). Объём, состав портфеля и порядок этапов — `docs/architecture/06-implementation-strategy.md`.

### 1.6. Когорта и якорь

**Когорта** — фиксированный на цикл перечень продуктов (якорь + 6–10 аналогов), формируемый по декларируемым правилам и **замораживаемый на гейте G1**:

1. отбор идёт из одного функционального класса (перекрытие якорных ролей ≥ порога, зафиксированного в пакете);
2. приоритет продуктам с публичной документацией (иначе весь кейс вырождается в ❓/NDA);
3. в когорту включается базлайн-участник, если он существует (архетипы A/B);
4. состав, обоснование включения/исключения и связи с якорем записываются в `packages/{case_id}/cohort.yaml` (`product_id`, `role_overlap`, `selection_reason`, `anchor_relation`);
5. смена состава когорты после G1 = новый цикл (межцикловый diff запрещён, §13).

**Якорь** — это не базлайн и не вес. Его операциональная роль строго ограничена: (а) задаёт ось и порядок изложения отчёта; (б) задаёт фокус по умолчанию, если `focus` не передан; (в) оценщики **anchor-blind** (§2.2 п.11). Якорь **не влияет** на статусы, веса, нормировку и Coverage. Если реализация придаёт якорю вес — это сигнал ошибки (A2).

## 2. Методологическое ядро

### 2.1. Статусы

| Статус | Семантика |
|---|---|
| ✅ | наличие подтверждено (валидная цитата или детерминированный вывод) |
| ⚠️ | наличие частично/неполно подтверждено либо реализовано ограниченно |
| ❌ | отсутствие непосредственно подтверждено: absence-evidence по absence-правилу параметра, а для `parameter_reference`/`distribution_absence` — ещё и `source_scope: exhaustive` (§4.2) |
| ❓ | после исчерпания предписанного протокола недостаточно доказательств |
| N/A | архитектурно неприменим; только человек |

**Главный инвариант: отсутствие evidence никогда само по себе не является evidence отсутствия.**

### 2.2. Принципы

1. Цитатная дисциплина: strict-✅/⚠️ требуют machine-verified evidence.
2. Равновесные трактовки → меньший статус. Правило применяется **только к наличие-статусам** (✅/⚠️/❌), где порядок «меньше» определён (✅>⚠️>❌). ❓ и N/A — не «меньший» статус, а иное эпистемическое состояние; они не участвуют в понижении по равновесию (перевод в ❓ возможен только через исчерпание протокола, I3; N/A — только человеком, I6/I7).
3. Показательный параметр (класс `showcase`) измеряет **capability + публичную измеримость**: механизм + публичная величина; одно из двух → ⚠️. Это осознанная семантика параметра, декларируемая в каталоге и легенде отчёта — не скрытая documentation bias. Открытость документации публикуется как фактор Comparability (§6).
4. Роли сателлитов: механизм в ядре, наполнение — в пакете.
5. Равный поисковый бюджет = равенство поискового *усилия*, не обнаруживаемости; полный лог. Бюджет (число запросов и время на продукт) зафиксирован в манифесте и залогирован (I23).
6. Ошибка ≠ вердикт: failed никогда не статус.
7. Детерминированное раньше поиска: реестры → наследование → дистрибутив → корпус → SERP.
8. Прямое доказательство старше наследования (П>В): противоречащее свидетельство понижает унаследованный статус → ревью.
9. Resolved Capability без Coverage не является достаточным основанием для сравнения.
10. N/A, границы зачёта, мера частичности — человеческие решения.
11. Якорь — система координат отчёта, не базлайн; оценщики anchor-blind (§1.6).

### 2.3. Инварианты

```
I1   evaluated + ✅/⚠️   → evidence ≥ 1
I2   evaluated + ❌      → absence-evidence по absence_rule параметра
I2b  evaluated + ❌, absence_rule ∈ {parameter_reference, distribution_absence}
                         → на absence-evidence source_scope: exhaustive И scope_attested_by ≠ null
                           (registry_absence — exhaustive по построению; explicit — source_scope не требуется)
I3   ❓ (strict)         → протокол исчерпан (full) ИЛИ reviewed_by ≠ null
I3b  ❓ (preliminary)    → допустим при protocol: partial
I4   failed              → status = null
I5   failed              → исключена из Capability; ВХОДИТ в знаменатель Coverage как неразрешённая
I6   N/A                 → reviewed_by ≠ null
I7   N/A                 → никогда автоматически
I8   inherited-статус    → правило наследования выполнено (mode учтён)
I9   сателлитная ячейка  → relationship evidence существует
I10  source URL          → системный резолв из source_id
I11  публикуемый балл    → сопровождается Coverage
I12  ❓                 → никогда не трактуется как ❌
I13  preliminary         → исключена из Capability/Coverage/публикации
I14  preliminary → strict → строгая переаттестация или human evidence
I15  source_id → URL     → детерминированный lookup
I16  профиль ретривала (R0/R1/R2, retrieval_cutoff_K, fusion-параметры) → идентичен для всех продуктов цикла
I17  evidence корпуса    → только чанки паспорта продукта и его сателлитов; ретривал продукт-скоупед
I18  оценщик (§7, Ш6)    → не вызывает внешний поиск ни при каком провайдере
I19  внешний контент     → становится evidence только после corpus_raw → extract → chunk → content_hash → index
I20  golden cut-off      → равен pipeline-параметру retrieval_cutoff_K
I21  маршрутизация модели→ детерминирована фазой; таблица scenario→{model_id, version} в манифесте
I22  отсутствие evidence → никогда не evidence отсутствия (главный инвариант, формализован)
I23  поисковый бюджет    → фиксирован и залогирован для каждого продукта
```

### 2.4. Четыре опоры данных

Стабильные slug-ID · версионирование каталогов в git (semver) · словарь статусов как отдельный источник истины · **evidence-объект как единственная единица доказательства** (никакие сведения из внешнего поиска не минуют §4.4).

## 3. Архитектура и технологический стек

### 3.1. Компоненты

CLI-ядро (`resolve · plan · run · diff · sensitivity · golden · report · discover · review · promote · gate · deploy-check`) · нормализатор входов с линтером · Discovery-агент · сборочный контур (краул, экстракция) · индексационный контур (чанкер, гибридный индекс) · движок наследования · реестровые фетчеры · **LLM-контур оценщика** (без поиска) · **search-контур** (SERP-адаптер, допустимо с веб-поиском) · очередь ревью / preliminary-рабочий стол · расчётно-отчётный модуль.

> **Примечание.** Команды `resolve`/`plan`/`run`/`diff`/`sensitivity`/`golden`/`report`/
> `discover`/`review`/`promote`/`gate`/`deploy-check` — **методологическое ядро**. Полная
> CLI-поверхность шире: помимо ядра — команды авторского и операционного контура (`package` с
> подкомандами, `passport-scout`, `doctor`). `gate` — единственная точка записи человеческих
> решений G1–G4 (`gate_decisions`, S9; §4.2); принятие решения о N/A (I6/I7) или аттестации
> `source_scope` без неё невозможно. Актуальный список и семантика — в
> `docs/architecture/03-data-config-cli.md` §E.1 и в коде (`core/cli/`); при расхождении верен код.

**Разделение ролей поиска (ключевое):** поиск в системе существует только как **источник входного контента** (Ш5: краул + SERP), который нормализуется, хэшируется и индексируется. Оценщик (§7, Ш6) **не имеет** доступа к внешнему поиску (I18). Подробности — §7.

### 3.2. Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык / данные | Python 3.14 (**пин-базлайн проекта**; актуальный стабильный CPython на 2026-10 — 3.15, апгрейд — отдельное решение) · YAML+CSV в git · Pydantic | greenfield, контролируемое развёртывание; все зависимости стека имеют cp314/abi3-колёса (`docs/architecture/05-dependency-stack.md` §1) |
| Операционное хранилище | SQLite (WAL, батчевые записи) | встроенное, без внешнего сервиса; соответствует масштабу MVP (A1) |
| **Векторный контур** | **NpyVectorIndex (in-process, brute-force cosine по .npy-шардам + манифест) — дефолт MVP**. Шардирование **по продукту**: `index_store/{package}/{build}/{product_id}/`. Порт `VectorIndex` сохраняется; Qdrant — отложенная подмена по измеримым триггерам (§14) | ретривал продукт-скоупед (I17): запрос не выходит за пределы ~60k чанков продукта и его сателлитов, поэтому brute-force укладывается в рабочие десятки мс |
| **Лексический контур** | tantivy (BM25): **двойной профиль — стеммеры RU/EN + raw-identifier/ngram** для идентификаторов (GUC, утилиты, версии, аббревиатуры). **Проверено (V1, 2026-10-08):** русский стеммер и стоп-слова доступны нативно (`Filter.stemmer("russian")`, `Filter.stopword("russian")`), внешний `snowballstemmer` не нужен | стемминг вредит точным идентификаторам — ровно тем, ради которых лексическое плечо введено; профиль тестируется на retrieval-golden |
| **Ретривал-профиль** | эксперимент в M1: R0=BM25 / R1=dense / R2=RRF-гибрид на retrieval-golden; дефолт фиксируется измерением и записывается в манифест. Параметр `retrieval_cutoff_K` (K единиц, отдаваемых оценщику) входит в профиль | ретривал принимается по evidence, не по предвидению (A3); гипотеза: R2 выигрывает на смешанном RU/EN корпусе — проверяемая, не предрешённая |
| Эмбеддинги | локально, sentence-transformers: **BGE-M3 — основной кандидат** (приоритет RU, EN хорошо; 8192 контекста, dense; MIT); multilingual-e5-large — альтернатива; подтверждение на R9/R10 | **RU — абсолютный приоритет, EN тоже сильный** (целевой корпус RU-вендоров + международные ID/термины); данные не покидают контур; NC-лицензии исключены |
| Краулинг | Scrapy + scrapy-playwright (per-domain рендер-профили); **robots.txt = obey** (при встраивании Scrapy как библиотеки флаг `ROBOTSTXT_OBEY` выставить явно — дефолт False). **V5 (2026-10-08):** scrapy-playwright — зрелый де-факто стандарт (org `scrapy-plugins`, BSD-3, py3.14); **smoke-тест пройден** на Scrapy 2.19 / playwright 1.63 (chromium + firefox) → жёсткий пин подтверждён. `curl_cffi` — первый ярус для антибот-доменов без JS | production-фреймворки; качество извлечения кормит цитатную валидацию; этическая норма §10 |

## 4. Модель данных

### 4.1. Словари и перечисления

`docs/status-dictionary.yaml`: статусы (§2.1) · `source_kind` (registry|inheritance|distribution|documentation|web|manual) · `evidence_type` (direct|derived) · `absence_rule_type` (explicit|parameter_reference|distribution_absence|registry_absence) · `source_scope` (**exhaustive|partial|unknown** — свойство экземпляра источника, поле evidence) · `failure_kind` (search_failed|source_unavailable|evaluation_failed|validation_failed|parser_failed) · `cell_state` (pending|preliminary|evaluated|failed|reviewed) · `run_mode` · `ranking_policy` (capability_ranked|coverage_fallback|unranked) · `gate` (G1|G2|G3|G4) · `capability_policy` (resolved-only-v1) · `unknown_policy` (excluded|unknown_as_zero) · `fetch_mode` (**http|browser**) · `extraction_route` (**auto|html|document**). `unexpected` — **run-level ошибка без ячейки** (системное исключение), в `failure_kind` не входит (S7): `failure_kind` описывает только сбой ячейки.

**Оси сателлита:**

```
origin:          in_house | third_party | upstream | community | unknown
relationship:    bundled | integrated | certified | recommended | external
evidence_state:  verified | claimed
```

**Маппинг на зачёт (Р-2, в ядре) — таблица приоритетов.** Правила применяются сверху вниз, первое совпавшее решает:

| # | Условие | Потолок зачёта |
|---|---|---|
| 1 | `evidence_state: claimed` (любые origin/relationship) | ⚠️ |
| 2 | `origin: community` **и** `relationship: external` | зачёт по интеграционным параметрам не даётся |
| 3 | `relationship ∈ {bundled, integrated, certified}` и `evidence_state: verified` | без потолка (✅ возможен) |
| 4 | `relationship: recommended` и `evidence_state: verified` | ⚠️ |
| 5 | `relationship: external` и `evidence_state: verified` | по `rule` параметра |
| 6 | иначе | по `rule` параметра |

### 4.2. Пакет категории

**package.yaml:** `archetype (A|B|C)` · модули с весами (сумма=100) · реестр ролей (definition, markers, query_patterns RU/EN, core_coverage_allowed, multi_instance) · реестр базлайнов · `baseline_participant` (null для C) · юрисдикции+реестры · языки.

**cohort.yaml:** состав когорты и обоснование (§1.6): `product_id · role_overlap · selection_reason · anchor_relation · frozen_at`.

**catalog.csv (11 колонок):** `param_id` (slug, иммутабельный) · `title` · `module` · `group` · `importance` (Кр|Вж|Баз|Опц) · `param_type` (fact|showcase) · `rule` (граница зачёта) · **`absence_rule`** (тип из словаря; дефолт `explicit`) · `role_binding` · `concept_terms` (структура `{ru: [..], en: [..]}` — детерминированная синонимичная экспансия; **типизирована как map со списками**, а не как строка) · `search_langs`.

**Гносеология absence-правил (согласовано с I2/I2b):** исчерпанность источника — свойство экземпляра, не типа правила, кроме registry:

- `registry_absence` — **exhaustive по построению** (реестр — авторитетная энумерация); отсутствие записи = валидное негативное свидетельство, механически; `scope_attested_by` не требуется;
- `explicit` — явное отрицание вендора; **`source_scope` не требуется** (само отрицание и есть evidence);
- `parameter_reference` / `distribution_absence` — требуют на absence-evidence `source_scope: exhaustive` **и** `scope_attested_by ≠ null` (человек подтверждает: действительно ли справочник полный, документирует ли вендор весь состав); иначе — понижение до ❓.

Следствие фиксируется честно: исчерпанные справочники редки → ❌ остаётся редким статусом в публичном цикле → компенсаторы: NDA-петля, дистрибутивный контур, coverage рядом с баллом. Приёмка требует **демонстрации** работоспособного ❌-пути (R12, §11.3), а не только декларации.

**Сила отсутствия и аттестация (B-4).** Не всякое ❌ эпистемически равно, и это фиксируется явно:
- **Порядок силы:** `registry_absence` (механическая энумерация авторитетного реестра) **>** `explicit` (явное отрицание вендора) **>** `parameter_reference` ≈ `distribution_absence` (обе опираются на человеческую аттестацию полноты справочника). Порядок публикуется в легенде отчёта; `❌` в battle_card сопровождается пометкой **«подтверждённое отсутствие ≠ гарантия отсутствия»** и указанием силы.
- **Аттестация — это человеческое решение, а не поле без владельца.** `scope_attested_by` обязан соответствовать записи в `gate_decisions` (S9): `actor`, `decided_at`, `notes` (какой справочник/источник признан полным). Тем самым процедура и владелец аттестации замыкаются на уже существующий носитель аудита; отдельного поля-строки без аудит-следа недостаточно.
- Остаточный риск (редкость исчерпанных источников, недокументируемость слабых зон) остаётся признанным; числовая мера этого риска — не вводится (качественная аннотация).

**baselines.csv:** `(baseline_id, param_id, min_version, inheritance_mode, note)`; режимы `direct` (дефолт для ядровых: upstream ≥ min_version + отсутствие явного исключения) · `conditional` (расширения/дистрибутивные: ревью/кандидат) · `blocked` (upstream-факт не используется). Отсутствие строки = кросс-линейный параметр (архетип B): только корпус. **Наследование переносит возможность проверить применимость upstream-факта, но не является автоматическим доказательством наличия функции в downstream-продукте.**

**Derived-evidence наследования и сателлитов (K5, контракт).** Унаследованный статус обязан нести evidence (I1/R2), но это evidence **производного** типа:

- `evidence_type: derived`; `source_kind: inheritance`;
- носитель — запись `cell_evidence` с ссылкой на upstream-паспорт/строку baselines и, где возможно, на корпусный чанк upstream-продукта (`source_id`); если чанк недоступен — на паспортный `Citation` upstream (`source_id = upstream://{baseline_id}#{param_id}`);
- derived-evidence **обязан резолвиться** через `source_url` (I10/I15) и `content_hash` (I19): паспортный `Citation` при внесении в прогон проходит нормализацию Ш5 (в `corpus_raw` продукта-сателлита/upstream) либо фиксируется как `source_kind: manual` с явной пометкой и `scope_attested_by`.

**Сателлиты как партиции (K5/I17).** Сателлит — это `component` с ролью, а не самостоятельный `product_id`. Чтобы I17 сохранялся, документы сателлита индексируются **в партицию продукта-владельца** (тот, у которого он в паспорте), с привязкой `role` в метаданных чанка; `VectorQuery.product_ids` для продукта включает партиции продукта и (при наличии) его сателлитовых доменов. `relationship_evidence` услуги сателлита — паспортный объект, не cell-evidence, но подчиняется тем же правилам provenance (резолв + hash). I9 остаётся: сателлитная ячейка требует relationship evidence.

**golden.csv:** `product_id, param_id, expected_status, expected_evidence_kind, case_class, note`; проверка kind — вхождение в допустимый набор. **Тиры:** `golden-fast` (~30, каждый PR) · `golden-full` (100–200: смена модели/правил/каталога, релиз). **Состав golden-full обязан включать страту ожидаемых ❌** (через `registry_absence` и `distribution_absence`) — иначе критический класс false-❌ нечем тренировать. **adversarial/** — страницы-ловушки; R8 — регрессионный gate, не заявление о безопасности.

**Линтер (блокирует прогон):** уникальность slug; разрешимость FK; валидность enum; showcase → rule упоминает величину; веса=100; ссылки baselines; `absence_rule` из реестра; **ошибка** при непустом `baselines.csv` для архетипа C; warning при пустых `concept_terms`; **ошибка** при `absence_rule ∈ {parameter_reference, distribution_absence}` без действующей процедуры аттестации `source_scope`.

### 4.3. Паспорт продукта

`passports/{product_id}/{YYYY-MM-DD}.yaml`. **Precision-first:** Discovery не устанавливает принадлежность компонента продукту без relationship evidence; доказываются две независимые вещи — существование и связь в роли.

```yaml
product_id: pangolin
canonical_name: "Platform V Pangolin"
vendor: "СберТех"
upstream: {baseline_id: upstream-pg, version: "16", evidence: {url, quote}} | null
edition_assessed: "Enterprise"
version: "6.2"
jurisdiction: RU
doc_domains: ["platformv.sbertech.ru/docs/products/pangolin"]
satellites:
  - role: backup
    component: "Platform V CopyWala"
    origin: third_party
    relationship: bundled
    evidence_state: verified
    relationship_evidence: {url, quote}
    state: approved                  # draft | approved | edited_by_human
    rejected_candidates: [{name, reason}]
  - role: management_console
    state: not_found                 # ❓ на уровне роли; протокол в логе
snapshot_date: 2026-06-01
```

Кэш `(product_id, role, snapshot_date)`; глубина сателлита = 1; G2 подтверждает relationship. **Сравнение редакций/версий:** сопоставимы только ячейки с совпадающим `edition_assessed`; расхождение редакций — флаг Comparability (§6), а не молчаливое сравнение.

## 5. Конвейер

```
Ш1  Нормализация входов, линт, план (scope, роли, когорта, перенормировка)  ── ГЕЙТ G1
Ш2  Discovery: по ролям scope, precision-first (search-адаптер допустим)     ── ГЕЙТ G2 (relationship)
Ш3  Реестровая волна (без LLM) → R-ячейки
Ш4  Волна наследования: по baselines.csv при совпадении upstream;
    direct → статус · conditional → ревью/кандидат · blocked → пропуск (без LLM)
Ш5  Корпус: краул (доменные профили: fetch × extract) / SERP → экстракция → дедуп → чанкер
    → tantivy + батч-эмбеддинги → .npy-продукт-партиции → index_manifest
    (весь внешний контент здесь получает source_id и content_hash — I19)
Ш6  Оценка per (продукт × параметр), оценщик БЕЗ внешнего поиска (I18):
      запросы = {title + concept_terms RU/EN} (≤3)
      → ретривал по зафиксированному профилю (R0/R1/R2), продукт-скоупед (I17)
      → топ-K чанков (K = retrieval_cutoff_K, I20)
      → LLM-оценщик (source_id + quote) → механическая валидация:
          strict:      прошёл → evaluated · не прошёл → failed (retry ≤2)
          preliminary: прошёл → evaluated · не прошёл → preliminary-кандидат
      корпус недостаточен → SERP-протокол через search-адаптер (в Ш5), затем повторный Ш6
Ш7  Очередь ревью / preliminary-рабочий стол                       ── ГЕЙТ G3
Ш8  Расчёт: Resolved Capability + Coverage (+модульные)            ── ГЕЙТ G4
Ш9  Отчёты: battle_card · preliminary_findings · nda_questions · diff · manifest
```

**SERP-раунды и иммутабельность корпуса (K2).** Иммутабельность индексной сборки относится к
*содержимому* продукт-партиции, а не к числу раундов. Корпус append-only и версионируется по
раундам: базовый раунд (краул/документация) — `index_build_id R0-base`; каждый SERP-раунд, доливающий
внешний контент, порождает **новую** сборку (`R1-serp`, `R2-serp`, …) с полным сохранением предыдущих.
После долива раунда инвалидируются только **затронутые** ячейки (те, чей срез ретривала изменился);
они помечаются `stale_reason='new_build'` и переоцениваются на новой сборке. Полная переоценка когорты
не требуется и не запрещена — определяется политикой прогона. Сборка никогда не мутируется на месте:
либо новый `index_build_id`, либо ячейка остаётся привязанной к своей (непереоценённой) сборке с явной
пометкой устаревания. «Повторный Ш6» идёт **по уже проиндексированному** контенту новой сборки.

Протокол исчерпания — машиночитаемый объект; ❓ = «протокол исчерпан, evidence недостаточно». Правило П>В действует на Ш6 поверх унаследованных статусов. **Реконсиляция когорты:** роль найдена у большинства и не найдена у одного → прицельный повтор тем же протоколом; **«большинство» определено над базой = когорта минус продукты без валидного паспорта (без `relationship_evidence` на уровне роли), порог = `role_overlap`-порог пакета (§1.6 п.1); симметричная ветка (найдена у меньшинства) трактуется так же — прицельный повтор, итог `not_found` (❓) на уровне роли, не ❌.** Итог — `not_found` (❓), не ❌. **SERP не встроен в оценщик:** поиск выполняется search-адаптером, его результат нормализуется в корпус (Ш5) и только затем попадает в оценку — повторный Ш6 идёт по уже проиндексированному контенту.

**Полный протокол исчерпания для strict-❓ (I3).** «Full» — не пустое слово, а перечисление пройденных контуров. Для strict-❓ обязателен проход, где применимо: (1) корпусный ретривал (≤3 запроса, I17/I20); (2) SERP-бюджет через search-адаптер (I23), если параметр достижим из внешнего контура; (3) реестры/наследование (для параметров, привязанных к `registry_facts`/`baselines.csv`). `search_exhaustion.protocol_json` (§4.4) обязан **перечислить** пройденные контуры и их `termination_reason` (из словаря). ❓, зафиксированный без исчерпания обязательных контуров, — аномалия прогона, а не статус (риск преждевременного ❓=FN, §12). Состав контуров — определительное требование; их бюджет — калибруемый (§11.5).

## 6. Расчёт показателей

Две метрики + одна производная аннотация; слияние в один score запрещено.

**Resolved Capability Score** — степень *подтверждённого* соответствия по разрешённым статусам: ✅=1, ⚠️=0.5, ❌=0. ❓ — не отрицательное свидетельство, вне числителя и знаменателя. N/A исключается (human). 0.5 — технический коэффициент агрегирования порядкового статуса, **не означает 50% функциональной реализации**. Имя показателя прямо несёт семантику: **«из исследованного — подтверждено N%», а не «продукт реализует N%»**.

**Правила отображения (защита от неправильного чтения):** Resolved Capability публикуется только рядом с Coverage; при Coverage ниже MEDIUM балл отображается приглушённо с пометкой «insufficient coverage»; легенда отчёта содержит различие «подтверждённая функциональность исследованного» vs «функциональность продукта».

**Асимметрия ❓ vs ❌ (зафиксировано).** Доказанное отсутствие (❌=0) снижает балл, а неизвестность (❓) из балла исключена. Это осознанная цена честного доказательства; компенсируется публикацией Coverage и запретом ранжировать балл без покрытия (I11). Альтернативная политика (`❓ как 0`) проверяется в sensitivity (§6) как отдельная ось — именно потому, что она потенциально меняет ранжирование.

**Evidence Coverage** — взвешенная по важности доля разрешённых результатов среди **вселенной scope прогона**. Вселенная = (выбранные модулями параметры) × (продукты когорты); т.е.

```
Coverage = Σ w(resolved{✅,⚠️,❌}) / Σ w(universe)
universe = applicable{✅,⚠️,❌,❓} ∪ failed ∪ pending ∪ отсутствующие-в-прогоне ячейки scope
```

N/A вне знаменателя (человеческое решение о неприменимости); **`preliminary`-ячейка также вне знаменателя** (I13: preliminary исключена из всех расчётов, включая Coverage). **`pending`/неоценённая/отсутствующая ячейка входит в знаменатель как неразрешённая** — иначе неполный прогон завышает покрытие. Публикуется `completed = (evaluated ∪ failed) / universe` отдельно. **Вырожденный случай:** `universe = 0` → Coverage = `UNDEFINED` (не `0.0`; `0.0` читалось бы как «ничего не покрыто»), и Capability не публикуется (I11/G4). **Семантика: полнота прохождения заданного протокола по всей вселенной scope, а не вероятность истинности результата.** `failed` присутствует в знаменателе как неразрешённое измерение (I5), поэтому сбои не завышают покрытие. Дополнительно публикуется `failure_rate = failed / (evaluated ∪ failed)` — диагностика надёжности конвейера.

**Comparability — кросс-продуктовая аннотация.** Comparability утверждается, только если выполнены **alignment-условия** когорты:

1. единое окно `snapshot_date` (все продукты сняты в одном цикле);
2. единый `retrieval_profile` и `retrieval_cutoff_K` (I16, I20);
3. единый набор эмбеддинг/индекс-сборок (`embed_model_id`, `index_build_id`);
4. единые `package_version`/`catalog_version`;
5. сопоставимые `edition_assessed` и юрисдикционный контур (Юрисдикционная симметрия).

При выполнении условий Comparability = f(min Coverage по продуктам): HIGH ≥90 · MEDIUM 75–89.9 · LOW 50–74.9 · INSUFFICIENT <50. При невыполнении любого условия Comparability помечается `cross-cycle` и понижается на один уровень, с явной причиной; **`INSUFFICIENT` — пол понижения (не понижается ниже)**. Пороги provisional, калибруются после кейса 1. **Открытость документации продукта** публикуется как **качественная аннотация** (не численная метрика, не влияет на уровни Comparability) — фактор риска documentation gaming (§12); переход в числовую метрику — отдельное калибруемое решение (§14).

Формула модуля: `Σ importance × score / Σ importance (resolved)`; итог — перенормировка весов модулей на применимые. Политика в манифесте: `capability_policy: resolved-only-v1 · unknown_policy: excluded · partial_score: 0.5`.

**Sensitivity analysis** (обязательный пост-хок отчёт, `hound sensitivity`) — пересчёт агрегатов по трём осям (перезапусков не требуется — статусы сохранены):
- коэффициент ⚠️ ∈ {0.25, 0.5, 0.75};
- политика ❓: excluded (дефолт) vs `unknown_as_zero`;
- веса важности: объявленные vs uniform.

**Предикат устойчивости ранжирования.** Перебираются все комбинации осей. Для каждой **пары продуктов** сравнивается знак разности агрегатов. Пара считается **флипнувшей**, если знак разности меняется между комбинациями, **кроме** случаев, когда оба значения пары лежат в пределах **порога неразличимости** `ranking_epsilon` на любой из комбинаций (такие пары не участвуют в подсчёте — они неразличимы, а не «флипнули»). Ранжирование **устойчиво** ⟺ множество флипнувших пар пусто. `ranking_epsilon` (доля от диапазона агрегата, дефолт `0` — точное равенство) — **калибруемый** параметр, идёт в манифест с `provenance` (A3). Реализация обязана следовать этому определению.

**Правило решения.** Если ранжирование устойчиво по всем трём осям → 0.5 и `unknown_policy: excluded` остаются. Если неустойчиво → Resolved Capability **демотируется до неранжирующего индикатора**, и battle_card публикует **fallback-порядок**: сортировку по Coverage (полнота прохождения) с по-модульной детализацией resolved-статусов и явной пометкой «упорядочено по полноте исследования, не по функциональности», а для каждой пары — интервал разброса. Официально допустимый исход — «без ранга» как честный результат (это не провал, а корректное отражение данных).

**Разграничение запрошенного и вычисленного ранга (K6).** `ranking_policy` во входе (`run.yaml`) — это **запрошенный режим отображения** (`capability_ranked` | `coverage_fallback` | `unranked`), а не разрешение ранжировать вопреки измерению. Вычисленный **допустимый ранг** определяется sensitivity: если ранжирование неустойчиво, оно демотируется **независимо от** запрошенного режима (A3 — не предрешение). Аудит фиксирует оба: `requested_ranking` и `computed_ranking` в манифесте.

**Join `requested` × `computed`.** Итоговый ранг = минимум по порядку «полноты ранжирования» `capability_ranked ⊐ coverage_fallback ⊐ unranked`:

| requested ↓ / computed → | capability_ranked | coverage_fallback |
|---|---|---|
| `capability_ranked` | capability_ranked | coverage_fallback (демотирование — ожидаемый случай, расхождение отображается) |
| `coverage_fallback` | capability_ranked | coverage_fallback |
| `unranked` | unranked | unranked |

Итог = `min(requested, computed)`: запрос `unranked` всегда даёт `unranked` (никогда не повышается до ранжирования); запрос `capability_ranked` ограничен сверху измерением; запрос `coverage_fallback` не может поднять вывод выше `computed` и не демотируется измерением ниже себя. Расхождение `requested ≠ computed` — ожидаемый и явно отображаемый случай; фиксируется в аудите.

## 7. LLM-контуры

**Разделение по роли, не по «нужен ли поиск».** Критерий: **обязан ли выход сценария быть резолвимым evidence-объектом**.

| Сценарий | Выход | Модель | Внешний поиск |
|---|---|---|---|
| **Оценщик ячейки** (Ш6) | evidence (`source_id`+цитата) | self-host, РФ-контур | **запрещён структурно (I18)** |
| **Search-адаптер** (Ш5/SERP) | url + сырые байты → корпус | Yandex Search API / GLM Web Search | это и есть поиск |
| **Discovery** (Ш2) | кандидат паспорта | search-enabled допустим | допустим (выход — гипотеза, G2) |
| **Concept scout** (preliminary) | кандидаты словаря | любая | допустим (только preliminary) |

### 7.1. Оценщик (Ш6)

Промпт компилируется механически: шаблон + `rule` + `absence_rule` + сателлиты релевантных ролей + чанки `[source: chunk_id]`; `prompt_hash` в ячейке. **LLM не генерирует URL** (I10/I15). Оценщик работает **только по переданным чанкам**; он не вызывает поиск ни при каком провайдере (I18). Контур данных замкнут (§3.2, §10).

```json
{"status": "✅|⚠️|❌|❓",
 "justification": "1–3 предложения",
 "evidence": [{"source_id": "chunk_183", "quote": "..."}]}
```

Правила: ✅/⚠️ → evidence ≥1 · ❌ → absence-evidence (+`source_scope`/`scope_attested_by` по §4.2) · ❓ → evidence может отсутствовать · N/A запрещён.

**Схема навязывается на уровне сэмплера.** При self-host используется constrained decoding (xgrammar в vLLM / XGrammar в SGLang) — гарантия *формы*, не семантики: механическая валидация остаётся обязательной.

**Валидация — эшелон (§10):** (1) существование source_id, резолв URL; (2) цитата — подстрока чистого текста чанка (strict); (3) достаточность: цитата подтверждает только то, что явно из неё следует; каждое утверждение justification должно иметь покрытие evidence (частично механически); over-claim → аномалия; (4) аномалии ревью: ✅ при слабом retrieval-скоре, расхождения по группе. Сбои → `failure_kind` → retry ≤2 → failed. LLM-экспансия запросов: запрещена в strict, допустима в preliminary как источник кандидатов для словарей концептов.

### 7.2. Search-адаптер (Ш5)

Поиск вне оценщика. Выход нормализуется в `(url, raw bytes, query, provider, language, results_count)` и пишется в `search_log`; контент — в `corpus_raw/{product_id}/`, затем общий Ш5-путь (extract → chunk → `content_hash` → index). Только после этого найденное может стать evidence (I19). Требования: симметрия бюджета (≤5 RU + ≤5 EN на продукт-параметр по умолчанию, или иной фиксированный бюджет), snapshot, идентичный протокол для всех продуктов (I16), логирование как `adapter_kind` (serp|llm_grounding). Цитаты заземлённого поиска (`url_citation`, `link`) считаются **кандидатами**, а не доказательствами: литература ([arXiv:2304.09848](https://arxiv.org/abs/2304.09848), [arXiv:2305.14627](https://arxiv.org/abs/2305.14627)) показывает систематически низкую verifiability цитат генеративного поиска.

### 7.3. Discovery и concept scout

Discovery (Ш2) может использовать search-enabled модель; выход — только кандидаты паспорта (component, role, `relationship_evidence`), проходящие G2; симметрия усилия; логирование. Concept scout — только preliminary, только кандидаты для словаря концептов, обязательное human-ревью перед попаданием в strict-словарь; запрещено влиять на уже зафиксированные `concept_terms` strict-цикла. **Приоритет: post-M1.** Concept scout не входит ни в один acceptance-критерий R1–R17 (§11.3) и не является несущим для кейса 1; отложен за MVP. Из модели не удаляется — помечен как «post-M1».

### 7.4. Маршрутизация моделей

Маршрут `scenario → {model_id, version, endpoint_kind, web_tool, decoder, seed, temperature}` **детерминирован по фазе** (не решением LLM) и зафиксирован в `llm_scenarios`/манифесте (I21). Смена модели под сценарий — версионная граница (§13): это **`execution_versions`** (условия измерения, commodity-слой по A2), а не `methodology_version`; блокирует межцикловый diff с пометкой `execution_change`, обязателен `golden-full`. Выбор модели — измерительная задача на golden (A3), как R0/R1/R2. Дефолт MVP: **лёгкий self-host оценщик** (GLM-4.5-Air / Qwen3.8-27B / GigaChat3.5-432B) с триггером возврата к флагман-классу по §14; search-enabled модель — только в ролях Ш2/scout/SERP.

## 8. Человеко-машинные интерфейсы

**G1** — план прогона (продукты, когорта, фокус→модули→роли, перенормировка, объём). **G2** — матрица ролей × продуктов, подтверждение relationship; паспорта фиксируются на цикл. **G3** — strict-ревью (⚠️/❌/❓/failed/Кр/аномалии) и preliminary-рабочий стол (`promote · set-status · fix-evidence · reject`), пакетные операции обязательны. **G4** — публикация: только strict, только с Coverage. Бюджеты времени G2/G3 фиксируются после первого полного кейса.

**Решения гейтов персистентны (S9).** Каждое человеческое решение G1–G4 пишется в `gate_decisions(decision_id, run_id, gate, target, actor, decided_at, notes)` — это носитель `reviewed_by` и аудит-след (кто подтвердил N/A, кто одобрил relationship на G2). Гейт не считается пройденным без строки в `gate_decisions`.

## 10. Безопасность и правовые рамки

Эшелонированная защита (цитатная валидация — один из эшелонов, не основной барьер):

```
недоверенный корпус/SERP → делимитеры данных/инструкций → LLM →
schema validation → source_id-резолв → цитатная валидация →
policy validation (absence+source_scope, границы зачёта) → аномалии → human review
```

Adversarial-корпус — регрессионный gate («0 известных инъекций»), не заявление о безопасности. Краулинг: robots.txt, лимиты, ToS — дефолты; обход антибота запрещён; юрчек-лист до M1. **Контур данных:** эмбеддинги и оценщик — локально/self-host в РФ; корпус не покидает контур; search-адаптер — РФ-контур (поисковые запросы — отдельный логируемый канал, к ним применяется то же правило равного бюджета). 152-ФЗ. Юрисдикционная симметрия.

**Изоляция веб-контура сетевым слоем (доп. эшелон).** Веб-функции (краул, внешний поиск, реестровые фетчеры, экстракция недоверенного контента) могут быть вынесены в **DMZ**, а не-веб функции — в доверенную зону без веб-эгрессии; взаимодействие — только через **application-layer firewall** по явному протоколу. Это материализует **I18** на сетевом уровне (у оценщика физически нет маршрута в интернет) и делает границу **I19** явной. Проектный регламент — `docs/architecture/07-deployment-topology.md`; профиль `split` (DMZ) — опция уже в MVP (M1, поток W13), `local` (один процесс) — дефолт. Контракты между частями coHound проектируются **прозрачными для корпоративных IDP/DLP/IDS** (L7-инспектируемый JSON, публикуемые схемы, TLS без пиннинга, атрибуция запросов); аттестация против конкретных средств — вне рамок проекта.

## 11. Контроль качества

### 11.1. Golden — регрессионная сеть, не измерение качества

golden-fast (30, PR) / golden-full (100–200: смена модели/правил/каталога, релиз). Порог 80% — временный порог калибровки MVP. Критические классы (допустимо 0): любой false ✅; false ❌ на Кр-параметрах. golden-full обязан содержать страту ожидаемых ❌ (§4.2).

**Разведение ролей golden (снимает напряжение «сеть vs приёмка»).** Golden — прежде всего **регрессионная сеть** (детектор *изменения* на неизменном эталоне), а **не измерение качества**. Поэтому:
- **R6 (golden agreement ≥80%)** — это gate **стабильности на неизменном golden**, а не измерение качества модели;
- **измерение качества** — только ручная калибровка §11.5;
- **смена методологии (§13) инвалидирует разметку golden**: `golden-full` требует пере-аннотации человеком, иначе R6 вырождается в «сеть всегда зелёная» (подгонка эталона под реализацию).

### 11.2. Retrieval-golden и extraction-golden

retrieval-golden: 30–40 пар «параметр → целевой чанк» (половина авто из evidence-URL golden, половина — ручные кросс-язычные). **Cut-off метрики равен pipeline-K** (`retrieval_cutoff_K`, I20): recall@K. Прогон при смене эмбеддинг-модели/чанкера/fusion-параметров + выбор retrieval-профиля (R0/R1/R2) и K в M1. extraction-golden: страницы с известными фактами; A/B экстракторов при смене extractor_version; **обязательный PDF-набор** (фич-матрицы РФ-вендоров) — блокер M0.

### 11.3. Acceptance MVP

```
R1  100% registry facts имеют source_url
R2  100% evaluated ✅/⚠️ имеют валидное evidence
R3  failed никогда → ❓ автоматически
R4  N/A невозможен автоматически
R5  inheritance не создаёт статус без выполнения правила
R6  golden agreement ≥ 80% (временный порог калибровки)
R7  воспроизводимость двойного прогона ≥ 95% (определение в §11.7)
R8  0 известных инъекций на adversarial-корпусе (регрессионный gate, не assurance)
R9  recall@K retrieval-golden ≥ 0.9 (K = pipeline-K; порог provisional)
R10 recall@K кросс-язычная ≥ 0.8 (порог provisional)
R11 sensitivity выполнена по осям {⚠️, ❓-policy, веса}; ветка поведения записана
    (при неустойчивости — демотирование + fallback-порядок, §6)
R12 кейс 1 демонстрирует ≥1 валидный ❌ через registry_absence ИЛИ distribution_absence
     (достаточно одного пути) и 0 false-❌ на Кр-параметрах на golden
R13 Coverage учитывает failed в знаменателе; failure_rate публикуется
R14 когорта и операциональная роль якоря зафиксированы в манифесте (проверяется)
R15 provenance ячеек: 100% evaluated-ячеек несут index_build_id и retrieval_profile;
    evidence-объекты имеют детерминированный evidence_id (идемпотентность resume)
R16 CI-гейты подтверждают: I16 (единый профиль+K для когорты), I20 (golden cut-off =
    pipeline-K), I23 (поисковый бюджет залогирован); diff запрещён при несовпадении
    methodology/catalog/retrieval/provenance (§13)
R17 оценщик не имеет веб-тула ни при каком сценарии-эвалуаторе (I18); все evidence
    корпусного типа имеют content_hash (I19)
```

### 11.4. Portability gate

Чеклист нейтральности v2 (11 пунктов: каталог без чужих терминов · upstream-деривативность/baselines · роли+маркеры · showcase-параметры+метрики рынка · реестры · эталон (для C — явная фиксация отсутствия + блокировка baselines) · N/A-политики · языки · (B) кросс-линейные · (C) калибровочный пол · грепп-тест). **Правка `core/` при онбординге кейса = блокировка кейса.** Пять кейсов дают **первичное эмпирическое подтверждение** гипотезы нейтральности.

### 11.5. Ручной baseline-эксперимент

Независимый ручной проход аналитика по стратифицированной выборке кейса 1 (~120–150 ячеек: статус, evidence, обоснование — без знания системных вердиктов). **Минимум два независимых аннотатора** на подвыборке (~30–40 ячеек, включая страту ❌, Кр **и N/A-решения**) с публикацией согласия (Cohen's κ **отдельно по N/A**, т.к. N/A-решения задают знаменатель Coverage — I6/I7); расхождения разбираются как источник ошибок. Сравнение с системой: FP/FN **по классам ошибок**, валидность цитат, дельта coverage, оценка сэкономленного времени. Побочный продукт — сидирование golden-full. Планируемая стоимость: 20–40 экспертных часов (каждый аннотатор). Это и есть «калибровка методологии» — самое дорогое место проекта по независимой оценке. **Пере-аннотация golden:** смена методологии (§13) инвалидирует разметку golden-full → обязательна повторная ручная аннотация (§11.1).

### 11.6. Preliminary-метрики и CI

Preliminary-метрики: yield · расхождение кандидат/strict на golden · время прохода. CI-гейты и их
текущее покрытие — `docs/architecture/04-reliability-adr.md` §C; единая точка входа — `scripts/ci.sh`.

### 11.7. Определение воспроизводимости (R7)

«Двойной прогон» = два запуска с идентичными входами, `snapshot_date`, `index_build_id`, `retrieval_profile`+K, набором моделей и фиксированными `temperature`/`seed`/decoder, **без живого ре-фетча** (корпус и SERP — из кэша). **Кэш внешних вызовов content-addressed и глобальный** (вне `runs/{run_id}/`): сырые байты страниц — `corpus_raw/{product_id}/{content_hash}` (уже глобальны), ответы SERP — `cache/serp/{query_hash}.json`, HTTP — `cache/http/{url_hash}.bin` в корне репозитория. Это делает R7 достижимым **между разными `run_id`**: второй запуск читает тот же кэш по хэшу ключа, а не по идентификатору прогона. Метрика — доля совпавших `status` по всем ячейкам. Детерминизм обеспечивается: greedy или seed (SGLang per-request seed; vLLM `VLLM_ENABLE_V1_MULTIPROCESSING=0`/batch invariance), зафиксированные версии весов и движка, одинаковое железо. Остаточный GPU non-determinism распределённых MoE конфигов документируется как известное ограничение.

| Механизм | Риск | Направление | Контрмера |
|---|---|---|---|
| Discovery | ошибочный сателлит | FP | relationship evidence + G2 |
| Inheritance | перенос чужой функции | FP | inheritance_mode + П>В |
| Слабая документация | функция не найдена | FN | корпус+SERP+coverage |
| Retrieval dense | близкий, но не подтверждающий чанк | FP | policy-валидация, метаданные чанка, ревью |

| Смена embed/чанкера | несопоставимые индексы | drift | index_manifest, R9/R10 |
| Экстрактор | потеря контента (особенно PDF-таблицы) | FN | extraction-golden, raw re-extract, PDF-блокер M0 |

| Documentation gaming | вендор недокументирует слабые зоны | bias | coverage, absence-правила+source_scope, NDA-петля, фактор Comparability |

| Preliminary leakage | кандидат в публикации | FP | I13, раздельные артефакты, G4 |

| Misreading score | Resolved Capability читают как «% функциональности» | bias | имя показателя + правила отображения + sensitivity |

## 13. Версионирование

**Два класса версий (B-7).**

**`methodology_version` — семантика правил** (изменение = версионная граница, инвалидирует межцикловый diff, требует `golden-full` + пере-аннотации golden): `status_dictionary_version` · `scoring_policy_version` (включая `partial_score`, `unknown_policy`) · отсутствие-правила/сателлитная модель/evidence-модель · определения Coverage/Comparability/sensitivity. Slug иммутабельны; deprecated + replaced_by.

**`execution_versions` — условия измерения** (commodity-слой; смена не меняет правила, но делает сборки/ячейки несопоставимыми численно — тоже блокирует diff, но с иной причиной): `package_version` · `catalog_version` · индексный контур `index_build_id`, `embed_model_id`, `chunker_version`, `extractor_version`, `lexical_engine_version`, `retrieval_profile`, `retrieval_cutoff_K`, `retrieval_params_json` (fusion-параметры, включая `rrf_k`) · модель под сценарий (I21) · когорта. Сборки иммутабельны; смена любого из них = новая сборка + retrieval-golden (S1).

**Diff-совместимость:** `hound diff` сравнивает манифесты и запрещает межцикловый diff при несовпадении **любого** из двух классов, но с **различной пометкой причины**: `methodology_change` (правила иные — сравнение семантически неверно) vs `execution_change` (условия измерения иные — сравнение численно несопоставимо). Major запрещает межцикловые diff.

## 15. Открытые вопросы к детальному проектированию

- **LLM-провайдер по сценариям** (self-host оценщика): финал модели (лёгкий класс vs флагман) по R6/R9/R10/R12 + CPU/GPU-бюджет батчей; выбор инференс-стека (vLLM vs SGLang) и стратегии детерминизма; подтверждение лицензий (DeepSeek/GLM-Flash — MIT; GigaChat3.5 — MIT) и юрстатуса self-host.
- **Что значит «инсталляция»**: свой кластер / аренда РФ-облака / вендорский контур — влияет на §10, 152-ФЗ и ops-бюджет.
- **PDF-контур:** тест docling на 3–5 реальных мануалах РФ-вендоров, PDF + Office (**блокер M0**); риск потери табличной структуры фич-матриц; офлайн-бандл весов и аудит лицензий (§3.2, `05-dependency-stack.md` §7).
- **Перечень JS-доменов per case.**
- **RU/EN/identifier-профили tantivy** на retrieval-golden.
- **Search-адаптер:** Yandex Search API vs GLM Web Search; бюджет, snapshot, `adapter_kind`; сверка цитат.
- **Юрчек-лист (до M1):** краулинг/ToS по доменам, хранение сырых байтов, self-host весов.
- **Стоимость/токены одного полного кейса** (число вызовов оценщика ≈ параметры × продукты × ≤3 запроса + ревью) — может стать ограничением сильнее latency.
- **Регламент аттестации `source_scope: exhaustive`** (`scope_attested_by`) для parameter_reference/distribution_absence: аттестация = запись в `gate_decisions` (actor/decided_at/notes), публикуется порядок силы ❌ (§4.2). Открыто: **кто именно и на основании чего признаёт справочник полным per кейс**.
- **Поведение продукта с 0 публичных документов:** Coverage → `UNDEFINED`/INSUFFICIENT, Capability непубликуем (I11/G4, §6); участие в battle_card как ❓-тяжёлого — правила закрепить после кейса 1.
- **Калибровка порогов** (Comparability, R6, R9/R10, yield, бюджеты G2/G3) и **`ranking_epsilon`** (порог неразличимости при устойчивости, §6) после кейса 1.

## 16. Глоссарий

**Якорь** — система координат отчёта, задаёт порядок/фокус по умолчанию; не базлайн, не вес, оценщики anchor-blind. **Когорта** — замороженный на G1 набор продуктов (якорь + 6–10 аналогов) с обоснованием в `cohort.yaml`. **Фокус** — scope сравнения. **Кейс** — пакет категории + когорта + якорь. **Архетип** — тип категории по OSS-upstream (A/B/C). **Базлайн** — upstream-линия наследования. **Роль** — инженерная функция с реестром в пакете. **Сателлит** — компонент, описанный тройкой origin/relationship/evidence_state. **Relationship evidence** — двухчастное доказательство связи спутника с продуктом в роли. **Паспорт продукта** — гипотеза экосистемы, фиксируется G2 (единственное значение слова «паспорт»). **Ячейка** — (продукт, параметр, прогон). **Evidence** — машинно-проверяемый объект доказательства (1..N), с `source_scope` для absence-evidence. **Чанк** — единица индексации с heading_path и метаданными изоляции. **Retrieval-профиль** — конфигурация гибридного поиска цикла (R0/R1/R2), симметрична (I16); включает `retrieval_cutoff_K`. **Оценщик (evaluator)** — LLM, работающий только по переданным чанкам, без внешнего поиска (I18). **Search-адаптер** — внешний поиск как источник входного контента, нормализуемый в корпус (I19). **Индексная сборка** — иммутабельный снапшот индекса (продукт-партиции). **Retrieval-/Extraction-golden** — эталоны качества ретривала/экстракции. **Исчерпание** — машиночитаемое состояние протокола поиска. **Preliminary-ячейка** — кандидат с невалидированной цитатой; вне расчётов. **Promote** — строгая переаттестация. **Resolved Capability Score** — подтверждённое соответствие по разрешённым статусам; «из исследованного — подтверждено N%». **Evidence Coverage** — взвешенная полнота прохождения протокола (failed в знаменателе). **Comparability** — кросс-продуктовая аннотация: alignment-условия когорты + min Coverage. **Sensitivity** — устойчивость ранжирования к осям {⚠️, ❓-policy, веса}. **Пакет категории** — данные предметной области; ядро их не содержит. **Аксиомы A1–A3** — руководящие принципы §0.
