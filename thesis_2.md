# coHound — технический паспорт v1.3

**Статус:** основание для детального проектирования и реализации (MVP)

**Кодовое имя:** **coHound** (утверждено; «co-» = competitive intelligence / cohort comparison; «hound» = идёт по следу до исчерпанного протокола). Товарные знаки и домены — отдельной задачей до внешнего запуска, M0 не блокирует.

---

## 0. Руководящие аксиомы

**A1. Сначала доказательство ценности, потом оптимизация.** Сначала доказать, что coHound воспроизводимо получает качественную сравнительную карту на маленьком корпусе детерминированными и минимальными средствами; только потом оптимизировать ретривал, масштабирование и инфраструктуру.

**A2. Moat — методология измерения, не AI-пайплайн.** Конкурентное преимущество — семантика каталога, absence/inheritance-правила, сателлитная модель, evidence-модель, политика валидации, модель ошибок, воспроизводимость. Ретривал, LLM, хранилища — заменимые commodity. **Правило:** если реализация требует изменить методологию — это сигнал об ошибке в реализации.

**A3. Эпистемология единообразна на всех уровнях** — включая инфраструктурные выборы: «установлено» отличается от «предположено» не только в ячейках, но и в паспорте. Дефолты помечаются как assumption/candidate; замена дефолта происходит по измерению, не по предвидению.

## 1. Назначение, границы, режимы

### 1.1. Назначение

coHound принимает четыре входа — **якорь, каталог параметров, перечень продуктов, фокус сравнения** — и производит сравнительную техническую карту программных продуктов.

**Философия:** coHound не пытается узнать «истину о продукте». Он измеряет **степень публично доказуемой функциональности по фиксированному протоколу** и строит воспроизводимую карту того, какие утверждения о продукте можно подтвердить публичными доказательствами — отдельно показывая: что подтверждено (Resolved Capability), насколько полно исследовано (Coverage), где осталась неопределённость (❓ / NDA-вопросник), почему сделан вывод (evidence), насколько результат сопоставим (Comparability-аннотация).

Свойства карты: каждый статус имеет публичную проверяемую ссылку или детерминированный вывод; «не установлено» (❓) отличается от «подтверждённое отсутствие» (❌) и «неприменимо» (N/A); функции сателлитов засчитываются корректному компоненту; все продукты оцениваются по одинаковым правилам; покрытие публикуется рядом с баллом.

### 1.2. Не-цели

coHound не является: нагрузочным бенчмарком · заменой PoC внедрения · юридическим заключением о сертификации · заменой NDA-опросника (он его *готовит*) · источником рейтинга без покрытия · системой, утверждающей что-либо о функциональности сверх публично доказуемой.

### 1.3. Категорийная нейтральность

Ядро (`core/`) не содержит терминологии предметных категорий; вся специфика — пакет категории (данные). CI-грепп-тест. Переносимость — приёмочное требование MVP (§11.4): пять кейсов MVP дают **первичное эмпирическое подтверждение** гипотезы нейтральности (формулировка сознательно не «доказательство»).

### 1.4. Режимы прогона

Одна политика обработки валидации, не два конвейера: невалидированный отклик в strict → failed, в preliminary → кандидат.

| | **strict** (публикационный) | **preliminary** (аналитический) |
|---|---|---|
| Назначение | Итоговые карты, баллы, публикация | Рабочий материал; предварительный этап к окончательной оценке; место для интерпретации |
| Цитатная валидация | Обязательна (механическая) | Не обязательна; mismatch → `validation_notes` |
| ❓ | После исчерпания полного протокола | Допустим по сокращённому (`protocol: partial`) |
| ❌ | Только по absence-правилу + `source_scope: exhaustive` (§4.2) | Кандидат-отрицания (помечены) |
| Inheritance conditional | Через ревью | Автоматический кандидат |
| В расчётах | Да | **Нет — I13** |
| Артефакт | `battle_card.xlsx` | `preliminary_findings.xlsx` |

Инвариантно: N/A только человеком · URL только системный резолв · failed никогда не статус · границы зачёта только из каталога · равное усилие · строгая переаттестация при promote. Preliminary-статус никогда не повышается автоматически; цикл кандидата: `promote · set-status (actor=human) · reject`; пакетно `promote --validated-only`.

### 1.5. Объём MVP: кейсы и архетипы

**5 кейсов** (якорь + 6–10 аналогов, 100–300 параметров), три архетипа:

| Архетип | Признак | Наследование | Калибровочный пол |
|---|---|---|---|
| **A** | Явный OSS-лидер — общий upstream | `baselines.csv` per-продукт | базлайн-участник (если существует) |
| **B** | Несколько OSS-альтернатив + коммерческие на их основе | матрица «параметр × базлайн»; кросс-линейные — только корпус | базлайн-участник (если существует) |
| **C** | Без сильного OSS-лидера | не заполняется (осознанно) | **эталона нет и не вводится**; golden + дисциплина правил; сопоставимость несёт Coverage |

Масштаб: 35–55 паспортов; ≤ ~3300 ячеек на кейс; корпус 1–3 млн чанков суммарно. Каждый кейс = пакет категории + прогон чеклиста нейтральности v2 (§11.4). Минимум один кейс на архетип.

## 2. Методологическое ядро

### 2.1. Статусы

| Статус | Семантика |
|---|---|
| ✅ | наличие подтверждено (валидная цитата или детерминированный вывод) |
| ⚠️ | наличие частично/неполно подтверждено либо реализовано ограниченно |
| ❌ | отсутствие непосредственно подтверждено: absence-evidence по absence-правилу параметра **и** `source_scope: exhaustive` (для не-registry правил — §4.2) |
| ❓ | после исчерпания предписанного протокола недостаточно доказательств |
| N/A | архитектурно неприменим; только человек |

**Главный инвариант: отсутствие evidence никогда само по себе не является evidence отсутствия.**

### 2.2. Принципы

1. Цитатная дисциплина: strict-✅/⚠️ требуют machine-verified evidence.
2. Равновесные трактовки → меньший статус.
3. Показательный параметр (класс `showcase`) измеряет **capability + публичную измеримость**: механизм + публичная величина; одно из двух → ⚠️. Это осознанная семантика параметра, декларируемая в каталоге и легенде отчёта — не скрытая documentation bias.
4. Роли сателлитов: механизм в ядре, наполнение — в пакете.
5. Равный поисковый бюджет = равенство поискового *усилия*, не обнаруживаемости; полный лог.
6. Ошибка ≠ вердикт: failed никогда не статус.
7. Детерминированное раньше поиска: реестры → наследование → дистрибутив → корпус → SERP.
8. Прямое доказательство старше наследования (П>В): противоречащее свидетельство понижает унаследованный статус → ревью.
9. Resolved Capability без Coverage не является достаточным основанием для сравнения.
10. N/A, границы зачёта, мера частичности — человеческие решения.
11. Якорь — система координат отчёта, не базлайн; оценщики anchor-blind.

### 2.3. Инварианты

```
I1  evaluated + ✅/⚠️      → evidence ≥ 1
I2  evaluated + ❌         → absence-evidence по absence-правилу параметра
I2b evaluated + ❌ (не registry-правило) → source_scope: exhaustive на absence-evidence
I3  ❓                    → протокол исчерпан (full) ИЛИ human-reviewed
I4  failed                → status = null
I5  failed                → исключена из всех расчётов и coverage
I6  N/A                   → reviewed_by ≠ null
I7  N/A                   → никогда автоматически
I8  inherited-статус      → правило наследования выполнено (mode учтён)
I9  сателлитная ячейка    → relationship evidence существует
I10 source URL            → системный резолв из source_id
I11 публикуемый балл      → сопровождается Coverage
I12 ❓                    → никогда не трактуется как ❌
I13 preliminary           → исключена из Capability/Coverage/публикации
I14 preliminary → strict  → строгая переаттестация или human evidence
I15 source_id → URL       → детерминированный lookup
I16 профиль ретривала     → идентичен для всех продуктов цикла
I17 evidence корпуса      → только чанки паспорта продукта и его сателлитов
```

### 2.4. Три анкера данных

Стабильные slug-ID · версионирование каталогов в git (semver) · словарь статусов как отдельный источник истины.

## 3. Архитектура и технологический стек

### 3.1. Компоненты

CLI-ядро (`resolve · plan · discover · run · review · report · golden · sensitivity · diff · promote`) · нормализатор входов с линтером · Discovery-агент · сборочный контур (краул, экстракция) · индексационный контур (чанкер, гибридный индекс) · движок наследования · реестровые фетчеры · LLM-оценщик с механической валидацией · SERP-контур · очередь ревью / preliminary-рабочий стол · расчётно-отчётный модуль.

### 3.2. Стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Язык / данные | Python 3.11+ · YAML+CSV в git · Pydantic | без изменений |
| Операционное хранилище | SQLite | без изменений |
| **Векторный контур** | **NpyVectorIndex (in-process, brute-force cosine по .npy-шардам + манифест) — дефолт MVP**. Порт `VectorIndex` сохраняется; Qdrant — **отложенная подмена по измеримым триггерам** (§15) | Иммутабельные индексные сборки не требуют upserts/онлайн-записи; 60k чанков/продукт ≈ 240 МБ и десятки мс brute-force; выбор Qdrant в v1.2 решал проблемы, спроектированные прочь — нарушение A3, исправлено |
| **Лексический контур** | tantivy (BM25, RU/EN стеммеры) | идентификаторы (GUC, утилиты, версии) — компетенция лексики |
| **Ретривал-профиль** | **эксперимент в M1: R0=BM25 / R1=dense / R2=RRF-гибрид на retrieval-golden; дефолт фиксируется измерением** и записывается в манифест каждого прогона | ретривал принимается по evidence, не по предвидению (A3); гипотеза: R2 выигрывает на смешанном RU/EN корпусе — проверяемая, не предрешённая |
| Эмбеддинги | локально, sentence-transformers: multilingual-e5-large (кандидат), BGE-M3 (альтернатива); финал по R9/R10 | данные не покидают контур; NC-лицензии исключены |
| Краулинг | Scrapy + scrapy-playwright (per-domain рендер-профили) | production-фреймворки; качество извлечения кормит цитатную валидацию |
| Экстракция | trafilatura (HTML) · docling (PDF, фич-матрицы → markdown) | PyMuPDF исключён (AGPL); лицензии верифицируются при пине M0 |
| LLM / SERP / Отчёты / Оркестрация | сменный адаптер с JSON-режимом · 2 SERP-адаптера · openpyxl · однопроцессный Python + thread-pool (**дефолт MVP**, пересматривается по триггеру) | без изменений |

**Свой код сбора — три вещи:** доменные профили · чанкер с `heading_path` · retention сырых байтов + `extractor_version` (ре-извлечение без ре-фетча, A/B экстракторов). **Ручной drop-in корпус** — штатный escape hatch для антибот-доменов, с правилом симметрии (одинаково доступен всем продуктам кейса); обход CAPTCHA/антибота запрещён.

## 4. Модель данных

### 4.1. Словари и перечисления

`docs/status-dictionary.yaml`: статусы (§2.1) · `source_kind` (registry|inheritance|distribution|documentation|web|manual) · `evidence_type` (direct|derived) · `absence_rule_type` (explicit|parameter_reference|distribution_absence|registry_absence) · `source_scope` (**exhaustive|partial|unknown** — свойство экземпляра источника, поле evidence) · `failure_kind` (search_failed|source_unavailable|evaluation_failed|validation_failed|parser_failed) · `cell_state` (pending|preliminary|evaluated|failed|reviewed) · `run_mode`.

**Оси сателлита:**

```
origin:          in_house | third_party | upstream | community | unknown
relationship:    bundled | integrated | certified | recommended | external
evidence_state:  verified | claimed
```

**Маппинг на зачёт (Р-2, в ядре):** bundled/integrated/certified + verified → без потолка; recommended + verified → ⚠️; любой + claimed → ⚠️; external + verified → по rule параметра; `origin` сам зачёт не ограничивает; `community+external` — не даёт зачёта по интеграционным параметрам.

### 4.2. Пакет категории

**package.yaml:** `archetype (A|B|C)` · модули с весами (сумма=100) · реестр ролей (definition, markers, query_patterns RU/EN, core_coverage_allowed, multi_instance) · реестр базлайнов · `baseline_participant` (null для C) · юрисдикции+реестры · языки.

**catalog.csv (11 колонок):** `param_id` (slug, иммутабельный) · `title` · `module` · `group` · `importance` (Кр|Вж|Баз|Опц) · `param_type` (fact|showcase) · `rule` (граница зачёта) · **`absence_rule`** (тип из словаря; дефолт `explicit`) · `role_binding` · `concept_terms` (`ru: "…" | en: "…"` — детерминированная синонимичная экспансия) · `search_langs`.

**Гносеология absence-правил (уточнение v1.3):** исчерпанность источника — свойство экземпляра, не типа правила, кроме registry:

- `registry_absence` — **exhaustive по построению** (реестр — авторитетная энумерация); отсутствие записи = валидное негативное свидетельство, механически;
- `parameter_reference` / `distribution_absence` — требуют на absence-evidence `source_scope: exhaustive` (подтверждает человек: действительно ли справочник полный, документирует ли вендор весь состав); иначе — понижение до ❓;
- `explicit` — явное отрицание вендора, source_scope не требуется.

Следствие фиксируется честно: исчерпанные справочники редки → ❌ остаётся редким статусом в публичном цикле → компенсаторы: NDA-петля, дистрибутивный контур, coverage рядом с баллом. Это усиливает строку documentation gaming в §12, а не ослабляет систему.

**baselines.csv:** `(baseline_id, param_id, min_version, inheritance_mode, note)`; режимы `direct` (дефолт для ядровых: upstream ≥ min_version + отсутствие явного исключения) · `conditional` (расширения/дистрибутивные: ревью/кандидат) · `blocked` (upstream-факт не используется). Отсутствие строки = кросс-линейный параметр (архетип B): только корпус. **Наследование переносит возможность проверить применимость upstream-факта, но не является автоматическим доказательством наличия функции в downstream-продукте.**

**golden.csv:** `product_id, param_id, expected_status, expected_evidence_kind, case_class, note`; проверка kind — вхождение в допустимый набор. **Тиры:** `golden-fast` (~30, каждый PR) · `golden-full` (100–200: смена модели/правил/каталога, релиз). **adversarial/** — страницы-ловушки; R8 — регрессионный gate, не заявление о безопасности.

**Линтер (блокирует прогон):** уникальность slug; разрешимость FK; валидность enum; showcase → rule упоминает величину; веса=100; ссылки baselines; `absence_rule` из реестра; warning при пустых `concept_terms`; для архетипа C — warning при непустом baselines.

### 4.3. Паспорт продукта

`passports/{product_id}/{YYYY-MM-DD}.yaml`. **Precision-first:** Discovery не устанавливает принадлежность компонента продукту без relationship evidence; доказываются две независимые вещи — существование и связь в роли.

```yaml
product_id: pangolin
canonical_name: "Platform V Pangolin"
vendor: "СберТех"
upstream: {baseline_id: upstream-pg, version: "16", evidence: {url, quote}} | null
edition_assessed: "Enterprise"
version: "6.2"
jurisdiction: RU
doc_domains: ["platformv.sbertech.ru/docs/products/pangolin"]
satellites:
  - role: backup
    component: "Platform V CopyWala"
    origin: third_party
    relationship: bundled
    evidence_state: verified
    relationship_evidence: {url, quote}
    state: approved                  # draft | approved | edited_by_human
    rejected_candidates: [{name, reason}]
  - role: management_console
    state: not_found                 # ❓ на уровне роли; протокол в логе
snapshot_date: 2026-06-01
```

Кэш `(product_id, role, snapshot_date)`; глубина сателлита = 1; G2 подтверждает relationship.

### 4.4. Операционная БД (SQLite + index_store)

```sql
products(product_id PK, canonical_name, vendor, jurisdiction, first_seen, last_seen);

runs(run_id PK, created_at, mode, case_id, anchor_product_id, focus_text, focus_modules,
     package_id, package_version, catalog_version, status_dict_version,
     scoring_policy_version, methodology_version,
     llm_model_ids, embed_model_id, index_build_id, retrieval_profile,
     snapshot_date, state);

corpus_docs(doc_id PK, product_id, url, fetched_at, content_hash,
            raw_path, extractor_version, render_mode, lang);
corpus_chunks(chunk_id PK, doc_id, product_id, url, heading_path, lang,
              chunk_no, text, context_prefix, content_hash,
              embed_model_id, embedded_at);
index_manifest(index_build_id PK, package_id, snapshot_date, chunker_version,
               embed_model_id, embed_dim, lexical_engine_version,
               vector_store, store_path, created_at, stats_json);

cells(run_id, product_id, param_id, state,
      status, preliminary_status, source_kind, justification, rule_note,
      validation_notes, failure_kind, model_id, prompt_hash, primary_evidence_id,
      reviewed_by, updated_at);

cell_evidence(evidence_id PK, run_id, product_id, param_id,
      source_kind, evidence_type, source_id, source_url,
      citation_quote, content_hash, source_scope,      -- для absence-evidence
      retrieved_at);

search_log(log_id PK, run_id, phase, provider, language, query, results_count,
           selected, lexical_score, dense_score, fused_rank, rerank_score,
           retrieval_score, termination_reason, ts);

search_exhaustion(run_id, product_id, param_id, protocol_json);
registry_facts(run_id, product_id, registry_id, fact_json, source_url, fetched_at);
```

Валидация цитат — по чистому `text` чанка (`context_prefix` не входит). `content_hash` заполняется с первого дня.

### 4.5. Конфигурация прогона (run.yaml)

`case_id · anchor · products · package · focus{modules, params} · languages · snapshot_date · mode`. Фокус меняет scope и перенормировку весов, не методологию. Роли scope = объединение `role_binding` выбранных модулей.

## 5. Конвейер

```
Ш1  Нормализация входов, линт, план (scope, роли, перенормировка)  ── ГЕЙТ G1
Ш2  Discovery: по ролям scope, precision-first                     ── ГЕЙТ G2 (relationship)
Ш3  Реестровая волна (без LLM) → R-ячейки
Ш4  Волна наследования: по baselines.csv при совпадении upstream;
    direct → статус · conditional → ревью/кандидат · blocked → пропуск (без LLM)
Ш5  Корпус: краул (доменные профили) → экстракция → дедуп → чанкер
    → tantivy + батч-эмбеддинги → .npy-сборка → index_manifest
Ш6  Оценка per (продукт × параметр):
      запросы = {title + concept_terms RU/EN} (≤3)
      → ретривал по зафиксированному профилю (R0/R1/R2) → топ-8 чанков
      → LLM (source_id + quote) → механическая валидация:
          strict:      прошёл → evaluated · не прошёл → failed (retry ≤2)
          preliminary: прошёл → evaluated · не прошёл → preliminary-кандидат
      корпус недостаточен → SERP-протокол (≤5 RU + ≤5 EN, симметрично)
Ш7  Очередь ревью / preliminary-рабочий стол                       ── ГЕЙТ G3
Ш8  Расчёт: Resolved Capability + Coverage (+модульные)            ── ГЕЙТ G4
Ш9  Отчёты: battle_card · preliminary_findings · nda_questions · diff · manifest
```

Протокол исчерпания — машиночитаемый объект; ❓ = «протокол исчерпан, evidence недостаточно». Правило П>В действует на Ш6 поверх унаследованных статусов. Реконсиляция когорты: роль найдена у большинства и не найдена у одного → прицельный повтор тем же протоколом; итог — `not_found` (❓), не ❌.

## 6. Расчёт показателей

Две метрики + одна производная аннотация; слияние в один score запрещено.

**Resolved Capability Score** — степень *подтверждённого* соответствия по разрешённым статусам: ✅=1, ⚠️=0.5, ❌=0. ❓ — не отрицательное свидетельство, вне числителя и знаменателя. N/A исключается (human). 0.5 — технический коэффициент агрегирования порядкового статуса, **не означает 50% функциональной реализации**. Имя показателя прямо несёт семантику: **«из исследованного — подтверждено N%», а не «продукт реализует N%»**.

**Правила отображения (защита от неправильного чтения):** Resolved Capability публикуется только рядом с Coverage; при Coverage ниже MEDIUM балл отображается приглушённо с пометкой «insufficient coverage»; легенда отчёта содержит различие «подтверждённая функциональность исследованного» vs «функциональность продукта».

**Sensitivity analysis** (обязательный пост-хок отчёт, `hound sensitivity`): пересчёт агрегатов при ⚠️ = 0.25 / 0.5 / 0.75 (перезапусков не требуется — статусы сохранены). **Правило решения:** ранжирование устойчиво → 0.5 остаётся; ранжирование сильно меняется → Resolved Capability официально демотируется до неранжирующего индикатора (только сравнение «выше/ниже» с указанием разброса).

**Evidence Coverage** — взвешенная по важности доля разрешённых результатов среди применимых: `resolved{✅,⚠️,❌} / applicable{✅,⚠️,❌,❓}`; failed — неразрешённые; N/A вне знаменателя; публикуется агрегатно и по модулям. **Семантика: полнота прохождения заданного протокола, а не вероятность истинности результата.**

**Comparability — производная аннотация Coverage** (не независимая метрика; терминологическая правка v1.3): HIGH ≥90 · MEDIUM 75–89.9 · LOW 50–74.9 · INSUFFICIENT <50; пороги provisional, калибруются.

Формула модуля: `Σ importance × score / Σ importance (resolved)`; итог — перенормировка весов модулей на применимые. Политика в манифесте: `capability_policy: resolved-only-v1 · unknown_policy: excluded · partial_score: 0.5`.

## 7. LLM-контур

Промпт компилируется механически: шаблон + `rule` + `absence_rule` + сателлиты релевантных ролей + чанки `[source: chunk_id]`; `prompt_hash` в ячейке. **LLM не генерирует URL.**

```json
{"status": "✅|⚠️|❌|❓",
 "justification": "1–3 предложения",
 "evidence": [{"source_id": "chunk_183", "quote": "..."}]}
```

Правила: ✅/⚠️ → evidence ≥1 · ❌ → absence-evidence (+source_scope по §4.2) · ❓ → evidence может отсутствовать · N/A запрещён.

**Валидация — эшелон (§10):** (1) существование source_id, резолв URL; (2) цитата — подстрока чистого текста чанка (strict); (3) достаточность: цитата подтверждает только то, что явно из неё следует; каждое утверждение justification должно иметь покрытие evidence (с evidence[] частично механически); over-claim → аномалия; (4) аномалии ревью: ✅ при слабом retrieval-скоре, расхождения по группе. Сбои → `failure_kind` → retry ≤2 → failed. LLM-экспансия запросов: запрещена в strict, допустима в preliminary как источник кандидатов для словарей концептов.

## 8. Человеко-машинные интерфейсы

**G1** — план прогона (продукты, фокус→модули→роли, перенормировка, объём). **G2** — матрица ролей × продуктов, подтверждение relationship; паспорта фиксируются на цикл. **G3** — strict-ревью (⚠️/❌/❓/failed/Кр/аномалии) и preliminary-рабочий стол (`promote · set-status · fix-evidence · reject`), пакетные операции обязательны. **G4** — публикация: только strict, только с Coverage. Бюджеты времени G2/G3 фиксируются после первого полного кейса (норматив v1.1 «≤1 ч» относился к пилоту 3×50 и более не утверждается).

## 10. Безопасность и правовые рамки

Эшелонированная защита (цитатная валидация — один из эшелонов, не основной барьер):

```
недоверенный корпус/SERP → делимитеры данных/инструкций → LLM →
schema validation → source_id-резолв → цитатная валидация →
policy validation (absence+source_scope, границы зачёта) → аномалии → human review
```

Adversarial-корпус — регрессионный gate («0 известных инъекций»), не заявление о безопасности. Краулинг: robots.txt, лимиты, ToS — дефолты; обход антибота запрещён; юрчек-лист до M1. Локальные эмбеддинги — корпус не покидает контур. 152-ФЗ. Юрисдикционная симметрия.

## 11. Контроль качества

### 11.1. Golden — регрессионная сеть, не измерение качества

golden-fast (30, PR) / golden-full (100–200: смена модели/правил/каталога, релиз). Порог 80% — временный порог калибровки MVP. Критические классы (допустимо 0): любой false ✅; false ❌ на Кр-параметрах.

### 11.2. Retrieval-golden и extraction-golden

retrieval-golden: 30–40 пар «параметр → целевой чанк» (половина авто из evidence-URL golden, половина — ручные кросс-язычные). Прогон при смене эмбеддинг-модели/чанкера/fusion-параметров + **выбор retrieval-профиля (R0/R1/R2) в M1**. extraction-golden: страницы с известными фактами; A/B экстракторов при смене extractor_version.

### 11.3. Acceptance MVP

```
R1  100% registry facts имеют source_url
R2  100% evaluated ✅/⚠️ имеют валидное evidence
R3  failed никогда → ❓ автоматически
R4  N/A невозможен автоматически
R5  inheritance не создаёт статус без выполнения правила
R6  golden agreement ≥ 80% (временный порог калибровки)
R7  воспроизводимость двойного прогона ≥ 95%
R8  0 известных инъекций на adversarial-корпусе (регрессионный gate, не assurance)
R9  recall@20 retrieval-golden ≥ 0.9
R10 recall@20 кросс-язычная ≥ 0.8
R11 sensitivity: ранжирование устойчиво к ⚠️ ∈ {0.25, 0.5, 0.75},
    иначе Resolved Capability демотирован до неранжирующего индикатора
```

### 11.4. Portability gate

Чеклист нейтральности v2 (11 пунктов: каталог без чужих терминов · upstream-деривативность/baselines · роли+маркеры · showcase-параметры+метрики рынка · реестры · эталон (для C — явная фиксация отсутствия) · N/A-политики · языки · (B) кросс-линейные · (C) калибровочный пол · грепп-тест). **Правка `core/` при онбординге кейса = блокировка кейса.** Пять кейсов дают **первичное эмпирическое подтверждение** гипотезы нейтральности.

### 11.5. Ручной baseline-эксперимент 

Независимый ручной проход аналитика по стратифицированной выборке кейса 1 (~120–150 ячеек: статус, evidence, обоснование — без знания системных вердиктов). Сравнение с системой: FP/FN **по классам ошибок**, валидность цитат, дельта coverage, оценка сэкономленного времени. Побочный продукт — сидирование golden-full. Планируемая стоимость: 20–40 экспертных часов. Это и есть «калибровка методологии» — самое дорогое место проекта по независимой оценке.

### 11.6. Preliminary-метрики и CI

Yield · расхождение кандидат/strict на golden · время прохода. CI: грепп-нейтральность · линт · юнит на валидатор/резолвер/ренормализацию/инварианты · retrieval-CI на NpyVectorIndex (без контейнеров) · golden-fast на PR.

## 17. Глоссарий

**Якорь** — система координат отчёта, не базлайн. **Фокус** — scope сравнения. **Кейс** — пакет категории + продукты + якорь. **Архетип** — тип категории по OSS-upstream (A/B/C). **Базлайн** — upstream-линия наследования. **Роль** — инженерная функция с реестром в пакете. **Сателлит** — компонент, описанный тройкой origin/relationship/evidence_state. **Relationship evidence** — двухчастное доказательство связи спутника с продуктом в роли. **Паспорт** — гипотеза экосистемы, фиксируется G2. **Ячейка** — (продукт, параметр, прогон). **Evidence** — машинно-проверяемый объект доказательства (1..N), с `source_scope` для absence-evidence. **Чанк** — единица индексации с heading_path и метаданными изоляции. **Словарь концептов** — детерминированная синонимичная экспансия. **Retrieval-профиль** — конфигурация гибридного поиска цикла, фиксируется измерением (R0/R1/R2), симметрична (I16). **Индексная сборка** — иммутабельный снапшот индекса. **Retrieval-/Extraction-golden** — эталоны качества ретривала/экстракции. **Исчерпание** — машиночитаемое состояние протокола поиска. **Preliminary-ячейка** — кандидат с невалидированной цитатой; вне расчётов. **Promote** — строгая переаттестация. **Resolved Capability Score** — подтверждённое соответствие по разрешённым статусам; «из исследованного — подтверждено N%». **Evidence Coverage** — взвешенная полнота прохождения протокола. **Comparability** — производная аннотация Coverage, не независимая метрика. **Sensitivity** — устойчивость ранжирования к коэффициенту ⚠️. **Пакет категории** — данные предметной области; ядро их не содержит. **Аксимы A1–A3** — руководящие принципы §0.
